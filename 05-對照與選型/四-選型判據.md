# 三 · 選型判據

> **一句話定位**：這篇的目標是**讓判斷可以機械回答**——
> 不問「你覺得哪個好」，只問「**你的情況滿足哪幾個條件**」，然後對照到結論。

---

## 1. 第一個判據：要不要上這套方法？

### 1.1 三個條件（全部成立才需要）

| # | 條件 | 為什麼是它 | 怎麼自己確認 |
|---|---|---|---|
| **A** | 你有 **≥ 2 個 AI 場景／工作台**（不是「打算有」，是「現在就有」） | 1 個場景用不上「共享層五塊板」與「場景主權」——那些機制是為了**多個**場景不打架 | `ls <工作台根>/場景/` 數一下 |
| **B** | **會話會被換掉**（你會主動換、或上下文滿了會被壓縮） | 這是場景記憶存在的**唯一理由**。不會換會話 ⇒ 記憶放檔案沒有意義 | 問自己：「上週有沒有會話被換掉過，換掉之後要重講一遍？」 |
| **C** | **狀態會遺失**（換會話後狀態真的不見了／你真的重講過） | 如果不會遺失，就沒有痛點要解 | 「上次換會話，我重講了哪些東西？」列出來 |

### 1.2 決策樹

```
① 你有 ≥2 個 AI 場景／工作台？
   │
   ├─ 否 → ❌ 不需要這套方法。
   │        一個場景用「一個 markdown 檔 + 一段 §〇 交接」就夠了。
   │        上整套方法＝為不存在的問題買複雜度。
   │
   └─ 是 → ② 會話會被換掉嗎？
            │
            ├─ 否 → ❌ 不需要（但先確認 B 的判斷準確：
            │        「引擎會自動壓縮」≠「會話會被換掉」）
            │
            └─ 是 → ③ 換會話後狀態真的會遺失嗎？
                     │
                     ├─ 否（你都有別的方法記著） → ❌ 不需要
                     │
                     └─ 是 → ✅ 需要。往下看：做到哪一級？
```

### 1.3 對照表

| A（≥2 場景） | B（會話會被換） | C（狀態會遺失） | 結論 |
|---|---|---|---|
| ❌ | 任何 | 任何 | **不需要**。單場景用簡單檔案就夠 |
| ✅ | ❌ | 任何 | **不需要**（先確認 B） |
| ✅ | ✅ | ❌ | **不需要**。你已有別的狀態管理方式 |
| ✅ | ✅ | ✅ | **需要** → 進 §2 選級別 |

> **三個條件是「且」不是「或」。**
> 只滿足 A（多場景）就上整套方法，最常見的結果是：**維護成本大於收益，半年後整個停用。**

## 2. 第二個判據：做到哪一級？

不是全做或全不做。三個層級，成本遞增，**收益遞增**。

| 層級 | 做什麼 | 成本 | 解掉什麼痛 | 什麼時候停在此級就夠 |
|---|---|---|---|---|
| **L0 最小可用** | 每場景一份記憶檔；`§〇` 交接 ≤ **4 096 位元組**（硬紅線，實測值）；**換會話前先寫交接** | **極低**（純習慣） | 換會話失憶 | 你只有 2 個場景、而且不會互相踩 |
| **L1 完整場景** | 加：六件套、**`.git` 劃界**、專屬技能、身份索引、共享層五塊板、場景主權規則 | 中（一個下午） | 場景串台、互相踩記憶、規則到處複製 | 你的場景之間會碰到彼此的檔案或職責 |
| **L2 有工具** | 加：校驗工具（`check`／`stamp`／`交接`）、**fail-closed**、派單四件套、回執回收（差異集合） | 中高（要寫工具） | 「做完了沒」查不出來、交接漏寫沒人知道 | 你的場景 ≥ 3 個，且已經開始出錯 |

> **建議路徑：先做 L0，用一週再決定要不要 L1。**
> 大部分人只做到 L0 就已經覺得值回票價——因為「換會話失憶」是最痛、也最常發生的那個。

### 2.1 選級別的決策樹

```
① 你已經會寫派單、會回執了嗎？
   │
   ├─ 會 → L1 足夠。把寫工具的時間省下來花在別處。
   │        （工具是給「流程上做不到」的人用的）
   │
   └─ 不會／常常忘 → 先用模板（04-模板/派單模板.md），那比工具划算。
                     模板是「形狀」，工具是「強制」。
                     模板都用不起來 ⇒ 工具也不會用。

② 你的場景之間會互相影響嗎（做 B 場景時會用到 A 場景的檔案）？
   │
   ├─ 會 → L1，而且要重新想場景劃分（可能該合併）
   └─ 不會 → L1（主要為了「各自的記憶不串台」）

③ 你的場景數 ≥ 3，且已經出過事（交接漏寫、記憶被覆蓋、看板寫錯地方）？
   │
   ├─ 是 → L2（有工具才有 fail-closed）
   └─ 否 → L1 跑三個月再說
```

> ⚠️ **判斷順序很重要：先解決「流程上你做不到」的部分，再上工具。**
> 給一個不寫回執的人一套精密的回執工具，他還是不會寫回執。

## 3. 第三個判據：幾個場景算夠？

### 3.1 一個場景的定義

> **判據（一條就夠）**：這類活**會反覆回來**，而且**每次都用到同一批檔案、同一套規矩、同一個領域的知識**。

| ❌ 不是場景 | ✅ 是場景 |
|---|---|
| 「今天做影片」——一次性的任務 | 「影片工作流」——每次做片都要用到分鏡規範、素材庫、發布檢查 |
| 「一個專案」——有明確結束點 | 「場景丁」——每週都會回來，永遠不會結束 |
| 「按工具分」——一個工具一個場景 | 「按職能分」——一段職責一個場景 |

### 3.2 場景數與專案數的對應

| 問題 | 答案 |
|---|---|
| 一個場景底下可以有多個專案嗎？ | ✅ 可以。**專案結束，場景還在**（專案記憶放在**場景**底下） |
| 幾個專案算一個場景？ | **看「會不會用到同一批檔案、同一套規矩、同一個領域的知識」**，不看數量 |
| **超過 3 個專案，該不該一個專案一個場景？** | **不該。** 見 §3.3 |
| 幾個場景算夠？ | **場景數由「有幾類會反覆回來的活」決定，不由專案數決定。** 下限是 **2**（見 §1 條件 A）；上限沒有硬規則，但**每多一個場景就要多養一份記憶檔、一套憲法、一個 git 倉庫** |

### 3.3 「超過 3 個專案不該一個專案一個場景」的理由

| 理由 | 說明 |
|---|---|
| **場景＝邊界，不是資料夾** | 一個專案一個場景 ⇒ 每個場景都要獨立 git 倉庫、獨立憲法、獨立技能、獨立交接檔。**維護成本隨場景數線性上升，收益不上升** |
| **專案有結束點，場景沒有** | 專案結束 ⇒ 場景就該合併回職責層。留著空場景會出現「場景越來越多，每個都沒活」 |
| **切太細的徵兆** | 場景裡總在講別人的事；兩個場景用同一批檔案；每個場景的 §〇 都只有兩三行 |
| **正確的切法** | **一個場景＝一類會反覆回來的活**。3 個專案只要是同一類活（例如都是同一個影片工作流的不同片子），就該放同一個場景，**用專案記憶分** |

> **數字判據**（健康 vs 警訊）：
> **專案數 > 場景數** ⇒ 正常（場景裡有多個專案，這是設計的樣子）。
> **專案數 ≈ 場景數** ⇒ 警訊，你可能把專案當場景切了。
> **專案數 < 場景數** ⇒ 一定切錯了（場景比活還多）。

## 4. 場景記憶 vs 通用任務管理工具（Todoist 之類）

**這兩者管的不是同一種東西，而且被搞混的機率很高。**

| | 場景記憶 | 通用任務管理工具（Todoist / Things / Jira 之類） |
|---|---|---|
| **管的對象** | **agent 的狀態** | **人的待辦** |
| **誰讀** | **agent**（新會話開場讀 §₀） | **人**（打開 App 看列表） |
| **誰寫** | agent（寫交接、寫結論）+ 人 | **只有人**（手動打勾） |
| **條目的粒度** | 場景 × 專案（附**下一步**與**卡點**） | 一件事一列 |
| **完成定義** | **判據可驗證**（「列出可釋放 ≥ 1 GB 的項目，每項標明路徑與大小」）＋ 落盤位置 | 打勾 |
| **狀態存放** | 檔案（git 可 diff、可 blame、可回滾） | 服務端資料庫（能不能匯出、能不能自備，看該工具） |
| **換會話後** | **新會話讀完 §₀ 就接得上** | 不相干——那是你的私人待辦，跟 agent 的上下文無關 |
| **逾時** | 沒有（靠人看） | 有（截止日、提醒、逾期標紅） |
| **人介入** | 門檻低：Markdown 隨手改 | 順手：打勾 |
| **成本** | 零網路請求 | 雲端服務 + 帳號（多數免費，但資料在別人那） |

### 4.1 該用哪個

| 你的需求 | 選 |
|---|---|
| 「我下午要交這份報告」 | **通用任務工具**。這是人的待辦。 |
| 「這個 agent 的活幹到哪、卡在哪、換個人接手要多久」 | **場景記憶**。這是 agent 的狀態。 |
| 「這週有 20 件事要做」 | **通用任務工具** |
| 「這個專案做到第 3 步，第 3 步的產出檔在 `<路徑>`」 | **場景記憶** |
| 「提醒我下午 3 點前回覆那封信」 | **通用任務工具**（場景記憶沒有逾時機制） |
| 「昨天那個 agent 說它做完了，但數字不對」 | **場景記憶**（要能 diff 回執與證據） |

### 4.2 可以並用嗎？

可以，而且**分工清楚就不會打架**：

```
通用任務工具  →  人的待辦、需要提醒與逾時的事
場景記憶      →  agent 的狀態、跨會話要接續的事
```

> ⚠️ **唯一要防的**：**不要把同一件事同時放兩邊並期待它們同步。**
> 那是「同一個值有兩份定義」——[已知裂縫 #3](../02-落地實作/四-已知裂縫與待修.md)那種分叉的溫床。
> 要麼只放一邊，要麼一邊只放**指針**（「見待辦板第 N 行」）。

## 5. 場景記憶 vs wiki／Notion／Obsidian vault

| | 場景記憶 | wiki／Notion／Obsidian vault |
|---|---|---|
| **誰寫** | **機器寫**（agent 寫交接、寫結論、寫回執）＋ 人修 | **人寫**（你打字、貼筆記） |
| **誰讀** | **機器讀**（新會話開場讀 §₀ 開工） | **人讀**（你打開來看） |
| **寫入門檻** | 低到可以自動化，但**必須符合格式**（五小節齊、≤ 4 KB） | 隨便寫，格式隨你 |
| **失敗怎麼樣** | **fail-closed**：缺小節或超紅線 ⇒ `check` 報錯 ⇒ **不許換會話** | 不會「失敗」；寫壞了就寫壞了，沒人擋 |
| **稽核** | `git log` 全在，可 blame、可 diff | 很多有版本歷史，但**不是同一回事**（多半只記「誰改了哪一段」，不記「這份狀態為什麼長這樣」） |
| **狀態語意** | 有明確語意：**現在**做到哪、下一步、卡在哪 | 沒有狀態語意；是**知識**，不是**進度** |
| **寫入方向** | **機器→機器**（這次會話寫、那次會話讀） | **人→人** |
| **典型用途** | agent 的交接、專案進度、回執、決策與坑 | 讀書筆記、參考資料、教學文件、規格 |

### 5.1 該用哪個

| 你的需求 | 選 |
|---|---|
| 「下次開工，agent 要能接上」 | **場景記憶** |
| 「我要把這個技術整理成教學文章」 | **wiki** |
| 「這個專案上次為什麼這樣決定」 | **兩者都要**：場景記憶記**決策與坑**（§五，只追加），wiki 記**展開的說明** |
| 「我要查某個 API 的用法」 | **wiki**（或專門的技能文件） |
| 「agent 要知道『這活現在卡在誰那』」 | **場景記憶**（§₀ 第 4 小節） |
| 「我要把上次踩的坑整理成教學」 | **場景記憶產出 → wiki 收錄**（前者是原料，後者是成品） |

### 5.2 兩者的關係不是二選一

> **場景記憶是「活的」，wiki 是「寫完的」。**
> 場景記憶每天被覆蓋寫、被 git 追蹤；wiki 是累積的、不動的。
> **場景記憶是原料，wiki 是成品**——把場景記憶裡成熟的坑與決策沉到 wiki，
> 是很自然的單向流動：**場景 → wiki 可以；wiki → 場景自動回寫不可以**（會造成狀態分裂）。

## 6. 該用／不該用 決策表（本篇主體）

### 6.1 該用

| # | 情況 | 做到哪一級 | 為什麼 |
|---|---|---|---|
| 1 | 多個 AI 場景在同一台機器上，會話會被換掉 | **L0**（再視情況 L1） | 換會話失憶是最常見、最痛的問題 |
| 2 | 兩個 agent 會動到同一份東西，怕互踩 | **L1** | 需要物理隔離（獨立 git 倉庫）＋場景主權 |
| 3 | 要追「誰在什麼時候改壞了記憶」 | **L1**（要稽核就得上 git） | `git log`＋`git blame` 是最低成本的答案 |
| 4 | 有人要接手你的工作，而且要能改 | **L1** | Markdown 人可讀可改，取代「問原作者」 |
| 5 | 要交給別人用／要在 CI 裡擋 | **L2** | 需要可執行的 fail-closed 閘門＋正確退出碼 |
| 6 | 多個場景、同一套規矩、同一個人 | **L1** | 共享層五塊板開始有價值 |
| 7 | 想要跨場景召回「以前的做法」 | 場景記憶 ＋ **語意記憶** | 見[三-場景記憶與語意記憶](三-場景記憶與語意記憶.md) |

### 6.2 不該用

| # | 情況 | 為什麼 | 該怎麼做 |
|---|---|---|---|
| 1 | **只有 1 個 AI 場景** | 多場景機制（共享層五塊板、主權規則）沒有對象 | 一個 markdown 檔 + 一段 §₀ 交接 |
| 2 | **會話從來不換** | 場景記憶的唯一理由不存在 | 老實說：你不需要這套方法 |
| 3 | **想用它當團隊待辦工具** | 它管 agent 的狀態，不是人的待辦 | 用通用任務管理工具（見 §4） |
| 4 | **想用它當知識庫／wiki** | 它管「現在」，不是「以前」 | 用 wiki；場景記憶留「決策與坑」的原料 |
| 5 | **要跨組織、跨廠商協作** | 場景派的前提（同機、同一套規矩）不成立 | 上 A2A（見[二-與A2A協定的對照](二-與A2A協定的對照.md)） |
| 6 | **要跨機器** | 檔案派的前提不成立 | 記憶層可留檔案，**派單通道**改走網路 |
| 7 | **只是想要「agent 越用越懂」** | 那是語意記憶的價值，不是場景記憶的 | 兩者分工：狀態歸場景，經驗歸語意 |
| 8 | **要處理幾十幾百個 agent 的任務分派** | 場景派沒有逾時、重試、續傳、服務級 SLA | A2A 或專門的任務基礎設施 |
| 9 | **團隊不肯花時間寫交接** | 整套方法的價值建立在「有人寫交接」上 | 先用模板；模板用不起來就別上整套 |
| 10 | **要 100 % 自動、不許人介入** | 場景記憶的寫入者是「人＋工具」；純自動抽取是語意層的事 | 兩層分工：狀態檔案、經驗語意 |

### 6.3 容易搞混的四組（一張速查）

| A | B | 差別一句話 |
|---|---|---|
| 場景記憶 | 通用任務工具 | 前者管 **agent 的狀態**，後者管 **人的待辦** |
| 場景記憶 | wiki／Obsidian | 前者**機器寫、機器讀、fail-closed**；後者**人寫、人讀** |
| 場景記憶 | 語意記憶 | 前者回答**現在**，後者回答**以前** |
| 場景記憶 | A2A | 前者是**檔案＋目錄路由**，後者是**能力發現＋任務生命週期**；同機用前者，跨組織用後者 |

## 7. 一個務實的起步路徑

```
第 1 天 ──▶ 建一個場景目錄，git init，寫一份場景私有記憶.md
             （不用管六件套，先有 §〇 和核心職責）

第 3 天 ──▶ 換一次會話，體會「沒寫交接」是什麼滋味
             （這是整套方法論的轉折點）

第 1 週 ──▶ 加第二個場景，跑起來
             開始注意「場景之間會不會互相干擾」

第 1 月 ──▶ 加身份卡 + 工具 stamp，開始有「卡指紋」的概念

第 3 月 ──▶ 加校驗工具 + 派單模板
             這時你已經清楚自己要什麼了——工具才寫得對
```

> **這個順序不是「由簡到全」，是「由痛到解」。**
> 每一步都對應一個你真的感覺到的痛，而不是一個抽象的完整架構。

## 8. 最後一條判據

> **如果這套方法在你自己的機器上，沒有讓你「換會話時不用重講一遍」——
> 那它就沒有價值，不管它多完整。**

所有設計最終都要回到這一句：
**新會話讀完 §〇，30 秒內能不能說出「下一步該幹什麼」。**

## 9. 需要機主拍板的判據（誠實列出）

這幾條**不是技術問題，是 取捨**，本文件只能提出建議，**要機主決定**：

| # | 判據 | 建議 | 為什麼需要拍板 |
|---|---|---|---|
| 1 | **語意層要不要接進來**（Hindsight 是否成為工作台的一部分） | 建議**接，但只當索引**：檔案是真源，語意層只負責召回 | 這決定了整套方法的複雜度與「兩份真相」的風險承擔 |
| 2 | **場景記憶要不要內建「匯出到 wiki」的流程** | 建議**要**，但要**單向、有人工確認** | 自動回寫 wiki 會造成狀態分裂；不自動又會手動到沒人做 |
| 3 | **場景記憶的邊界要不要對外（跨機器的共享層）** | 建議**先不要**；真要跨機再回頭設計 | 跨機共享會把「檔案是唯一介面」變成「檔案 + 同步機制」，是另一套架構 |
| 4 | **紅線數字（4 KB / 25 KB / 8 KB）要不要寫死在規格裡** | 建議**寫死成常數，但集中在 `交接規則.json` 單一來源** | 寫死＝可機械判定；集中＝要改時只改一個地方（[維護手冊](../02-落地實作/三-維護手冊.md)的原則） |
| 5 | **要不要把「逾時偵測」列為 P0** | 建議**升為 P0**（目前[已知裂縫 #2](../02-落地實作/四-已知裂縫與待修.md) 是 P2） | 「沒人接」發現不了是派單鏈最實在的洞；升級順序涉及取捨 |
| 6 | **要不要承諾「跨組織協作」** | 建議**不承諾**；需要時走 A2A | 承諾了就等於要維護跨機制、跨信任邊界的東西，成本完全不同 |
