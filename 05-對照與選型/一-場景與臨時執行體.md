# 一 · 場景與臨時執行體

> 這篇回答一個很具体的問題：**主流框架都有 sub-agent（臨時執行體），為什麼還要場景？**
>
> 答案不是「sub-agent 不好」。sub-agent 在它擅長的地方非常好。
> 這篇要說的是**兩者適不適合同一種活**——以及差異真正的位置在哪。

---

## 1. 先講清楚：sub-agent 擅長什麼

|sub-agent 的優點 | 說明 |
|---|---|
| **隔離** | 它的 context 乾淨，不污染主線對話 |
| **便宜** | 派出去就是一次任務，不用養常駐的東西 |
| **可並行** | 幾個子任務同時跑，總時間是較慢那一條 |
| **context 不炸** | 主線只拿到結論，拿不到中間那堆探索 |

**這四點都是真的，而且很多活就該用 sub-agent。** 一句話的查詢、一次性的重構、一段需要獨立 context 的探索——這些不該開新場景。

## 2. 真正的差異在哪

三點，全部成立。

### 差異一：有沒有自己的事件歷史

sub-agent 的定義**可以改**——角色設定、系統提示、工具清單都是可編輯的。
但它記錄的是「**這角色是什麼**」，不是「**這件事上次怎麼做**」。

| | sub-agent | 場景 |
|---|---|---|
| 角色設定 | 有，可編輯 | 有（定位卡＋身份卡） |
| **這件事的歷史** | **無** | 有（`§〇` 交接、`§五` 決策與坑） |
| 專案/任務的進度 | 只在當輪 context | 落盤，跨 session 存活 |

> **所以「sub-agent 不可改」這句話是錯的。** 錯的是把「角色設定」當成「經驗」——
> 角色設定說明它是誰，經驗說明它做過什麼。**只有後者會累積。**

### 差異二：累積會不會回流

sub-agent 產生的經驗，預設只留在**那一輪的 context** 裡。session 一結束就沒了。

要回流，必須有人主動把它寫進某個檔案。**主流框架沒有給這個位置**——不是不給權限，是沒有「這個位置」的觀念。

場景的做法是：**回執必須帶可累積物，並寫回場景記憶。**
這件事之所以能成立，是因為場景本來就是「一個會長期存在、會被改寫的東西」。

### 差異三：誰是本體

| | sub-agent | 場景 |
|---|---|---|
| 存在條件 | 被召喚的那一輪 | **不依賴任何一次呼叫** |
| 走掉之後 | 什麼都不剩 | 檔案還在，下次接得上 |
| 誰持有 | 沒有持有者（臨時物） | **主控端** |

> **臨時執行體是對的設計——它本來就該用完即棄。**
> 問題從來不是「它不夠好」，是「別把累積的期待放在它身上」。

## 3. 那什麼時候該用哪個

| 活的性質 | 用誰 | 理由 |
|---|---|---|
| 一次性查詢、獨立探索 | **臨時執行體** | 隔離＋便宜，開個場景太重 |
| 同類的活會**反覆回來** | **場景** | 需要累積，需要記住上次怎麼做 |
| 需要跨 session 活著 | **場景** | sub-agent 的 context 不跨 session |
| 結果要能被稽核、被回滾 | **場景** | 場景有 git 歷史 |
| 大量平行、互不相干 | **臨時執行體** | 場景的邊界成本不划算 |
| 一次要跑一大串有順序的事 | **場景＋工作流** | 工作流是場景的編排，不是 sub-agent 的 |

> **判準一句話：這件事的價值，有沒有超過「它上次是怎麼做的」。**
> 沒有 → sub-agent。有 → 場景。

## 4. 兩者不是互斥的：場景裡本來就有 sub-agent

這是最容易誤解的地方。**場景不是 sub-agent 的替代品，是它的持有者。**

```
主控端（持有場景）
  ├─ 派活給場景 ──▶ 場景自己開對話、必要時再派臨時執行體
  │                      ↑
  │                 臨時執行體：用完即棄，成果回到場景
  ↓
  可累積物寫回場景記憶  ← ★ 累積發生在這裡，不在臨時執行體身上
```

場景執行一件事時，內部完全可以拆出臨時執行體去並行處理幾個子任務。
**差別只在最後一步：那些子任務的產出，必須被收回場景。**

> 這也回答了「場景會不會太笨」的問題：
> 場景不比 sub-agent 聰明，它只是**記得比較多**。
> 而「記得比較多」在反覆回來的活上，比聰明有用。

## 5. 為什麼不用 A2A 這類跨主體協作協定

工作流看起來很像「agent 之間互相派活」——但方向相反。

| | A2A 這類協定 | 這套架構的工作流 |
|---|---|---|
| 協作對象 | **不同主體**（不同組織的 agent） | **同一個本體內部的不同場景** |
| 傳遞的東西 | 任務、狀態、產物 | **可累積物** |
| 關係 | 委託關係，彼此不認識 | **同一個場景體系，共用規矩與台帳** |
| 信任基礎 | 協定與憑證 | **同一份檔案、同一套規矩** |
| 人怎麼介入 | 通常插手不進去 | 隨時讀檔、隨時改 |

> **工作流是「同一個本體內部的接力」，A2A 是「不同本體之間的委派」。**
> 需要的不是跨主體信任，是同一主體內的分工與累積。
> （完整對照見[二-與A2A協定的對照](二-與A2A協定的對照.md)）

## 6. 這套架構不擅長什麼

誠實清單：

| 不擅長 | 說明 |
|---|---|
| **一次性的短任務** | 開場景的成本遠高於開一次 sub-agent |
| **大量互相獨立的平行任務** | 場景有邊界成本，sub-agent 沒有 |
| **跨組織、跨信任域的協作** | 這是 A2A 的地盤，不要硬套 |
| **即時的流暢對話** | 場景之間靠檔案，不是靠對話 |
| **不打算累積的活** | 那是 sub-agent 的位置，別硬塞 |

## 7. 一句話記住

> **sub-agent 每次都從零開始，場景從上次的地方開始。**
> **前者擅長一次性，後者擅長反覆回來。**
> **要哪一個，先問：這件事的價值有沒有超過「它上次是怎麼做的」。**
