# 二 · 場景記憶與語意記憶

> **一句話定位**：這篇是[六-兩套記憶的分工](../00-核心機制/六-兩套記憶的分工.md)的**選型視角**——
> 那篇講「它們是兩個層次」，這篇講「**面對一個具體需求，你放哪一邊、怎麼防止兩邊串味**」。

> 📌 **量測說明**：本文所有語意層數字為**本機實測值**（Hindsight 語意記憶服務，本機 Docker 部署），
> 量測時間 **2026-10-31 / 2026-11-01**。場景記憶層數字為本機工作台實測值。

---

## 1. 兩層的定位（各一句）

| | 場景記憶 | 語意記憶 |
|---|---|---|
| **比喻** | **帳本**（ledger） | **wiki** |
| **回答的問題** | **現在**做到哪、欠誰的活 | **以前**學到什麼、上次怎麼解 |
| **形態** | 一份 ≤ 4 KB 的交接檔（§〇）+ 專案記憶 + 共享層五塊板 | 數萬條事實節點（實測：單一 bank **14 489** 個 fact 節點） |
| **誰寫** | 人 + 工具主動寫 | 機器每 N 輪自動抽 |
| **覆蓋** | **窄**——只有你主動寫進去的 | **廣**——所有聊過的都進來，不靠自覺 |
| **召回時機** | 開場先讀 §〇，**精準且零網路請求** | 每輪 prefetch（實測上限 **2 048 token**） |
| **隔離** | **強**：每場景獨立 git 倉庫，模型看不到別場景的東西 | **弱**：預設多 profile 共用同一個庫 |
| **可稽核** | `git log` 全在，可 diff、可 blame | 抽取結果本身**不可 diff**（要靠服務端 log 側推） |
| **失敗模式** | 交接沒寫 → 下一任接手缺一步 | 抽取錯了 → 錯誤**長期留在記憶裡**，之後被當事實召回 |
| **成本** | 零網路請求 | 每次抽取都燒 token（實測：單次 retain 排隊約 **18.8 s** 牆鐘時間） |
| **人能救場嗎** | **能**：Markdown，人可讀可改 | **較難**：得另外寫一份 correction 文件去蓋 |

> **一句話總結**：
> **只留帳本，agent 不會變聰明；只留 wiki，你會忘記昨天那個活兒到底誰做了一半。**

## 2. 語意層的實測數字：失敗率與它的形狀

語意層最大的風險是**失敗是靜默的**。所以失敗率必須是可觀察數字，而不是「應該很少」。

### 2.1 失敗率（實測值，快照 2026-10-31 09:27 UTC）

| 指標 | 數值 | 口徑 |
|---|---|---|
| **整體失敗率** | **約 0.89 %** | 22 次失敗 ÷ 2 465 次操作總數（failed ÷ 總數） |
| 失敗 ÷ 成功 | 0.90 % | 22 ÷ 2 443（completed） |
| **只看抽取類操作** | **1.30 %** | 22 ÷ 1 692（retain + batch_retain，不含 consolidation） |
| 只看 consolidation 類 | **0 %** | 0 ÷ 804 |
| 量測快照 | 2026-10-31 09:27（UTC） | 該時點 completed = 2 443、failed = 22、總計 2 465 |

> ⚠️ **這是快照值，不是常數。** 隨著服務累積操作，分母會變；2026-11-01 複測為
> completed = 2 482、failed = 22、總計 2 504 ⇒ 整體失敗率 **0.879 %**（失敗次數不變，分母變了）。
> **引用時務必附上量測時點**，否則兩個月後的讀者會以為數字錯了。

> ⚠️ **口徑要講清楚**：0.89 % 是「**全部操作**」的失敗率（含抽取與整併兩類）。
> 若只看**抽取本身**（retain + batch_retain），失敗率是 **1.30 %**，比整體口徑高。
> 引用這個數字時要連口徑一起引用，否則會低估。

> **這 0.89 % 看起來很小，但要看它怎麼分布**——這才是重點。

### 2.2 失敗不是隨機的，是**成群**的（實測值）

| 觀察 | 數據 | 意義 |
|---|---|---|
| 失敗集中在少數幾天 | 22 筆失敗分布在 **5 天**：10-17（10 筆）、10-18（2）、10-28（4）、10-29（4）、10-30（2）；其餘 16 天**零失敗** | 失敗是**事件性**的，不是每天都有 |
| 22 筆失敗其實是 **11 次真實失敗** | 每個失敗都同時記一筆 `retain` 與一筆 `batch_retain`（父／子同一事件） | **別把 22 當成 22 個不同事故** |
| 受影響文件數很少 | **5 份**文件有 `document_id`；另有 6 筆早期失敗（10-17／10-18）沒有 `document_id` | 失敗集中在少數幾個檔案，不是全面性的 |
| 主流失敗原因是**上游限流**，不是抽取邏輯壞掉 | 22 筆中 **18 筆是 HTTP 429**（`Token Plan usage limit reached`），**4 筆是 TimeoutError** | 抽取失敗 ≠ 內容錯；多是**沒配額沒回應** |
| 失敗會**先重試 3 次**再放棄 | 22 筆中 11 筆 `retry_count = 3`、11 筆 `retry_count = 0` | 有重試機制，但重試完還是會放棄 |
| 失敗的規模很小 | 每次失敗的錯誤訊息都是 `1/1 chunks failed`——**每個失敗事件只損失 1 個 chunk** | 損失是局部的，不是整份文件沒進來 |

### 2.3 這個數字對決策的意義

> **0.89 % 的失敗率本身不構成「不要用語意記憶」的理由。**
> 理由是**失敗的形狀**：
>
> - 失敗是**成群**的 ⇒ 你的失敗率不是 0.89 %，而是「**平常 0 %，某天突然 40 %**」。
> - 失敗是**靜默**的 ⇒ 那 40 % 那天，你以為自己有記憶，其實沒有。
> - 失敗是**上游配額**造成的 ⇒ 它跟你寫得好不好無關，你**控制不了**。
> - 失敗留下的是**空白**（該抽取的內容沒進庫），但更大的風險是**抽取錯了還進去了**——
>   那一類在失敗率裡**根本不算數**，因為它「成功」了。
>
> ⇒ **判斷語意層健不健康，不能只看失敗率，要看「有沒有可觀察的失敗率」這件事本身。**
> 這個數字必須能被定期拉出來、被人看到（實測可行的做法：
> 語意服務提供 `failed_operations` 與 `operations_by_status` 兩個欄位，直接可查）。

## 3. 串味怎麼治：三個層次

「串味」＝ 場景 A 寫進去的專業事實，場景 B 召回時也帶出來。
三個層次**由強到弱**（隔離最徹底、覆寫最溫和），**但不是三選一——是三個不同的開關**。
**能停在第 ① 層就不要往下走。**

### 層次 ①　bank 隔離 —— 路徑即邊界

| 項目 | 內容 |
|---|---|
| **做法** | 不同場景用**不同的 bank**；`mapPathToBank` 把每個場景路徑明確對應到自己的 bank（最長前綴優先） |
| **範例配置** | 見下方 `mapPathToBank` 片段 |
| **效果** | 隔離乾淨：A 場景寫的東西，B 場景**召不到** |
| **代價** | 失去跨場景召回（要跨場景共享，得另外給共享層一個專用 bank） |
| **本機實況（2026-11-01）** | 語意服務上**實際只有 2 個 bank**（皆為通用用途，非場景專用）；**沒有**依場景切好的 bank；`wb-shared` 這類共享層 bank **目前不存在**（查詢回 `not found`） |

```jsonc
// 設定模板片段（形狀，不是本機現況）
"mapPathToBank": {
  "<工作台根>/場景/<場景A>":   "coding-agent::<scene-a>",   // ← 每場景一個 bank
  "<工作台根>/場景/<場景B>":   "coding-agent::<scene-b>",
  "<工作台根>/場景/<場景C>":   "coding-agent::<scene-c>",
  "<工作台根>/場景/_共享記憶": "wb-shared"                  // ← 跨場景召回事實的固定落點
}
```

### 層次 ②　標源 —— 記住「這條事實來自哪個場景」

| 項目 | 內容 |
|---|---|
| **做法** | 共用同一個 bank 時，**retain 時就記下來源**：`source = <場景名>`（實作上是 `retainTags` 之類的來源標籤），召回時可依來源過濾 |
| **效果** | 保留跨場景召回能力，同時**召回到時知道它是哪個場景的**——不串味，只是**分得清** |
| **前提（重要）** | **過濾機制必須真的存在**。標了源卻不能過濾，等於沒標 |
| **代價** | 需要在 retain 流程裡強制寫入來源；來源欄位漏填的那條會變成「無源事實」，召回時要能被辨認出來 |

> ⚠️ **標源 vs 隔離的取捨**：
> 標源是「知道來源但不擋」，隔離是「根本看不到」。
> **需要跨場景共享經驗 → 標源；不需要 → 隔離。**
> 別用標源假裝隔離——標源只是**可辨認**，不是**不可召回**。

### 層次 ③　覆寫 —— 場景層可以覆寫全域注入設定

| 項目 | 內容 |
|---|---|
| **做法** | 全域層設定的是**預設值**；場景層可以**覆寫**全域注入的內容（例如：本場景不召回某個 bank、不開某個工具、召回時加上本場景的過濾條件） |
| **效果** | 不用改全域設定就達成**局部隔離**；改全域設定會影響所有場景 |
| **這是本架構原生就有的模式** | 兩層憲法就是這樣疊的：全域 `AGENTS.md`（每輪注入）＋ 場景 `AGENTS.md`（只在本場景樹內） |
| **前提** | 覆寫必須**顯式宣告**（不是「沒寫就覆寫」）——否則誰也不知道某場景的行為被改過 |
| **代價** | 覆寫多了會**漂移**：全域改了、場景沒跟著改，行為就不一樣了（⇒ 覆寫要能被 `check` 看到） |

### 3.1 三層怎麼選

| 你的狀況 | 該停在哪一層 | 理由 |
|---|---|---|
| 場景之間**不該**互相看到對方的專業事實 | **① 隔離** | 最省事、最徹底。沒有過濾機制時，① 是唯一安全的選擇 |
| 場景之間**偶爾**要共享經驗，且共享是公開的 | **① + ②** | 共享層給專用 bank；其餘維持隔離 |
| 已經共用一個庫、短期無法拆 | **② 先行** | 先標源讓「來源」可辨認，再排期拆庫 |
| 某個場景有特殊需求（不召回全域設定） | **③** | 覆寫是例外通道，不是預設路徑 |

> **分庫做一半是最糟的狀態**：庫分好了，但配置沒切、內容沒搬，
> 結果是「以為隔離了，其實沒有」——**比不做還危險，因為它讓你停止警覺**。

### 3.2 串味的三個早期徵兆（可以自己查）

| 徵兆 | 大概原因 | 怎麼查 |
|---|---|---|
| 場景 B 召回結果裡出現場景 A 的專有名詞 | 層次 ② 沒做，或過濾沒生效 | 隨機抽 5 筆召回結果，檢查有沒有跨場景的專有名詞 |
| 「以為隔離了，其實沒有」 | 層次 ① 只做了配置、沒搬內容 | 查實際 bank 數量與實際有內容的 bank 是否一致 |
| 覆寫後行為跟預期不符 | 層次 ③ 覆寫沒宣告，或全域改了場景沒跟 | 覆寫要進 `check`，不能靠人記 |

## 4. 需求 → 該用哪種記憶（選型表）

| 需求 | 選 | 為什麼 | 放錯的樣子 |
|---|---|---|---|
| 換會話後要知道「幹到哪」 | **場景記憶** | 這是**狀態**，必須精確、必須一次只一個答案 | 塞進語意記憶 → 召回靠相似度，回「上次好像有提到…」 |
| 知道「下一步該幹什麼」 | **場景記憶** | 這是**指令**，不能有歧義 | 塞進語意記憶 → 召回排序會把它排到第 5 名 |
| 知道「現在卡在哪、欠誰的活」 | **場景記憶** | 這是**待辦**，有 owner、有到期 | 塞進語意記憶 → 沒人會主動去看 |
| 判斷「這活到底做完了沒」 | **場景記憶** | 要**可驗證的落點**（檔案、數字、diff） | 塞進語意記憶 → 模型會說「看起來完成了」 |
| 兩個 agent 會不會互踩記憶 | **場景記憶** | 要**物理隔離**（獨立 git 倉庫）＋主權規則 | 只靠語意層標源 → 召回層不是寫入層 |
| 稽核「誰在什麼時候改壞了記憶」 | **場景記憶** | `git log`＋`git blame` | 語意層沒有 diff 能力 |
| 人要能直接接手、接手還要能改 | **場景記憶** | Markdown，人可讀可改 | 語意層要寫 correction 文件才能蓋 |
| 半年後再問同類問題，想不起上次怎麼解 | **語意記憶** | 這是**經驗**，要跨 session 自動累積 | 只留場景記憶 → agent 不會變聰明 |
| 「上次那個錯誤是怎麼解的」 | **語意記憶** | 語意層能跨場景、跨 session 召回 | 場景記憶覆蓋窄，半年後那份檔可能已被歸檔 |
| 不想每次都手寫交接、覺得煩 | **語意記憶**（但**狀態還是得寫**） | 覆蓋廣、零自覺 | ⚠️ 這是最容易自我欺騙的一格：狀態仍然需要場景記憶 |
| 想知道「這個 agent 為什麼會這樣答」 | **兩者都要** | 場景層給**現在的規矩**，語意層給**以前的經驗** | 只留一層都會答得缺一角 |
| 想讓 agent 越用越懂 | **語意記憶**（＋場景記憶守底） | 累積經驗是語意層的天賦 | 把進度也丟進語意層 → 召回出噪音 |
| 要跨場景共享「以前的做法」 | **語意記憶**（＋層次 ① 的共享層 bank） | 需要「找得到」而不是「開得起來」 | 用共享層看板記經驗 → 看板是最新在上，不是知識庫 |

## 5. 一個最常見的誤用：把「進度／下一步／卡點」放進語意記憶

> **這是本篇最想滅掉的一個錯誤做法。**

### 5.1 症狀

| 應該 | 實際被放進語意記憶 |
|---|---|
| §〇 第 2 小節「當前專案」表 | 「這個專案進度 60 %」 |
| §〇 第 4 小節「下一步／卡點」 | 「下一步應該去處理那個回執問題」 |
| 共享層待辦板 | 「還有人欠一件磁碟體檢」 |

### 5.2 為什麼一定會壞（機制層面的原因）

| 原因 | 說明 |
|---|---|
| **召回靠相似度，不靠「這是最新的」** | 語意層沒有「最新優先」的排序保證。你寫的「下一步」可能和三個月前另一段相似的文字競爭，**排序結果不由你控制** |
| **沒有單一答案** | 場景層的 §〇 有**唯一一份**（覆蓋寫）。語意層裡有**幾百條**語意相近的句子，全部都是「真的」——模型必須自己挑，挑錯了就動手做錯的事 |
| **無法 fail-closed** | 場景層可以機械擋（§〇 缺小節 ⇒ `check` 報錯 ⇒ 不許換會話）。語意層**沒有「缺了就不許開工」這種閘門** |
| **抽取失敗會留洞** | 實測失敗率約 **0.89 %**（見 §2.1），而且**成群發生**。那一天「下一步」沒抽進去 → 召回時那個位置是空的 → **模型不會知道自己不知道** |
| **錯誤會被當事實** | 抽錯了的「下一步」不是失敗，是**成功**。它會長期留在記憶裡，被召回、當成現行事實 |
| **人改不動** | 場景層是 Markdown，人五秒改完。語意層要寫 correction 文件去蓋 |

### 5.3 那怎麼辦

| 做法 | 對不對 |
|---|---|
| 把「進度／下一步／卡點」寫進 **§〇 第 4 小節**（≤ 4 KB 硬紅線，實測值） | ✅ |
| 同時把**結論與可複用的做法**沉到**專案記憶**（≤ 8 KB）與**語意層** | ✅ |
| 把「下一步」只寫在語意層，場景層不寫 | ❌ 召回排序不由你控制，而且沒有 fail-closed |
| 把「下一步」寫在共享層待辦板，**同時**在 §〇 第 4 小節寫「下一步：見待辦板第 N 行」 | ✅ 指針模式——避免同一件事有兩份定義 |

> **判據一句話**：
> **「這件事需要『唯一的、最新的一份』答案嗎？」**
> 需要 ⇒ 場景記憶。不需要（多個都對、能搜到就好）⇒ 語意記憶。

## 6. 兩層怎麼合（分工，不是二選一）

```
┌─ 場景記憶 ＝ 真源 ─────────────────────────────┐
│  交接、判據、落點、稽核 —— 全在檔案裡             │
│  誰能寫：只有本場景；改誰的記憶，只歸誰          │
└──────────────────────────────────────────────────┘
              ↕ 只往外送摘要，不回寫
┌─ 語意記憶 ＝ 召回層 ──────────────────────────┐
│  讓跨場景、跨 session 的東西「搜得到」            │
│  而不是「靠翻檔案」                              │
└──────────────────────────────────────────────────┘
```

| 規則 | 破了會怎樣 |
|---|---|
| **狀態分開、經驗共用並標源** | 共用一個庫時不標來源 ⇒ 跨場景串味 |
| **語意層只讀摘要，不回寫狀態** | 回寫狀態 ⇒ 狀態有兩個真源 ⇒ 分裂 |
| **抽取失敗要能看見** | 靜默失敗 ⇒ 錯誤長期留在記憶裡，日後被當成事實召回 |
| **語意層是索引，不是本體** | 只存在於語意層、沒落盤的內容 ⇒ 一律當作**未經證實的線索**；檔案與語意層衝突時**以檔案為準** |

> 最後一條在本機有實際對應：語意服務本機實測的 bank 資料**與場景檔案是兩份**，
> 而場景檔案才是真源。**索引可以錯，真源不能錯。**

| 層 | 已知問題 | 狀態 |
|---|---|---|

| 場景記憶 | 無原生派單／回執（靠留言＋人工確認） | 🟡 有修法未動工 |
| 語意記憶 | 抽取失敗**成群**發生（實測 0.89 %，集中在 5 天） | ⚠️ 設計上接受 |

## 8. 一句話記住

> **場景記憶是帳本，回答「現在」；語意記憶是 wiki，回答「以前」。**
> **要「唯一、精確、可稽核、人能接手」⇒ 帳本；要「找得到、會累積、跨 session」⇒ wiki。**
