# 一 · 與 A2A 協定的對照

> **一句話定位**：A2A 解決的是「**跨組織的 agent 怎麼互相找到、互相交辦**」；
> 場景記憶派單解決的是「**同一台機器上、同一套規矩的幾個 agent 怎麼不踩到彼此**」——
> 兩者處在不同的問題層次，不是同一個坑的兩種解法。

> 📌 **事實來源**
> A2A 側：來自 A2A 官方文件（`a2a-protocol.org`），擷取於 **2026-11-01**（規格 v1.0.x，Linux Foundation / Agentic AI Foundation）。
> 場景記憶側：來自本機 DSH 工作台實測，量測時間 **2026-10-31 / 2026-11-01**。

---

## 1. 兩者的核心命題（一句話講完）

| | 場景記憶派單 | A2A 協定 |
|---|---|---|
| **核心命題** | 狀態**在檔案裡**，路由**問檔案系統** | 能力**可發現**，任務**有生命週期** |
| **三個核心物件** | 檔案 · 目錄路由 · git 倉庫 | **Agent Card · Task · Message / Artifact** |
| **派單是什麼** | 在共享層留一條記錄 + 一份派單四件套（做什麼·判據·落盤位置·回執方式） | 對方 agent 建立一個 `Task`（唯一 id、`status`、`artifacts`、`history`） |
| **怎麼找到對方** | 目錄就是地址：`<工作台根>/場景/<場景名>/` | **Agent Card**：JSON 自描述（身分、端點 URL、技能、認證方式），掛在 `/.well-known/agent-card.json` |
| **誰是權威** | **檔案**是權威，agent 只是執行者 | **agent 端點**是權威，artifact 是產出物 |

> **差異的真正分歧點**：「狀態存在哪裡、由誰說了算」。
> 場景記憶派單把狀態放在**可被人直接打開、可 diff、可 blame 的檔案**裡；
> A2A 把狀態放在**服務端**（Task 物件由 agent 的 A2A Server 持有），
> 客戶端拿到的是一個 id、一個狀態碼、一個 artifact 連結。

---

## 2. 九維對照表（本篇主體）

| 維度 | 場景記憶派單 | A2A 協定 | 誰強 |
|---|---|---|---|
| **① 任務描述** | 一份**派單四件套**：`做什麼 · 判據 · 落盤位置 · 回執方式`。判據必須可驗證（「列出可釋放 ≥ 1 GB 的項目，每項標明路徑與大小」） | `Message`（`messageId` + `role` + `parts`）或直接 `Task`；內容型別自由（文字／檔案／結構化資料） | 各有所長。派單四件套**強在「完成定義」**，A2A `Message` 強在**型別自由、跨語言** |
| **② 狀態存放** | 檔案。`§〇` 交接段（≤ **4 096 位元組** 硬紅線，實測值）、專案記憶（≤ 8 KB）、共享層看板／待辦／索引 | **服務端**。`Task.status`（`submitted`→`working`→…→`completed`／`canceled`／`rejected`／`failed`）、`artifacts`、`history`、`metadata`；`contextId` 串起多個 Task | 檔案派強在**可稽核**；A2A 強在**生命週期語意齊備**（含 `input-required`／`auth-required` 這種中斷態） |
| **③ 喚醒機制** | 兩條通道併用：**通道 A 引擎 RPC**（`session/prompt` 排隊不干擾、`session/page` 抓回對方最近訊息核對、`session/cancel` 打斷）、**通道 B 檔案留言**（寫進共享層看板 + 收件方 §〇-通知） | **推播／輪詢／串流**三選一：Request/Response（polling）、SSE 串流（`TaskStatusUpdateEvent`／`TaskArtifactUpdateEvent`）、**Push Notification**（對方掛 webhook 回呼） | A2A 強在**跨機器的推播與長任務續傳**；檔案派強在**零網路、對方不醒也能收**（離線投遞） |
| **④ 回執** | **一次派單＝一條回執**；回執必帶**差異集合**（「與上輪的差異：/ +1G、free 4.0→2.5Gi、swap −0.1G」），≤ 10 行／≤ 2 KB；回執寫進檔案 ⇒ **可 diff、可 blame** | `Artifact`（有 `artifactId`、名稱、parts）＋ Task 狀態轉換；**版本變更是客戶端的事**——規格明言 agent 不追 artifact 變更 | 檔案派強在**回執本身就是可讀的差異**；A2A 強在**產出物有正式型別與取回路徑** |
| **⑤ 邊界強制** | **事實，不是承諾**。每場景＝獨立 git 倉庫；引擎從 cwd 往上找第一個含 `.git` 的目錄當專案根，**只**載入該樹的 `AGENTS.md` 與 `.dsh/skills/` ⇒ 別場景的憲法／技能／記憶**模型根本看不到** | **Opaque Execution**：對方 agent 的內部邏輯、記憶、專有工具不外露；靠 **HTTPS＋憑證＋授權**劃信任邊界（`securitySchemes`、OAuth2／Bearer） | 場景派強在**隔離是結構事實**（不是靠提示詞請求）；A2A 強在**跨組織的授權與隱私** |
| **⑥ 稽核** | `git log` 全在，每場景一個倉庫；另有交接前快照進歸檔（只進不改、可回滾）；寫入審計日誌 | **訊息 log 分散在兩邊**（client 與 server 各一份）；可追溯性靠 tracing／monitoring 這類企業功能另建 | 檔案派**強一個量級**。這是「能不能 blame 誰寫壞了」的差別 |
| **⑦ 跨組織** | ❌ **不擅長**。前提是：同機、同一套規矩、同一個人看得懂 | ✅ **就是為它而生**。跨廠商、跨框架、跨組織、跨語言；用 Curated Registry 做能力目錄 | A2A 完全勝出 |
| **⑧ 實作成本** | 低。**零網路請求、零伺服器、零註冊中心**；場景邊界＝`git init`；校驗工具可執行（`check`／`stamp`／`交接`），退出碼可被 CI 呼叫 | **要一整套伺服器與註冊中心**：每個 agent 一個 A2A Server（HTTP 端點）、一張 Agent Card、一套認證、必要時**部署並維護一個 Curated Registry 服務**（規格本身**未**規定 registry 的標準 API） | 檔案派勝出（同一台機器上） |
| **⑨ 何時該用哪個** | 小規模、同機、同一人（或同一小組）、同一套規矩；**狀態要精確、要稽核、要人能接手** | 真的需要**跨組織／跨廠商／跨語言**協作；有**第三方 agent** 要接進來；需要**非同步長任務**、推播、SLA（逾時／重試／補償） | 分工明確 |

## 3. A2A 的四個物件，逐個對到場景記憶的什麼東西

| A2A 物件 | 它是什麼 | 場景記憶裡**最接近**的東西 | 差距（誠實說） |
|---|---|---|---|
| **Agent Card** | JSON 自描述：身分、服務端點、技能（`id`／`name`／`inputModes`／`outputModes`）、認證方式；掛在 `/.well-known/agent-card.json` | `定位卡.md` ＋ `身份卡.md`（工具生成，⛔ 手改即校驗失敗） | 場景版**不描述端點與認證**，因為它們同機共用；也**不做能力目錄查詢** |
| **Task** | 有狀態的工作單：唯一 id、`contextId`、`status`、`artifacts[]`、`history[]`、`metadata` | §〇 第 2 小節「當前專案」表（專案／記憶檔／狀態／下一步） | 場景版**沒有正式的狀態機與生命週期語意**；靠「§〇 第 4 小節：下一步／卡點」＋看板 |
| **Message** | 一輪通訊：`messageId` + `role`(user/agent) + `parts[]` | 派單四件套（自由格式 markdown）＋ 共享層看板的一行 | 場景版**無結構化 schema**、無 `messageId`、無 `role` 欄位（這是[已知裂縫 #10](../02-落地實作/四-已知裂縫與待修.md)） |
| **Artifact** | 任務產出的具體成果：`artifactId` + 名稱 + `parts[]` | **落盤檔案本身**（`專案記憶/<專案id>.md` 等），回執裡標明路徑 | 場景版的產出物**沒有型別化 metadata**，靠人可讀的路徑；好處是**拿到手就是能用的檔案** |

> **可以抄的三件事**（觀念，不抄架構）：
> ① **派單帶編號**（對應 `taskId`）——現在只能靠時間戳對單，回執引派單編號會更準；
> ② **主動 ack ＋ 逾時升級**（對應 `pushNotifications` 與 Task 超時態）——
> 對應[已知裂縫 #2](../02-落地實作/四-已知裂縫與待修.md)「回執沒有逾時偵測」；
> ③ **狀態機的正式語意**——`submitted/working/input-required/completed/canceled/rejected/failed`
> 這組名字比「做完了／沒做完」更不容易吵架。

## 4. 場景記憶派單**不擅長**什麼（誠實清單）

這一節是本篇的重點。**方法論文件如果只寫自己好的那一面，就變成行銷。**

| # | 不擅長 | 為什麼（機制層面的原因） | 撞上時的徵兆 | 該怎麼辦 |
|---|---|---|---|---|
| **1** | **跨機器** | 整個派單鏈的基礎是「檔案系統就是路由表」：`.git` 劃界、共享層看板、檔案留言。檔案不在同一台機器就沒有「同一張桌子」 | 留言寫了但收件方永遠看不到；看板時間戳不動 | 派單通道改走 A2A / RPC，**但記憶層仍可留檔案**（記憶在磁碟，派單走網路） |
| **2** | **跨組織** | 場景邊界＝「同一套規矩」＝同一份 `AGENTS.md` 與同一個校驗工具。對方是別家公司、別套規矩時，「場景主權」「⛔ 只許請求不許改對方記憶」這套假設全部不成立 | 對方 agent 直接改你方記憶；或根本不理會你的四件套 | 上 A2A：靠 Agent Card 宣告能力、靠憑證劃信任邊界 |
| **3** | **非同步長任務** | 場景派沒有逾時偵測（[已知裂縫 #2](../02-落地實作/四-已知裂縫與待修.md)）、沒有重試、沒有續傳。任務跑三天，回執就真的「掉在桌子上了」 | 派出去就沒回音，人工回頭巡 | 要嘛上 A2A（Task 生命週期＋推播），要嘛先補逾時偵測 |
| **4** | **有第三方 agent 參與** | 第三方 agent 不會照你的檔案約定來，也不會跑你的 `check`。§〇 的五小節、「≤ 4 KB」紅線、sha256 指標——**全部無法對它強制** | 第三方 agent 寫出一份沒有 §〇 的記憶檔，你的校驗直接全紅 | 第三方 agent 走 A2A 當作**外部服務**；你的場景只跟它的 artifact 打交道 |
| **5** | **任務狀態機的正式語意** | 檔案派靠 markdown 段落承載狀態，機器解析要先寫工具（[已知裂縫 #10](../02-落地實作/四-已知裂縫與待修.md)） | 想要「所有進行中的任務清單」得自己寫解析器 | 用結構化前綴標記，但要**保持對人可讀**——記憶是給人看的 |

> ⚠️ **第 5 條的教訓比前四條更重要**：
> 場景記憶派**不是** A2A 的劣化版，它是**換了一個問題**。
> 前四條是「換了場景就不適用」；第 5 條是「同一場景內也想要更多」——
> 後者可以自己補（補工具），前者只能換協定。

## 5. 什麼時候該換成 A2A（切換訊號）

| 訊號 | 說明 | 嚴重度 |
|---|---|---|
| 場景要跨機器 | 共享檔案系統的前提沒了 | 🔴 必須換 |
| 有外部第三方 agent 要接進來 | 對方不會照你的檔案約定來，也不會跑你的校驗 | 🔴 必須換 |
| 需要非同步長任務（跨天／跨週） | 檔案留言撐不住；需要推播與續傳 | 🟠 該換 |
| 需要服務級 SLA（逾時、重試、補償、告警） | 目前的回執沒有逾時偵測 | 🟠 該換 |
| 需要跨組織的能力目錄 | 「誰能幹什麼」要能被查詢與授權 | 🟠 該換 |
| 需要正式的任務狀態機與並發追蹤 | 多個任務並行，要統一追蹤狀態 | 🟡 可以自己補 |

> **換的成本很高**：檔案派的所有場景記憶、稽核、人能接手的能力，
> 都建立在「**檔案是唯一介面**」這件事上。
> 換協定＝換掉整套記憶模型。**先想清楚再換。**

### 5.1 反過來：什麼時候**不該**上 A2A

| 訊號 | 判斷 |
|---|---|
| 幾個場景都在同一台機器上 | ❌ A2A 過重。邊界已經由檔案系統給了（`.git` 劃界），稽核已經由 git 給了，「找到對方」不需要 Agent Card——**目錄就是地址** |
| 只是想要「有回執、有逾時」 | ❌ 先補[已知裂縫 #2](../02-落地實作/四-已知裂縫與待修.md)。為了一張派單表架一整套伺服器＋註冊中心，比例失衡 |
| 團隊還在共用同一台機器 | ❌ 同上。先把場景邊界與校驗做對 |
| 想要「跨場景召回以前聊過的東西」 | ❌ 那不是 A2A 的問題，是**語意記憶**的問題 → 見[二-場景記憶與語意記憶](二-場景記憶與語意記憶.md) |

## 6. 兩者不是競爭關係（一張圖講完）

```
跨組織／跨廠商／跨語言／第三方 agent
        │
        ▼
┌───────────────────────────────┐
│  A2A：能力發現 + 任務生命週期  │  ← 解決「對方是誰、活跑到哪、有沒有回來」
│  Agent Card · Task · Artifact  │
└───────────────────────────────┘
        │  派單／回執走這裡
        ▼
┌───────────────────────────────┐
│  場景記憶：檔案 + 目錄路由 + git │  ← 解決「誰歸誰管、狀態落在哪、能不能查帳」
│  §〇 · 定位卡 · 專案記憶 · 看板   │
└───────────────────────────────┘
```

> **兩者可以疊著用**：跨組織那一層用 A2A；
> 跨組織**之內**每個 agent 自己的狀態，仍然用檔案管。
> **不要為了做 A2A 而放棄檔案層**——那會同時失去稽核與「人能接手」。

---

## 7. 兩句話結論

> **一、小規模同機工作台：場景記憶派單就夠了。** A2A 的伺服器與註冊中心是為了
> 「跨邊界」而存在的；沒有跨邊界需求時，那是純成本。
>
> **二、真的要做跨組織協作：才需要 A2A。** 但那時也別把檔案層丟掉——
> A2A 管「活怎麼交辦」，場景記憶管「我的狀態落在哪、這筆帳誰寫的」。
