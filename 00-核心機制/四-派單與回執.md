# 四 · 派單與回執 —— 活怎麼派出去，怎麼帶著累積物回來

> 「派單」聽起來很簡單：把一句話丟給某個 agent。
> 真正難的是**回來**——**怎麼知道對方真的做了，而不是說它做了。**
>
> 還有一件更難的：**怎麼讓這次做完的活，變成下次的起點。**

---

## 1. 先講清楚：派單不是公告

| | 公告 | 派單 |
|---|---|---|
| 期望 | 「大家看一下」 | 「你做這件事，做完給我回執」 |
| 結束條件 | 沒有 | **一條回執** |
| 誰負責跟 | 沒人 | 派單的人 |

> **一次派單 ＝ 一條回執。** 沒有回執的派單，等於沒派。
> 「活幹完了但對方還不知道」＝**沒幹完**。

---

## 2. 派單四件套

任何一張派單，必須寫清四件事。缺一件就會變成「做完了但沒人知道」：

```
做什麼 · 判據 · 落盤位置 · 回執方式
```

| 件 | 寫什麼 | 寫不好的樣子 | 好的樣子 |
|---|---|---|---|
| **做什麼** | 一句話的動作 | 「處理一下磁碟」 | 「找出 /mnt 下可清理的項目清單」 |
| **判據** | 什麼算完成（可驗證） | 「清理乾淨」 | 「列出可釋放 ≥ 1 GB 的項目，每項標明路徑與大小」 |
| **落盤位置** | 檔案寫到哪 | 「記錄一下」 | 「寫進 `場景/場景丙/專案記憶/磁碟體檢-2026-10-31.md`」 |
| **回執方式** | 怎麼回、回什麼 | 「做完跟我說一聲」 | 「在 §〇 第 4 節寫明已回執，並把結論首行追加到共享看板」 |

> **判據這一欄最常被略過，也最致命。** 沒有判據，回執就無從判定真假。

---

## 3. 回執三件套

這是整套機制裡最重要的一條規矩。**回執不是回報，是交付。**

```
回執 ＝ 差異集合 ＋ 可累積物 ＋ 下一棒
```

| 件 | 記什麼 | 為什麼不能少 |
|---|---|---|
| **差異集合** | 這次狀態變了什麼 | 「一切正常」無法驗證——它可能是編的 |
| **可累積物** ★ | 下次能用的：做法、坑、判準、更好的一次做法 | **少了它，這次活就白做了** |
| **下一棒** | 這件事接著交給誰 | 沒有下一棒，鏈就斷在這裡 |

### 3.1 差異集合：不是「一切正常」，是「與上輪的差異」

```
❌ 磁碟已清理，一切正常。

✅ 磁碟體檢完成，與上輪差異：
   /mnt/minecraft   56% → 41%（-8.2G）
   swap 使用       67% → 22%（-3.1G）
   free            4.0Gi → 2.5Gi
   已刪：舊地圖備份 3 個（-1.4G）
   落盤：場景/場景丙/專案記憶/磁碟體檢-2026-10-31.md
```

**為什麼**：
- 「一切正常」無法驗證——它可能是編的
- 差異集合**可對照**：拿上輪的數字比對就知道有沒有動
- 差異集合**省字數**：不重複的背景資訊

**寫回上限**：≤ 10 行 / ≤ 2 KB。超了就是在抄過程，不是回執。

### 3.2 可累積物：這次活留給下次用的東西

差異集合回答「**狀態**變了什麼」，可累積物回答「**認識**變了什麼」。

| | 差異集合 | 可累積物 |
|---|---|---|
| 內容 | 數字、檔案、刪了什麼 | 做法、坑、判準、「下次這樣做比較好」 |
| 落點 | 專案記憶（該專案的現況） | **`§五 決策與坑`**（只追加）＋ 場景專屬技能 |
| 誰讀 | 這個專案的下一步 | **所有未來的這件事** |

```
✅ 磁碟體檢完成，與上輪差異：…
   可累積物：
     · /mnt 下的舊地圖備份可安全刪，但要先確認沒人在跑那個世界
     · 判準：刪前用 lsof 檢查，>1GB 的才動
     · 坑：swap 佔 67% 是 Minecraft 撐的，不是真記憶體不足
   下一棒：清理（場景丙）
```

> **沒有可累積物的回執 ＝ 這次活白做。**
>
> 這條紅線跟既有的「活幹完了但對方還不知道 ＝ 沒幹完」是同一族病：
> **做了，但沒留下。**
>
> 前者留下的是「對方知道」，後者留下的是「下次知道」。

**兩種落點的差別**：

| 落點 | 什麼時候寫 | 例子 |
|---|---|---|
| `§五 決策與坑`（只追加） | 一次性的坑、判準 | 「lsof 檢查過才能刪」 |
| **場景專屬技能** | 這套做法會**反覆用到** | 「磁碟體檢流程」變成一支專屬技能 |

> **判準：會再用一次以上的，寫成專屬技能；只這一次的，寫進 `§五`。**
> 這是「累積」的兩級——`§五` 是堆積，專屬技能是提煉。
>
> ★ **這是分流，不是雙寫：同一條可累積物只去其中一個地方，不要兩邊各抄一份。**
> 兩邊都抄 ⇒ 改一邊另一邊就過期，而「兩份數字打架」正是本架構最貴的失效模式。
> 另一個場景的累積物要看 ⇒ **寫指標**（「見 X 場景 §五 2026-11-05」），不要把對方的內文複製過來。
>
> ★ 落地檢查比的是「**最長公共子字串 ≥ 8 字**」，**不是逐字相同** ——
> 落地檢查要證明「它真的在那裡」，不是「它一字不差地在那裡」。
> 逐字比對會把「明明寫進去了」判成沒落地（場景落地時常改寫措辭或用簡體）。

### 3.3 下一棒：鏈要接在哪裡

| 情況 | 下一棒怎麼定 |
|---|---|
| 單點派單 | 人指定的下一個場景 |
| 工作流執行 | **由工作流定義決定**（見[五-工作流](五-工作流.md)） |

可累積物不只留在原地——**它要被下一棒讀到**。
這就是工作流和「排三個場景」的差別：資訊在跳之間流動，而流動的載體是累積物。

## 4. 兩條通道：怎麼把單子送達

同一件事有兩種送法，**併用**。

### 通道 A｜引擎 RPC（真呼叫，把對方叫醒）

直接對目標會話發提示詞，把對方叫醒；再用 `session/page` 把它的回答抓回來核對——**不靠信任，靠讀證據**。

```js
// 建會話.mjs:92
async function rpc (method, args) {
  await auth()
  const r = await fetch(BASE + '/api/' + method, {   // BASE = http://127.0.0.1:3080
    method: 'POST',
    headers: { 'content-type': 'application/json; charset=utf-8', cookie },
    body: JSON.stringify({ type: 'client-request', rpcId: 'r1', method, payload: { args } }),
  })
  ...
}
```

**叫醒對方**：

```js
// 建會話.mjs:217
await rpc('session/prompt', {
  request: {
    requestId: crypto.randomUUID(),
    sessionId: targetSessionId,
    mode: 'queue',                                    // 排隊，不打斷當前那一輪
    content: [{ type: 'text', text: '……派單正文……' }],
  },
})
```

`session/prompt` 一發，目標會話立刻收到訊息、agent 開始跑。配套還有 `session/page`（抓回對方最近 200 條訊息**核對結果**）、`session/cancel`（打斷）、`workspace/pinSession`（釘側邊欄）。

> **認證的一個坑**：token 不在設定檔裡，要從 systemd 日誌撈；
> 換 cookie 時必須 `redirect: 'manual'`——跟隨重定向反而 401。

### 通道 B｜檔案留言（對方不醒著也能收）

```js
// 發消息.mjs
const line = '- [' + ts + '] → ' + to + '：' + text
fs.appendFileSync(BOARD, line + '\n')                 // 共享層看板
// 同一行再追加進收件方的「## 〇-通知」
```

### 兩條通道的分工

| | 引擎 RPC | 檔案留言 |
|---|---|---|
| 對方是否立刻醒 | ✅ | ❌ |
| 能確認結果 | ✅ `session/page` | ❌ 只能等回執 |
| 依賴 | 引擎在跑＋token 有效 | 檔案可寫即可 |
| 用途 | 派單、報到、抓證據 | 留言、留痕、離線投遞 |

> **檔案留言像桌上傳紙條**：同一張桌子，誰看見那張紙誰負責，誰沒回自己去看桌子。
> RPC 像打電話開會：有接通狀態、有「我還在查、等下回你」。
> 兩者併用：**RPC 送急件，檔案留底**。

## 5. 派單鏈：從機主一句話到回執

```
機主一句話
   ↓
主控端（只讀 + 路由，不動手）
   ↓  依「項目 → owner」匹配
派單（四件套）──── 通道 A：RPC 叫醒
   ↓                通道 B：檔案留言（同時留痕）
owner 自己動手
   ↓
回執三件套（差異集合 + 可累積物 + 下一棒）
   ↓
主控端讀回執 → 驗收（★ 讀場景記憶，確認可累積物真的落地）
   ↓
組回覆給機主
```

**主控端只做路由，不動手**——這是它的職責邊界。
它一旦開始自己幹活，場景之間的邊界就糊了，稽核也沒了。

## 6. 跨場景協作的三條規矩

| 規矩 | 內容 |
|---|---|
| **⛔ 只許請求，不許改對方記憶** | 改誰的記憶，只歸誰。要改就派單。 |
| **一次派單 = 一條回執 = 結束** | 不來回客套，不追問「你收到了嗎」。 |
| **有可觀察落點才算做完** | 寫了，但寫到了沒人看的地方 ＝ 沒做 |

> 第三條是從真實事故來的：**看板分裂過**——訊息被寫進舊看板，
> 收件方的記憶檔裡根本收不到。**寫了 ≠ 生效**，生效要有可觀察的落點。

---

## 7. 回執回收：目前最大的缺口

**主控端只送到 prompt，沒有讀回來的程式。** 這是整套機制目前最實在的一個洞。

技術上的難點：`session/prompt` 是非同步的，**訊息何時算完成**？

| 做法 | 說明 | 評價 |
|---|---|---|
| **A. 輪詢** | `session/list` 看 `running` 旗標 + 讀訊息內容 | ✅ 推薦——現有工具已經在用 `session/list` 拿 `running` 旗標了 |
| B. 事件流 | `dsh-api-gateway` 的 WebSocket 端點 | ⚠ 比較重，暫不必要 |

> 補上回收腿之後，這條鏈路才閉環：**派得出去 → 收得回來 → 核對得了**。

---

## 8. 失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 「活幹完了但對方還不知道」 | 沒有回執機制 | 一次派單＝一條回執；主控端需有回收腿 |
| 回執是「一切正常」 | 沒要求差異集合 | 派單四件套裡明訂判據 |
| **活做完了，認識沒累積** | 回執沒帶可累積物 | 回執三件套；**沒有可累積物＝白做** |
| **可累積物只在回執裡，沒落地** | 沒驗收 | 主控端讀場景記憶確認落地 |
| 留言寫了但對方收不到 | 記憶根路徑分裂，寫進了舊看板 | 統一路徑解析；**且要有可觀察落點** |
| 主控端自己動手了 | 職責邊界糊掉 | 主控端只做路由 |
| 派錯場景 | 沒有路由表，靠臨場判斷 | 路由表放共享層，命中不了才交給模型判 |
