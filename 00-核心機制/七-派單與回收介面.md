# 派單與回收介面規格

> **這是 repo 與引擎之間的契約。**
> repo 定義「派單長什麼樣、回執長什麼樣、怎麼驗收」；
> 引擎那端（某引擎／另一引擎／任何）只管**把這兩份東西送到、收回來**。
>
> **引擎不需要理解這套方法論。** 它只需要做三件事：
> 送出一份派單、收回一份回執、把回執交給驗收工具。
>
> ---
>
> **為什麼要有這份文件**：方法論倉庫（repo）與實際工作台（引擎端）
> 會各自演化。沒有共同契約，兩邊就會各做一套、然後說「我這邊有做」。
> 這份文件是**兩邊唯一的真相來源**：介面在這裡定，兩邊各自實作。

---

## 零、介面全貌

```
  ┌──────────────────────┐                        ┌──────────────────────┐
  │  引擎端（某引擎／另一引擎）│                        │  方法論倉庫（repo）    │
  │                      │                        │                      │
  │  ① 讀派單檔          │                        │  ④ 產生派單檔         │
  │     ↓                │                        │     （工作流定義+狀態）│
  │  ② 送進目標場景會話   │──── 派單（純文字）────▶│                      │
  │     ↓                │                        │                      │
  │  ③ 收回場景的回覆     │◀─── 回執（純文字）─────│  ⑤ 驗收回執           │
  │     ↓                │                        │     （三件套+落地）    │
  │  存成回執檔          │                        │                      │
  └──────────────────────┘                        └──────────────────────┘
```

**邊界在哪**：① 與 ③ 是引擎的活（它才知道怎麼叫醒一條會話、怎麼讀回來）；
② 與 ⑤ 是格式與規則（本文檔定義，工具執行）。

---

## 一、派單格式（repo → 引擎 → 場景）

### 1.1 派單是一份檔案

派單不進對話框，**先落成檔案**——因為派單必須可稽核、可重跑、可被工具讀。

檔名：`<工作台根>/執行/<run-id>/回執/派單-<步驟序號>.md`

### 1.2 派單的結構

```markdown
# 派單 · <工作流名稱> · 步驟<N>/<總數>

【<目標場景名> · 派單 · 請回執】

做什麼：
  <一句話的動作>

判據：
  <什麼算完成，可驗證>

落盤位置：
  <完整檔案路徑>

需要（上一跳的可累積物）：     ← 可選，沒有就整段省略
  <從交接串帶進來的內容>

回執方式：
  ① 結論 + 證據 + 路徑
  ② 必須帶「差異集合」
  ③ 必須帶「可累積物」★ 少了這條＝這次活白做
  ④ 必須寫明「下一棒」
```

### 1.3 引擎要做什麼（就這一件）

**把派單檔的正文送進目標場景的會話。**

| 引擎 | 怎麼送 |
|---|---|
| DSH | `session/prompt`（RPC 到常駐會話），`mode: 'queue'` 不打斷當前那一輪 |
| 檔案通道 | 追加到目標場景的「〇-通知」段落 + 共享層看板（留痕，對方不醒也能收） |

**引擎不解析派單、不改寫派單、不裁切派單。** 原文送達。

> **為什麼要求「原文送達」**：派單是受檢的對象。引擎動過它，
> 工具就沒辦法驗收「送出來的東西有沒有帶判據」。

### 1.4 引擎送完要做什麼

**把「我送了什麼」記錄下來**（時間戳、session id、送達結果）。
這是稽核用的——repo 的 `執行狀態.md` 會引用它。

## 二、回執格式（場景 → 引擎 → repo）

### 2.1 回執是一份檔案

引擎收到場景的回覆後，**存成檔案**。回執不靠對話框裡的文字——對話會被下一次擠掉。

檔名：`<工作台根>/執行/<run-id>/回執/回執-<步驟序號>.md`

### 2.2 回執的結構

```markdown
【<場景名> · 回执】

结论：<一句话>
证据：<可打开的路径 / commit / 数字>
路径：<写到哪了>

### 差异集合
- <项目A>：<旧值> → <新值>
- <项目B>：<旧值> → <新值>
- <删了什么 / 加了什么>

### 可累积物
- <做法 / 判准：下次该怎么做>
- <坑：下次会踩什么>
- <更好的那次做法：这次改进了什么>

### 下一棒
- <哪个场景接手 / 没有了>

卡点：<无 / 等谁、等什么>
```

### 2.3 三個小節標題是介面的一部分

| 小節 | 必填 | 驗收會檢 |
|---|---|---|
| `### 差异集合` | ✅ | 非空 |
| `### 可累积物` | ✅ | **非空，且必須落地**（見 §四） |
| `### 下一棒` | ✅ | 非空 |

> **標題文字本身是介面契約。** 引擎不改、工具不改、場景不���。
> 如果實作端用別的字（繁體／簡體），**由引擎端在落地時轉換**，不要兩邊都猜。

### 2.4 引擎要做什麼（就這一件）

**把場景的回覆存成一份回執檔，然後交給驗收工具。**

```bash
# 引擎端收到回覆後
node <repo>/03-可执行工具/回执校验.mjs \
  --root <工作台根> --場景 <場景名> --回執 <回執檔>
# exit 0 ⇒ 合格；exit 1 ⇒ 不合格（缺可累積物 / 沒落地）
```

## 三、可累積物的落地規則（介面裡最重要的一條）

### 3.1 規則

> **回執裡的每一條可累積物，都必須能在場景自己的記憶裡找到。**

「場景自己的記憶」指：
- 場景私有記憶檔的 **`§五 決策與坑`** 段落（累積的落點）
- 或場景的**專屬技能**（提煉後的做法）

### 3.2 為什麼這麼嚴

| 只寫在回執裡 | 也寫進場景記憶 |
|---|---|
| 回執是一次性的，看完就沉 | 記憶是長期的，下次會被讀到 |
| 下次做同類活，讀不到 | 下次開場就讀得到 |
| **等於沒累積** | 真的累積了 |

> **這是「累積」的機械證據。** 沒有落地，工具擋下。

### 3.3 落地比對怎麼做

工具做的事（不靠語意比對，靠**正規化後的包含關係**）：

```
把「可累積物」的每一行去掉清單符號與空白，
檢查它是不是出現在「場景記憶的 §五（或專屬技能）」的正規化文字裡。
```

**為什麼不用語意比對**：那會有 false negative（寫法不同但意思一樣 → 誤擋）。
正規化包含關係夠嚴謹又不會誤擋——**寫法不同的後果是漏檢，不是誤擋**。

## 四、驗收規則（repo 的工具執行）

### 4.1 回執驗收

```bash
node 03-可执行工具/回执校验.mjs --root <工作台根> --場景 <場景名> --回執 <回執檔>
```

| 檢查 | 不合格時 |
|---|---|
| 三個小節都在 | exit 1 |
| 三個小節都非空 | exit 1 |
| 可累積物每條都落地 | exit 1 |

### 4.2 派單驗收（引擎送之前）

派單檔必須包含：做什麼／判據／落盤位置／回執方式。
少了**判據** ⇒ 這張單不能送（回執會無從判定真假）。

### 4.3 工作流定義驗收

```bash
node 03-可执行工具/工作流校验.mjs --root <工作台根>
```

## 五、字體與用語的相容（實作端必讀）

repo 的文件與工具是**繁體中文**；有些引擎端（DSH）的工作台是**簡體中文**。
這是**兩套獨立的命名**，不是同一套東西的兩種寫法。

### 5.1 規則

| | repo（方法論倉庫） | 引擎端（你的工作台） |
|---|---|---|
| 場景目錄 | `場景/` | `场景/`（DSH） |
| 場景記憶檔 | `場景私有記憶.md` | `场景私有记忆.md`（DSH） |
| 身份索引 | `_場景身份索引.md` | `_场景身份索引.md`（DSH） |
| 專案記憶 | `專案記憶/` | `项目记忆/`（DSH） |

### 5.2 怎麼共存

**不要把 repo 的工具硬指向引擎端的名字。** 做法是：

1. **檔名對應表放進引擎端**（不是 repo）
2. repo 的工具**接受覆寫**——用 `--記憶檔` 之類的參數，或讀引擎端自備的設定檔
3. repo 的規則檔（`交接規則.json`）是**預設值**，引擎端可以帶自己的版本

> **為什麼不把 工作台的簡體名寫進 repo**：repo 是公開的、引擎中立的方法論倉庫。
> 把某一個引擎的目錄名寫進規則檔，等於宣告「這套方法就是給 DSH 用的」——
> 那就毀了引擎中立這件事。
>
> **正解**：repo 定**介面**（派單格式、回執格式、驗收規則），
> 引擎端定**命名**（自己的檔名、自己的路徑），兩者用設定檔橋接。

## 五又二分之一、引擎狀態檔（校驗工具唯一的引擎依賴）

> **校驗工具是引擎中立的** —— 它不知道任何引擎的私有格式。
> 但它必須能回答一個問題：**面板綁定的那條會話，還活著嗎？**
>
> 面板指向一條**已歸檔**的會話 ⇒ 症狀是「切場景像換了個人」，
> 跟「三處少同步一處」**一模一樣**，但根因完全不同 ⇒ 必須能分開查。

### 契約

引擎端在工作台根寫一份 JSON：

```json
{
  "已歸檔會話": ["session-xxxx", "session-yyyy"],
  "釘住會話":   ["session-zzzz"]
}
```

檔名由規則檔的 `引擎狀態檔名` 決定（預設 `引擎狀態.json`）。

### 校驗工具拿它做什麼

| 情況 | 處置 |
|---|---|
| 面板綁定的會話 **在已歸檔清單裡** | **擋**（exit 1）——面板指向死會話 |
| 面板綁定的會話不在清單裡 | 通過（12 項 + 1） |
| 狀態檔不存在 | **略過這項檢查**（引擎中立：沒有引擎就沒有引擎狀態） |

> **為什麼狀態檔不是「引擎私有格式」**：
> 私有格式會讓 repo 綁死某個引擎。這份檔的形狀由 **repo 定義**，
> 引擎端只負責**填內容**——跟派單／回執是同一種關係（repo 定介面，引擎填資料）。

## 六、引擎端的實作清單（照著做就對了）

- [ ] 能把一份派單檔的正文送進目標場景的會話
- [ ] 送達後把「送了什麼、送到哪、什麼時候」記錄下來
- [ ] 能讀回場景的回覆並存成回執檔
- [ ] 收完回執**立刻**呼叫驗收工具，不合格就停下（fail-closed）
- [ ] 回執的三個小節標題**原文保留**（轉換字體可以，改標題不行）
- [ ] 可累積物落地到場景記憶的 §五（由場景自己寫，主控端不代改）
- [ ] 提供一份**自己的**規則檔，把檔名對應到你的工作台
- [ ] 產生**引擎狀態檔**（`已歸檔會話` ＋ `釘住會話`），放在工作台根
- [ ] 換會話／歸檔之後**刷新**引擎狀態檔（否則校驗工具會以為舊會話還活著）
