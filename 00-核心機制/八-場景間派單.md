# 八 · 場景間派單（信箱與路由）

> **這篇補《四-派單與回執》與《七-派單與回收介面》沒寫到的那一段：**
> 工作流驅動的派單已經有契約（派單是檔案、引擎當信差），
> 但**場景自己想起要別人幫忙**時，要往哪裡寫、寫完誰來送——
> 那條路徑原本沒有契約。

---

## 零、為什麼要有這一篇

實測（2026-11-03，DSH 工作台，10 個場景）：

| 量測 | 數字 |
|---|---|
| 跨場景通知總數 | 71 條 |
| **有明確發起方**的 | **29 條** |
| 沒有發起方（只知��派給誰） | **42 條** |
| 有發起方的 29 條裡，發起方是**同一個**場景的 | **19 條（命令場景）** |
| 命令場景退役之後，有明確發起方的傳遞 | **0 條** |

**結論**：命令場景不只是路由器，它還是**唯一的自發傳遞者**。
它退役後，場景間的傳遞從「場景之間」退化成「人（Hermes）與場景之間」——
每一條留言都要有人去敲門才會被處理。

而留言本身也沒有發起方：`發消息.mjs` 連 `--from` 參數都沒有，
所以 42 條記錄裡根本看不出是誰說的。

## 一、鏈條的五個環節

```
  場景 A ─①產生派單→ 路由表 ─②落盤+雙寫→ 信箱 ─③叫醒→ 場景 B 的常駐會話
                                                      │
        ⑤落地驗收 ← ④收回執+正規化 ←──────────────┘
```

| # | 環節 | 規格 | 狀態（2026-11-03） |
|---|---|---|---|
| ① | 產生派單（四件套） | 《七》§1.2 | ✅ |
| ② | 路由（該派給誰） | **本篇 §二** | ✅（新增） |
| ③ | 落盤＋雙寫＋叫醒 | 《四》§4 | ✅ |
| ④ | 收回執＋落地驗收 | 《七》§2、《四》§7 | ✅（本篇補「自發」那一腿） |
| ⑤ | 不合格要能退回 | **本篇 §四** | ✅（新增） |

**★ 缺任何一環，整條鏈就是「場景寫給牆上的留言」。**

## 二、路由：機械優先，語意後援

### 2.1 路由表放共享層

`場景/_共享記憶/路由表.json`：

```json
{
  "版本": 1,
  "路由": [
    { "項目": ["簡報", "報告頁", "deck"], "owner": "簡報設計" },
    { "項目": ["影片", "剪輯", "mp4", "旁白"], "owner": "影片剪輯" }
  ]
}
```

### 2.2 比對規則

1. **機械優先**：用派單的「做什麼＋判據」比對關鍵字，**長關鍵字優先**（避免「剪輯」蓋掉「影片剪輯」）。
2. **命中不了就交給模型判**——引擎端以**退出碼 3** 表示「機械命中不了」，
   **不要自己猜一個 owner**。這是《四》§8 明列的失效模式（「派錯場景｜沒有路由表，靠臨場判斷」）的修法。

> ★ 路由表**不新增場景時必須同步**——路由表少一條，那類活就會被判成「交給模型判」。

### 2.3 路由表不是路由器

**路由表只回答「這活該給誰」，不回答「這活怎麼做」。**
後者是 owner 場景的職責。路由層一旦開始動手，邊界就糊了（見《四》§6）。

## 三、自發派單：信箱

### 3.1 為什麼要有信箱

工作流驅動的派單有落點（`執行/<run-id>/回執/派單-<n>.md`），
但**場景自發的派單沒有 run**——它不是任何工作流的一步。

⇒ 自發派單落在**共享層的信箱**：`場景/_共享記憶/派單/<收件場景>/<派單id>.md`。

### 3.2 雙寫（通道 B）

派單產生時**同時**寫兩個地方：

| 寫哪 | 為什麼 |
|---|---|
| 共享層 `_跨場景通知.md` | 留痕。所有人看得到。 |
| 收件場景的 `## 〇-通知` | **收件方自己看得到**。 |

> ★ 《四》§6 第三條：「**寫了 ≠ 生效**，生效要有可觀察落點。」
> 只寫看板、不寫進對方的記憶檔，就是「訊息被寫進舊看板，收件方的記憶檔裡根本收不到」——
> 那個真事故正是這樣發生的。**雙寫不是冗餘，是生效條件。**

### 3.3 派單要帶發起方

派單檔與看板行**都必須記發起方**。沒有發起方的傳遞記錄是廢的：
事後無法稽核、無法追責、也畫不出傳遞圖（3D 總覽裡 42 條無主線就是這樣來的）。

## 四、回執回收與退回

### 4.1 回收腿（《四》§7 的洞）

`session/prompt` 是非同步的，**訊息何時算完成**？

| 做法 | 說明 |
|---|---|
| **A. 輪詢**（採用） | `session/list` 的 `running` 旗標 ＋ `session/page` 讀內容；看到 `turn/end` 或 `running=false` 就收 |
| B. 事件流 | WebSocket 端點，較重 |

**逾時了不能就丟掉**——回執可能晚到。⇒ 派送時記下「送出前 seq」，
之後可單獨跑「收回」把那條回執撈回來。

### 4.2 引擎端在落地時轉換格式（《七》§2.3）

場景寫回來的回執格式不一定合規（可能用粗體、可能用簡體、可能編號在前）。
**由引擎端在落地時統一**，不要兩邊都猜：

```
**④ 差异集合（本次新增）**   →   ### 差異集合
**⑤ 可累積物 ★**             →   ### 可累積物
```

### 4.3 不合格要能退回

回執被校驗擋下時（「可累積物沒落地」），要有一份**有判據的新派單**把它送回去，
而不是在對話裡追問。

**退回 ≠ 追問。** 退回是：把「缺哪幾條、寫到哪、怎麼算落地」列清楚的一張派單。

## 五、可累積物怎麼算「落地」（校驗器的兩個坑）

`回執校驗.mjs` 的落地檢查踩過兩個坑，都在 2026-11-03 修掉：

| 坑 | 症狀 | 修法 |
|---|---|---|
| **落點文字用扁平的 `parseSections` 取** | §五 底下的 `###` 子節把內容「挖走」⇒ 明明寫進去了卻判沒落地 | 落點文字抓「§五 的整段原文（含 `###` 子節）」 |
| **逐字比對** | 回執用簡體、記憶用繁體（或場景改寫措辭）⇒ 必然判沒落地 | 改成「**最長公共子字串 ≥ 8 字**」——檔案路徑、指令、識別碼一定會重現 |

> ★ 退一步想：**落地檢查要證明「它真的在那裡」，不是「它一字不差地在那裡」。**
> 逐字比對把紅線從「有沒有落地」偷換成「有沒有照抄」，那不是這條紅線的意思。

★ **第三個坑（2026-11-09 才發現）：派單那一份沒跟上。**
> 校驗器改了，**`派單.mjs 退回` 卻還寫著「（逐字比對）」** ——
> 而派單是**場景真正會讀到的那一份**（被派出去的派單正文），校驗器只是驗收用的。
> 場景照派單做「逐字」⇒ 被逼把同一段內容抄成兩份（§五 一份、SKILL.md 一份）⇒ 雙寫點長出來。
> 實測：郵件處理場景有 4 組段落兩邊逐字完全相同，標題早寫了指標但內文整份複製。
>
> ⇒ **改校驗器時，記得一起改派單那一份** —— 場景照的是派單，不是校驗器。

## 六、失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 場景之間沒在溝通 | 只有留言，沒有人叫醒收件方 | 補派送腿（叫醒）＋回收腿 |
| 通知記錄看不出誰說的 | 留言沒有發起方欄位 | 派單與看板行都記發起方 |
| 留言寫了但收件方不知道 | 只寫看板沒雙寫進記憶檔 | 雙寫是生效條件，不是冗餘 |
| 派錯場景 | 沒有路由表 | 路由表放共享層，命中不了才交給模型判（退出碼 3） |
| 回執晚到就當成沒有 | 等不到就丟 | 記「送出前 seq」，之後可補收 |
| 可累積物貼在回執裡就算數 | 沒落地檢查 | 回執校驗讀場景記憶確認落地 |
| 落地了卻被判沒落地 | 校驗器逐字比對 ＋ 取不到子節 | 本篇 §五 |
