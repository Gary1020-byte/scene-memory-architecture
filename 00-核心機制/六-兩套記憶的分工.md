# 四 · 兩套記憶的分工 —— 帳本與 wiki 的差別

> 同一台機器上，同一個問題有兩種解法：
> 一套是「**檔案派**」，狀態由人寫、工具校驗；一套是「**語意派**」，記憶由機器自己抽。
>
> 兩套都對，而且它們**回答的根本不是同一個問題**。

---

## 1. 兩種流派

| | 場景記憶（檔案派） | 語意記憶（語意派） |
|---|---|---|
| 核心命題 | 記憶**在檔案裡**，不在會話裡 | 記憶由機器從對話裡**自動抽取** |
| 誰寫 | 人 + 工具主動寫 | 機器每 N 輪自動抽 |
| 記憶單位 | 一份 4 KB 的交接檔 | 數萬條事實節點 |
| 回答的問題 | **現在做到哪、欠誰的活** | **以前學到什麼、上次怎麼解** |
| 召回時機 | 開會先讀 §〇，精準且免費 | 每輪 prefetch，上限 2048 token |
| 隔離 | 強：每場景獨立 git 倉 | 弱：多個 profile 共用同一個庫 |
| 可稽核 | `git log` 全在 | 服務端 log，抽取結果本身**不可 diff** |
| 失敗模式 | 交接沒寫 → 下一任接手時缺一步 | 抽取錯誤 → 錯誤長期留在記憶裡 |
| 成本 | 零網路請求 | 每次抽取都燒 token |
| 人能救場嗎 | 能：Markdown，人可讀可改 | 較難：要寫 correction 文件去蓋 |

---

## 2. 各自解決的問題

### 檔案派解決的三件事

**第一件：換個視窗就失憶。**
同一個場景、同一件事，開新會話重問一次，它從頭開始。
記憶如果長在上下文裡，那它其實是「對話尾巴」——尾巴一剪，狀態就沒了。

**第二件：記憶會被搶。**
兩個 agent 同時處理同一個專案，各自往同一份記憶寫。誰覆蓋了誰？不知道。事後根本查不出來。

**第三件：不知道有沒有做完。**
「我覺得做完了」不算證據。要能驗。

> 這三件事的共同點：**它們都不是模型能力的問題，是記憶的存放位置與邊界的問題。**

### 語意派解決的三件事

**第一件：覆蓋廣。** 所有聊過的東西自動進記憶，不靠自覺。
**第二件：零維護成本。** 不用寫交接檔、不用跑 check。
**第三件：會越用越懂。** 第一次遇到的問題，半年後再問，它可能直接答出上次的做法。

### 語意派的代價

- **記憶裡有噪聲**：抽出來的事實不一定準。
- **失敗會長期污染**：抽取壞掉時，錯誤會安靜地留在記憶裡，之後還會被召回、當成事實。
- **要能手動蓋掉**：發現記憶說錯了，得另外寫一份 correction 文件去蓋，比改一個檔案麻煩。

---

## 3. 洞見：這是帳本與 wiki 的差別

對照完會發現，它們**不是同一個東西的兩種做法，而是兩個層次**：

| | 角色 | 比喻 |
|---|---|---|
| **場景記憶** | 回答「**現在**」 | **帳本**（ledger）——你換了模型、換了會話、agent 掛了都還在 |
| **語意記憶** | 回答「**以前**」 | **wiki**——這個 agent 越用越懂的東西 |

很多人糾結「到底要檔案還是要向量庫」，其實是因為把「記憶」當成一件事。
真實工作流裡：

> **只留帳本，agent 不會變聰明；只留 wiki，你會忘記昨天那個活兒到底誰做了一半。**

**取捨原則，簡單到可以直接抄：**

> **要「狀態精確、可稽核、人能接手」→ 檔案。**
> **要「覆蓋廣、不用自覺、會累積經驗」→ 語意。**

---

## 4. 怎麼合起來用（分工，不是二選一）

```
┌─ 場景記憶 ＝ 真源 ─────────────────────────────┐
│  交接、判據、落點、稽核 —— 全在檔案裡             │
│  誰能寫：只有本場景；改誰的記憶，只歸誰          │
└────────────────────────────────────────────────┘
              ↕ 只往外送摘要，不回寫
┌─ 語意記憶 ＝ 召回層 ──────────────────────────┐
│  讓跨場景、跨 session 的東西「搜得到」            │
│  而不是「靠翻檔案」                              │
│  召回時可過濾（依場景 / 依標籤 / 依來源）         │
└────────────────────────────────────────────────┘
```

**合起來的關鍵是不破壞邊界**：

| 規則 | 為什麼 |
|---|---|
| **狀態分開、經驗共用並標源** | 共用同一個庫時，每條事實要帶來源標籤，召回才可過濾 |
| **語意層只讀摘要，不回寫狀態** | 一旦回寫，狀態就有兩個真源 → 分裂 |
| **抽取失敗要能看見** | 靜默失敗會讓錯誤長期留在記憶裡；失敗率必須是可觀察數字 |

---

## 5. 跨層串味的真實教訓

多個 profile 共用同一個語意庫時，會發生**跨層串味**：
一個場景寫進去的專業事實，另一個不相干的場景召回時也會帶出來。

**兩種解法**：

| 做法 | 效果 | 代價 |
|---|---|---|
| **分庫**（每 profile 一個） | 隔離乾淨 | 失去跨 profile 召回 |
| **共用庫 + 標源**（`retainTags` 標明來源） | 保留跨 profile 召回，召回可過濾 | 需要過濾機制真的存在 |

> **與場景記憶的邊界模型一致的做法：狀態分開、經驗共用並標源。**
>
> 分庫做一半是最糟的狀態：庫分好了，但配置沒切、內容沒搬，
> 結果是「以為隔離了，其實沒有」——比不做還危險，因為它讓你停止警覺。

---

## 6. 失效模式

| 層 | 症狀 | 根因 | 修法 |
|---|---|---|---|
| 場景記憶 | 交接沒寫 → 下一任接手缺一步 | 人忘了 | fail-closed：check 不過不許換會話 |
| 場景記憶 | 兩份數字打架 | 同一事實兩處 | 單一權威 |
| 語意記憶 | 抽取失敗但沒人知道 | 失敗是靜默的 | 失敗率必須是可觀察數字 |
| 語意記憶 | 錯誤事實長期污染 | 抽錯了就留在那 | 蓋掉成本必須夠低（能寫 correction 就能救） |
| 兩層之間 | 語意層把狀態也寫回去 | 分工沒定清楚 | **語意層只讀不寫狀態** |

---

## 7. 一句話記住

> **場景記憶是帳本，語意記憶是 wiki。**
> **帳本回答「現在」，wiki 回答「以前」。**
> **兩個都要，但分工要死——分工不清，兩套加起來會比只有一套更亂。**
