# 二 · 場景 —— 一個場景＝累積的載體

> 場景不是「資料夾」，是**邊界**。
> 它同時回答三個問題：**這個場景歸誰管？它的邊界在哪？別的場景看得到它什麼？**
>
> 在[一-累積](一-累積.md)的框架裡，它還回答第四個問題：
> **這次做過的活，累積到哪裡去了？**

---

## 1. 什麼才算一個場景

**判據（一條就夠）**：這類活**會反覆回來**，而且**每次都用到同一批檔案、同一套規矩、同一個領域的知識**。

> 為什麼「會反覆回來」是判準？因為**累積只在反覆的活上才有意義**。
> 一次性的活不該開場景——那是[臨時執行體](../05-對照與選型/一-場景與臨時執行體.md)的位置。

| ❌ 不是場景 | ✅ 是場景 |
|---|---|
| 「今天做影片」——一次性的任務 | 「影片工作流」——每次做片都要用到分鏡規範、素材庫、發布檢查 |
| 「一個專案」——有明確結束點 | 「場景丁」——每週都會回來，永遠不會結束 |
| 「按工具分」——一個工具一個場景 | 「按職能分」——一段職責一個場景 |

**場景與專案的差別**（很容易搞混）：

| | 場景 | 專案 |
|---|---|---|
| 生命週期 | 長期存在 | 有明確結束點 |
| 邊界 | 由職責決定 | 由交付物決定 |
| 記憶歸屬 | 場景擁有 | 專案記憶放在**場景**底下 |
| 例子 | 場景丁 | 「2026 年 10 月電路學講義考古」 |

> 一個場景底下可以有多個專案；**專案結束，場景還在**。

---

## 2. 六件套：一個場景要齊的東西

| # | 件 | 誰寫 | 作用 |
|---|---|---|---|
| 1 | **場景配置**（json） | 機主 | 面板布局、型別、座標、綁定哪條會話 |
| 2 | **定位卡** | 人 | 一句話說清「我是誰、我在哪、我管什麼」——**路由與校驗的錨點** |
| 3 | **場景私有記憶** | 人 | §〇 交接 + 職責 + 決策與坑（**唯一真源**） |
| 4 | **場景專屬技能** | 人 | 只有本場景看得到的做法；**別的場景連清單裡都沒有** |
| 5 | **可選面板** | 機主 | 預覽 / 檔案 / 網址 / 對話——工作台的可見部分 |
| 6 | **常駐會話 + 身分索引一行** | 工具建 | 每次開場都是同一條會話；索引表是**單一權威** |

目錄長相：

```
場景/<場景名>/
├── .git/                        ← ★ 場景邊界（引擎靠它判定專案根）
├── AGENTS.md                    ← 場景憲法（只對本場景的會話注入）
├── .dsh/skills/<場景id>/SKILL.md ← 場景專屬技能（只在本場景可見）
├── 定位卡.md                     ← 場景身分說明書
├── 場景私有記憶.md                ← ★ 記憶真源（§〇 交接 ≤ 4 KB）
├── 身份卡.md                     ← 工具生成，⛔ 手改即校驗失敗
├── 場景畫像.md                   ← 工具生成，⛔ 手改即校驗失敗
├── 專案記憶/                     ← 一專案一份
├── 歸檔/                         ← 舊版快照（只進不改）
└── _檔案索引.md
```

## 3. 邊界怎麼劃：`.git` 就是路由表

這是整個架構裡最值得拿出來講的一段。

很多人以為「派給誰」就是把一句話丟給某個 agent。這套做法是：
**派給誰，不問模型，問檔案系統。**

引擎從會話的工作目錄往上找，命中第一個含 `.git` 的目錄，就把它當「專案根」，
然後**只**載入這棵樹裡的 `AGENTS.md` 和 `.dsh/skills/`：

```js
// dsh-agent-instructions/lib/index.js:574
async function findProjectRoot(cwd, markers, fileSystem, signal) {
  let current = resolve(cwd);
  for (;;) {
    for (const marker of markers)          // markers 預設 = [".git"]
      if (await existsAsMarker(join(current, marker))) return current;
    const parent = dirname(current);
    if (parent === current) return resolve(cwd);
    current = parent;                       // 一路往上找
  }
}
```

技能可見性是同一套邏輯：

```js
// dsh-skill-filesystem/lib/index.js:154
const projectRoot = await findProjectRoot(resolve(cwd), ...);
roots.push({ path: join(projectRoot, ".dsh/skills"), source: "project-dsh" });
roots.push({ path: join(projectRoot, ".agents/skills"), source: "project-agents" });
roots.push({ path: join(this.dshHome, "skills"), source: "user-dsh" });     // 全域可見
```

### 所以「換場景 = 換腦子」

| | 場景丁 | 場景甲 |
|---|---|---|
| 場景憲法 | 只有 `場景/場景丁/AGENTS.md` | 只有 `場景/場景甲/AGENTS.md` |
| 可見技能 | `sc-d` | `sc-a` |
| 記憶真源 | `場景/場景丁/場景私有記憶.md` | `場景/場景甲/場景私有記憶.md` |

準確地說，不是「模型被禁止接別的活」，而是**它看到的世界裡根本沒有那個場景的東西**——
沒有那套憲法、那個技能、那份記憶，所以連「該不該接」都無從判斷。

> **這裡的哲學：用結構消除錯誤，而不是用提示詞請求正確。**
> 提示詞寫得再好，它也只是「請求」；檔案系統的邊界是「事實」。

### 兩層憲法

```
Instructions from: <全域>/AGENTS.md      ← 全域憲法（每輪注入，所有會話共用）
Instructions from: AGENTS.md              ← 場景憲法（只在本場景樹內）
```

全域憲法定義規矩（記憶在檔案裡、場景主權、一次派單＝一條回執、有可觀察落點才算做完）；
場景憲法定義**這個場景**的職責與邊界。

## 4. 怎麼切場景：十種真實切法

| # | 切法 | 例子 |
|---|---|---|
| 1 | 按**職能** | 場景甲（派單）／場景丁（整理）／場景丙（維護） |
| 2 | 按**交付物型別** | 影片／文章／簡報 |
| 3 | 按**客戶** | 甲方 A／甲方 B（但：**同一職能、不同客戶**通常該放同一場景，用專案記憶分） |
| 4 | 按**時間週期** | 日更／週更 |
| 5 | 按**技術棧** | 前端／後端 |
| 6 | 按**裝置** | 桌機／筆電／伺服器 |
| 7 | 按**權限邊界** | 涉密工作隔離 |
| 8 | 按**節奏** | 常駐待命／突發搶修 |
| 9 | 按**記憶特徵** | 需要長期累積 vs 一次性 |
| 10 | 按**人手** | 誰負責這塊 |

### 切錯的三種典型

| 症狀 | 切錯在哪 | 修法 |
|---|---|---|
| 場景越來越多，每個都沒活 | **切太細** | 合併：兩個場景如果用同一批檔案、同一個領域知識，就該合 |
| 場景裡總在講別人的事 | **切太粗** | 拆開：出現跨領域的活，說明邊界沒對齊 |
| 場景要同時讀兩個目錄 | **邊界不對** | 換成「一個場景一個 git 倉庫根」，需要跨的那部分放共享層 |

## 5. 場景主權：硬規則，不是禮貌

| 規則 | 內容 |
|---|---|
| **只寫自己的** | 每個場景只寫自己的 `場景私有記憶.md` |
| **要動別人的，只能發請求** | 發現別人的記憶有錯 → 派單／通知，⛔ 不許代改 |
| **改誰的記憶，只歸誰** | 這條消滅了最難查的一種 bug：兩個 agent 搶著寫同一份記憶 |

獨立 git 倉庫 + 主權規則，等於每次改動都能 **diff、能追責**——
**記憶變成有版本控制的資產，不是模型的體內記憶。**

## 6. 場景幾何與六件套的對應

```
┌─ 全域層 ────────────────────────────────────────┐
│  全域 AGENTS.md · 全域技能 · 引擎 · 工具          │
│  （規則只有一份，場景只做 specialize）             │
└────────────────────────────────────────────────┘
                    ▲ 每一場景只能看見自己這棵樹
┌─ 場景 A ─────┐ ┌─ 場景 B ─────┐ ┌─ 場景 C ─────┐
│ 自己的 .git  │ │ 自己的 .git  │ │ 自己的 .git  │
│ 自己的憲法   │ │ 自己的憲法   │ │ 自己的憲法   │
│ 自己的技能   │ │ 自己的技能   │ │ 自己的技能   │
│ 自己的記憶   │ │ 自己的記憶   │ │ 自己的記憶   │
│ 自己的專案   │ │ 自己的專案   │ │ 自己的專案   │
└──────────────┘ └──────────────┘ └──────────────┘
         唯一合法的跨場景通道 ↓
┌─ 共享層 ────────────────────────────────────────┐
│  身分索引 · 跨場景看板 · 待辦 · 衝突簿 · 專案清單 │

└────────────────────────────────────────────────┘
```

## 7. 場景体系的失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 場景越加越多，越加越空 | 切太細 | 用「會反覆回來」判準合併 |
| `.git` 掉了，場景技能全部消失 | 引擎只認 `.git` 當專案根 marker，掉了會**靜默上溯** | 把「`.git` 存在性」加進 check（⚠ 症狀不明顯：憲法仍會被鏈式載入） |
| 切場景後 AI 像換了個人 | `sessionId` 指向舊會話 | 換會話協議第 ③ 步 |
| 別的場景的技能也看得到 | 全域技能對所有會話可見 | 場景隔離只隔離**專案級**那部分；全域技能要精簡 |
