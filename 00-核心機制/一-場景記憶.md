# 一 · 場景記憶 —— 會話會被換掉，狀態必須留在檔案裡

> 一條 AI 會話是有壽命的：上下文會滿、會被壓縮、會被換掉、會因為一次升級而重啟。
> **所有「只存在於對話裡」的東西，都會在某一天消失。**
>
> 這套機制只幹一件事：**讓「記憶」不依賴會話而存在。**

---

## 1. 核心前提：記憶在檔案，不在會話

| 做法 | 結果 |
|---|---|
| 靠對話歷史記著「我幹到哪了」 | ❌ 一換會話就斷片；壓縮之後細節也沒了 |
| 靠 AI 自己「記得」 | ❌ 它記不住；它只會在上下文裡看到什麼就以為是什麼 |
| **靠檔案裡的交接** | ✅ 會話換一百次，記憶都還在 |

**推論（很重要）**：一條會話的價值 = 它**產出的檔案**，不是它聊了多少。
所以「換會話」不是災難，**沒寫交接就換**才是災難。

---

## 2. 三層結構：為什麼必須分層

```
┌─ ① 注入層（全域鐵律）──────────────────────────────┐
│  每輪對話自動注入。人人都在付這個成本 ⇒ 必須極短   │
│  只放「不讀就會白幹」的鐵律，⛔ 不放教程和細則       │
└──────────────────────────────────────────────────┘
┌─ ② 私有層（每個場景一個資料夾）─────────────────────┐
│  場景私有記憶.md（§〇 交接 ≤ 4 KB，人寫）            │
│  身份卡.md / 場景畫像.md（工具生成，手改即校驗失敗） │
│  + 專案記憶/<專案id>.md（一專案一份，≤ 8 KB）        │
│  只有本場景開場讀 ⇒ 換會話時它是唯一入口            │
└──────────────────────────────────────────────────┘
┌─ ③ 共享層（板 / 台帳 / 索引）─────────────────────┐
│  發生了什麼 · 該做什麼 · 東西在哪 · 誰是誰          │
│  不屬於某個場景，誰需要誰讀                          │
└──────────────────────────────────────────────────┘
```

**三層怎麼流動**：

```
一輪對話 ──每輪自動注入──▶ ① 注入層（全域鐵律，必須極短）
    │
    └──新場景開場讀──▶ ② 私有層（§〇 交接 ≤ 4 KB）
                              │
              結論落到長期────┴──▶ ③ 共享層（看板·待辦·索引）
                              │
              歷史太厚──────────┴──▶ 歸檔層（只留指針）
```

**為什麼不能合成一份**：

| 合一之後的後果 | 具體數字 |
|---|---|
| 注入層變長 ⇒ **每輪都更貴** | 注入 60 KB ≈ 每輪多付 20k token；一天幾十輪就是災難 |
| 私有層變長 ⇒ **開場讀不完** | 曾經有一份場景記憶漲到 40 KB，結果沒人讀，交接形同虛設 |
| 共享層混進私有內容 ⇒ **互相干擾** | 別人的進度擠進你的開場，你讀到一堆與你無關的東西 |

> **判據：「這東西誰會讀？多久讀一次？」**
> 每輪都讀 ⇒ 注入層（必須極短）· 每場開場讀 ⇒ 私有層（≤ 4 KB）· 需要時才查 ⇒ 共享層或按需文件。

---

## 3. 私有層：`§〇 交接` 到底寫什麼

每個場景的私有記憶在 `<工作台根>/場景/<場景名>/場景私有記憶.md`
（人寫；同目錄 `身份卡.md`、`場景畫像.md` 由工具生成，⛔ 手改即校驗失敗）。

`§〇` **覆蓋寫**，只留最新一份，固定五小節：

```markdown
## §〇 當前交接（≤ 4 KB，新會話先讀這一節）

### 1) 上次交接
- <做了什麼 / 結果 / 證據>

### 2) 當前專案
| 專案 | 記憶檔 | 狀態 | 下一步 |
|---|---|---|---|
| <專案名> | <專案id>.md | 進行中 | <動作> |

### 3) 私有記憶變更
- <YYYY-MM-DD>：<改了什麼 + 為什麼>

### 4) 下一步 / 卡點
- 下一步：<誰先動，按什麼順序>
- 卡點：<沒有就寫「無」；有就寫清等誰>

### 5) 全貌（工具生成，別手改）
```

**§〇 的回答只有四個**：我是誰／幹到哪／下一步／卡在哪。

> ⚠️ **最常見的錯誤：把 §〇 寫成週報**（今天做了 1、2、3、4、5 件事，每件三大段）。
> 結果：一是超線，二是新會話讀完之後仍然不知道「下一步該幹什麼」。

### 四條硬規矩

| 規矩 | 為什麼 |
|---|---|
| **只留最新一份**（覆蓋，不追加） | 追加會無限長；「上次進度」只有一份是有意義的 |
| **≤ 4 KB** | 超了就沒人讀；4 KB 約等於「看 30 秒就能開工」 |
| **每輪最新，舊的搬 `歸檔/`** | 歷史不能丟，但不能占著入口 |
| **寫「指針」不寫「全文」** | 細節放專案檔案／技能裡，這裡只寫「在哪」 |

## 4. 共享層：四塊板，各回答一個問題

| 板 | 回答 | 誰寫 | 生命週期 |
|---|---|---|---|
| **跨場景看板** | **發生了什麼**（公告 / 派單 / 回執） | 發通知的工具自動寫 | 最新在上；每場景只在自己記憶裡留 ≤5 條摘要 |
| **待辦板** | **該做什麼**（全機唯一落點） | 任何場景加一行，同一件只許一行 | 做完刪行；掛起太久搬歸檔 |
| **總索引 / 身份索引** | **東西在哪**（場景 ↔ 記憶 ↔ 卡 ↔ 技能） | 新建／移動時就登記 | 表格化，單一權威 |
| **衝突簿** | **兩處打架了** | 任何人發現就登記 | 裁決後關閉 |

**為什麼板要分開**：它們**更新頻率不同**（看板一天幾十條、索引一週幾條）、
**讀者不同**（看板人人看、索引偶爾查）、**責任不同**（看板誰發誰寫、索引誰建誰登記）。
混在一起的結果是：更新最頻繁的那塊把所有東西都擠沒了。

---

## 5. 寫回判據：什麼該記，什麼不該記

**只有「實質工作」才寫回**：

| ✅ 記 | ⛔ 不記 |
|---|---|
| 建／改了一個應用、修了一個 bug | 搜尋結果 |
| 寫了一份報告／文件 | 臨時路徑 |
| 重構 / 架構變更 | 工具報錯原文（要記就記「症狀→根因」） |
| 選定了一個技術方案 | 一次性約束（「這次先這樣」） |
| 機主分享的約定 | 聊天過程 |

**量也有上限**：每次寫回 **≤ 10 行 / ≤ 2 KB**。
超了說明你在抄過程，而不是記結論——過程屬於當輪的對話，結論才屬於記憶。

> **判據：「三個月後我還會需要這一行嗎？」** 不需要就別寫。
> 記憶的價值不在於「全」，在於「**下次開工能 30 秒接上**」。

## 6. 體量紅線與到線動作（記憶會發胖，必須減肥）

| 對象 | 紅線 | 到線怎麼辦 |
|---|---|---|
| 場景記憶主檔案 | **≤ 25 KB** | 把舊輪次、舊決策搬進 `歸檔/`，主檔案只留入口 + 指針 |
| `§〇 交接` | **≤ 4 KB** | 同上：歷史搬走，只留「最新一份 + 指針」 |
| 專案記憶 | **≤ 8 KB** | 拆成「主檔 + 附錄」 |
| 技能（單篇） | **≤ 12 KB** | 拆成「主檔 + reference 子檔」 |
| 注入層（全域鐵律） | 越短越好 | 細則全部下沉到「規範」層（不注入，按需查） |

**減肥的硬要求：只搬不丟，而且必須能證明。**

```
① 先存一份「搬之前」的快照
② 搬（歷史 → 歸檔/）
③ 跑核對腳本：逐行比對「搬前非歷史行 == 搬後非歷史行」
      命中 0 差異 ⇒ 才算沒丟
④ 跑索引體檢：死條目 / 未登記 / 過期 / 身分漂移
```

> 真實教訓：有一次沒存快照就動手拆，結果**核對腳本根本跑不了**——你無法證明自己沒丟東西。
> 從那以後規矩改成：**先快照，再動手。**

---

## 7. 換會話協議（這套機制裡最實操的一條）

```
① 先把「進度 / 下一步 / 卡點」覆蓋寫進 §〇   ← 這一步就是「交接」，別省
② 再換（新建會話 + 舊會話歸檔）
③ 換完同步三處：
     · 場景配置裡的 sessionId
     · 身分索引表的會話 id 欄
     · §〇 裡的交接署名（「本交接由會話 <新id> 於 <日期> 改寫」）
④ 跑自檢：逐面板應印出「✓ id 命中（身分校驗通過）」
```

**為什麼第 ③ 步不能省**：面板是按 `sessionId` 釘會話的。不同步 ⇒ 面板指向一條**已歸檔的會話**，
表現為「切到這個場景，AI 像換了個人」（其實就是換了個人）。

**什麼時候才該換**（這條很反直覺）：

| 觸發 | 換嗎 |
|---|---|
| 機主說「換會話」 | ✅ 換 |
| 上下文超限（報 413）且**壓縮之後仍然** 413 | ✅ 換（真死局） |
| 只是「到壓縮線了」、還沒報錯 | ❌ **不換**——引擎會自動壓縮，繼續幹 |
| 任務做完了 | ✅ 建議換（一個話題一個會話） |

## 8. 失效模式（都真實發生過）

| 症狀 | 根因 | 修法 |
|---|---|---|
| **記憶越寫越肥，最後沒人讀** | 把過程、搜尋結果、報錯原文都寫進去 | 寫回判據 + 體量紅線 |
| **兩份數字打架**（記憶說 A，台帳說 B） | 同一事實存在兩處 | 單一權威：一個事實只存一處，另一處只放指針 |
| **切換場景後「失憶」** | `sessionId` 指向舊會話 | 換會話協議第 ③ 步 |
| **別人的判斷出現在我的記憶裡** | 跨場景直接寫對方記憶 | 場景主權：別人的地盤只許寫請求 |
| **「體積正常」但內容沒用** | 只盯體量，不看「讀完能不能開工」 | 判據改成：新會話讀完 §〇，**30 秒內能不能說出「下一步幹什麼」** |
| **看板分裂成兩塊** | 兩個腳本的記憶根指向不同路徑 | 統一路徑解析（見 [四-已知裂縫與待修](../02-落地實作/四-已知裂縫與待修.md)） |

---

## 9. 最小可用（先只做這四件）

1. **每個場景一份記憶檔案**，第一個小節固定寫 `§〇 交接`（身分／進度／下一步／卡點）；
2. **換會話之前必須先寫 `§〇`**（寫不出「下一步」說明這輪白幹了）；
3. **`§〇` 控制在 4 KB 內**，超了把歷史搬進 `歸檔/`；
4. **只記結論，不記過程**（≤ 10 行／次）。

等你有 3 個以上場景、且開始「同一個事實兩處不一致」了，再來補共享層四塊板。
