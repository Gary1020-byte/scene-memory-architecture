> 狀態：**計畫，未執行**（2026-11-09 草擬）

> 規格依據：[九-場景粒度與路由階層](九-場景粒度與路由階層.md)

## 0. 先擋掉一個錯誤前提

**「場景越多 → 注入層越多 → token 浪費」不成立。**

引擎注入的是 `ancestorChain(projectRoot, cwd)`——**從專案根走到 cwd 那一條路徑**，
不是所有場景。專案根 = 從 cwd 往上找第一個含 `.git` 的目錄。

實測本機：

| | 字數 |
|---|---|
| 全域 `~/.dsh/AGENTS.md` | 921 chars |
| 24 個場景 AGENTS.md **合計** | 33,451 chars（**不會一起注入**） |
| **單會話實際注入** | **≈ 2,315 chars**（全域 + 本場景那一個） |

⇒ **拆場景不會增加單會話 token；拆得夠細反而更省**（每個小場景的 AGENTS.md 更短）。

**所以「更小的場景」的理由不是省 token，是別的。** 下面三個才是真的：

| # | 真理由 | 證據 |
|---|---|---|
| 1 | **累積的東西不同批** | 影片剪輯 §五#11 有 7 條音訊／字幕軸實測值，跟 beats／zoompan 是不同批知識 |
| 2 | **路由表命中精度** | 24 場景 / 348 關鍵字，平均 14.5 字／場景，最多「開發工具」30 字 |
| 3 | **場景主權邊界清楚** | 語音合成 職責(2) 已聲明「人聲分軌」；影片剪輯也在做音訊驗證 ⇒ 邊界有重疊 |

## 1. 候選對象（三個，都用累積判準篩過）

### 候選 A：音訊分離與驗證（使用者原始構想）

> 從既有混音分離人聲、驗證人聲在位與對齊。

**問題：可能切錯了。**

實測：
- **語音合成場景** 職責(2) 已寫：「**分軌輸出** —— 人聲分軌 + 可疊加的伴奏軌，供音效配樂／影片剪輯場景混音」
- **影片剪輯** §五#11 已有：「相減法驗人聲、相關法驗位置」、「單獨渲染人聲分支用 silencedetect 可拿到句段」

⇒ **這個活已經有 owner 了**。再切一個「音訊分離」小場景，就是規格 §4 的典型「切太細」：
兩個場景用同一批工具（ffmpeg）、同一批知識（人聲／伴奏的關係），記憶會被切成兩半，
切口處兩個場景都要重述同一件事。

**除非**累積的東西真的不同批——比如「從成品混音反向分離」需要一套跟 TTS 完全不同的
模型選擇、參數、誤判型態。目前**沒有證據顯示這是常態**（§〇 裡的實測案例是
配音的產生與驗證，不是反向分離）。

### 候選 B：SPOT 機械檢查（實測證據最強）

> `專案記憶/SPOT檢查.mjs` —— 21 KB 的機械驗收腳本，負責「動態圖像／影片的時序對照檢查」。

**支持拆的理由：**
- 它有**獨立的語言與契約**（§〇 提到「SPOT 對照契約」是影片剪輯場景的三條核心職責之一）
- §〇 有明確的待決事項：「修 SPOT 鍵號錯位」——這是**這支腳本自己的坑**，不是影片剪輯的坑
- 它跨多個場景可用（動態圖像也有對應的檢查需求）
- **它是程式，不是記憶**——很適合做成「能力場景」：主體是 skill，記憶很薄

**反對拆的理由：**
- 它現在住在「影片剪輯」的**專案記憶/** 裡（不是場景記憶），本來就沒污染 §〇
- 拆了要處理 ffmpeg／動畫渲染的依賴

### 候選 C：字幕軸對齊（phrase_timing）

> `phrase_timing.json` 的產生與量測（§五 有實測值：實測字幕比人聲慢 1.6 s、停頓量測法）。

**支持：**這是**語言層**的活（量停頓、切語氣片語、對回標點），跟影片剪輯的**畫面層**（beats／zoompan／轉場）確實不同批。
**反對：**它需要拿到配音成品與最終混音，跟影片剪輯的驗收流程交疊很緊。

---

## 2. 推薦：**先做候選 B（SPOT 機械檢查）做「能力場景」示範**

理由：
1. **累積不同批有實證**（鍵號錯位是它自己的坑）
2. **它是程式不是記憶** ⇒ 記憶可以很薄，正好演練「無記憶場景」這個新型別
3. **它本來就在專案記憶裡**（不是場景記憶）⇒ 拆出來不動任何既有記憶真源，**零風險**
4. **它跨場景**（影片剪輯 + 動態圖像）⇒ 值得有自己的路由關鍵字

## 3. 型別設計：「能力場景」（Capability Scene）

現在只有三型，缺的那一格正是「有專屬技能、有路由入口、有憲法，但不需要記住上次做到哪」。

### 最小型別

| | 有 | 沒有 | 理由 |
|---|---|---|---|
| `.git/` | ✅ **必須** | | 沒有它專屬技能不載入（症狀不明顯：憲法仍鏈式載入） |
| `AGENTS.md` | ✅ **極短**（≤800 bytes） | | 只講「我幹什麼／我不幹什麼」 |
| `.dsh/skills/<id>/SKILL.md` | ✅ **主體** | | 能力本身在這裡 |
| `定位卡.md` / `身份卡.md` / `場景畫像.md` | ✅ 工具生成 | | |
| `_檔案索引.md` | ✅ | | |
| `專案記憶/` | | ❌ | 沒有專案概念 |
| `歸檔/` | | ❌ | 沒有交接概念 |
| `場景私有記憶.md` | | ❌ | **沒有「上次做到哪」這件事** |
| 常駐會話 | ✅ | | 要能接活、能被打擾 |

### 記憶歸屬：母場景持有，只讀借用

子場景**不開記憶檔**。它的記憶落在母場景的 `場景私有記憶.md`：

- 子場景的 `AGENTS.md` 寫：「我的進度與決策寫在 `../影片剪輯/場景私有記憶.md` 的 §〇 / §五」
- 子場景**只讀**，回執**寫回母場景**（派單機制天然支持：回執發給母場景）
- ⇒ 記憶仍然**只有一個真源**，主權規則不破

### 需要改的工具（3 處）

| 工具 | 改什麼 | 為什麼 |
|---|---|---|
| `工具/場景記憶.mjs` `check` | 場景 json 帶 `"型別": "能力場景"` ⇒ 免檢 `場景私有記憶.md`／`專案記憶/`／`歸檔/`；仍必檢 `.git`、`AGENTS.md`、定位卡、身份卡、場景畫像、技能 | 現在 check 硬性要求 4 個檔 + 2 個目錄 |
| `工具/場景記憶.mjs` `stamp` | 能力場景不寫「記憶真源」那行 | 身份卡模板寫死「記憶真源：場景私有記憶.md」 |
| `工具/派單.mjs` 路由表 | 條目可帶 `"型別": "能力場景"`；關鍵字仍用複合詞優先機制 | 路由本身不需改，只加型別欄位 |

**不改的**：`建會話.mjs`、`呼叫場景.mjs`、`開新場景.mjs` 的註冊邏輯（能力場景照樣要 4 處登記）。

## 5. 風險與停止條件

| 風險 | 機率 | 緩解 |
|---|---|---|
| 改 `check`/`stamp` 影響到既有 24 場景 | 中 | 步驟 2 後立刻對 24 場景跑 `check --all` 比對前後輸出；**有差異就停** |
| 改路由表格式影響既有路由 | 中 | 步驟 3 後跑 `路由回歸測試.mjs`（已有 67 句回歸測試，命中率 100%） |
| 能力場景沒有記憶 → 換會話後不知道做到哪 | **高** | 這是型別的**設計後果**，不是 bug。緩解：能力場景**不開常駐會話也沒關係**——它靠派單被叫，幹完回執給母場景。若實測發現真的需要自己的進度，就補一個極薄的 `場景私有記憶.md`（只留 §〇） |
| 路由關鍵字跟既有 owner 搶字 | 中 | 步驟 6 用 `派單.mjs` 歧義檢查；關鍵字用複合詞（「時序對照」而非「檢查」） |
| 這是為做而做（沒有真實需求） | 中 | 步驟 8 端到端若跑不出真實派單場景，就停——**不為了示範而建場景** |

**停止條件**：步驟 8 若沒有真實的活可派，這個能力場景就不該存在（回滾步驟 4-7）。

## 6. 一次性成本 vs 永久成本

| | 一次性 | 永久 |
|---|---|---|
| 新增 | 能力場景型別規格、3 支工具各改幾十行 | 能力場景的 AGENTS.md（≤800 bytes，**每會話注入**） |
| | 一個場景目錄（6 件套，無記憶檔） | 它的技能（可增量改） |
| | 4 處登記 + 1 條常駐會話 | 路由關鍵字（複合詞，會被其他關鍵字壓制，勝率隨語料變動） |
| | 路由回歸測試加 3-5 句 | |
| **vs 現況** | | **每會話注入量：從 ≈2,315 → ≈1,700 chars（少 26%）** |
