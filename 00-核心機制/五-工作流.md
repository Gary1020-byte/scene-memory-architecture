# 五 · 工作流 —— 場景怎麼串成一條線

> 一個場景是一件事。工作流是**幾件事的順序與銜接**。
>
> 派單是**一跳**，工作流是**多跳，而且會自己接著往下跳**。

---

## 1. 為什麼需要工作流

沒有工作流時，跨場景的活要靠機主逐段下指令：

```
機主 → 場景A → （機主回話）→ 場景B → （機主回話）→ 場景C
```

每一跳都要人接一次，而且**中間的資訊靠人轉述**。人有一次沒接住，整條鏈就斷在那裡。

有工作流時：

```
機主啟動一次 → A → B → C → 總回執
```

中間的銜接由工作流定義決定，不由人臨場決定。

> **工作流把「誰接著誰」從人的記憶裡搬到檔案裡。**
> 這跟場景把「狀態」從對話裡搬到檔案裡，是同一個動作。

## 1又二分之一、引擎端實作：鏈式呼叫（2026-11-03 實測）

> 工作流在引擎端的最簡形式：**場景依序串成一條鏈，每一棒都帶著上一棒的結論與下一棒是誰。**
> 對應工具：`<工作台根>/工具/鏈式呼叫.mjs`；repo 端的引擎中立部分見[工作流定義格式](../04-模板/工作流模板.md)。

### 為什麼一棒一棒等，不是「一次全叫」

| | 一次全叫 | 一棒一棒 |
|---|---|---|
| 五個場景 | 同時講話 | 依序接 |
| 讀回來 | 分不清誰跟誰接 | 每一棒都拿到上一棒的結論 |
| 交接 | 靠場景自己猜誰是下一棒 | **主控端明講下一棒是誰** |

### 每棒的訊息帶四件（缺一件就會空轉）

```
① 你是第 N 棒（共 M 棒）
② 上一棒的結論（第一棒則是「你是第一棒，先讀 §〇」）
③ 下一棒是誰（最後一棒則是「請總結整條鏈」）
④ 請回覆：狀態 ＋ 【下一棒】交接
```

### 實測結果（5 棒：場景甲 → 場景乙 → 場景丙 → 場景丁 → 場景戊）

| 棒 | 場景 | 回覆品質 |
|---|---|---|
| 1 | 場景甲 | ✅ 讀了 §₀、講了三項待拍板、寫了具體交接 |
| 2 | 場景乙 | ✅ 讀了 §₀、指出 11-02 練習單因 cron 撞 429 未生成 |
| 3 | 場景丙 | ⚠️ 「狀態與上一棒一致，未開始任何操作」 |
| 4 | 場景丁 | ⚠️ 「本次為第 4 棒交接轉述，未做實際操作」 |
| 5 | 場景戊 | ✅ **看穿了整條鏈**：「整條鏈實質為空轉」 |

> ★ **空轉不是 bug，是正確行為。**
> 訊息只說「回覆你的狀態」，沒有派任務 ⇒ 場景讀了自己的 §₀，發現沒活，就如實回報。
> **第 5 棒還主動指出整條鏈沒推進任何東西**——這正是「不靠信任，靠讀證據」。

### 兩個實作坑

| # | 症狀 | 根因 |
|---|---|---|
| 1 | 讀回的「回覆」是「已读」這種中間輸出 | assistant 會送出只有 tool-call 的中間訊息 ⇒ **要抓最長的那則有實質文字的** |
| 2 | `session/create` 報 `accepts workspaceId or cwd, not both` | 引擎不接受兩者同給 ⇒ 擇一 |

## 2. 工作流是什麼、不是什麼

| 是 | 不是 |
|---|---|
| 幾個場景的**順序、入口條件、判準、失敗策略** | 一段程式碼 |
| 一份**檔案**（共享層第五塊板） | 一個常駐的執行器 |
| 一次啟動 = 一條**鏈** | 一個把所有場景綁在一起的容器 |

**它跟「把三個場景排成一列」的差別**在兩件事：

- **分岔**：什麼情況走別的路
- **失敗處理**：壞了停在哪、要不要人介入

沒有這兩項，那只是序列；有這兩項，才是工作流。

## 3. 工作流定義（共享層第五塊板）

工作流定義住在共享層，**共享的是定義，不是狀態**。

```
共享/
├── _場景身份索引.md      ← 板 1：東西在哪
├── _跨場景通知.md        ← 板 2：發生了什麼
├── _待辦.md              ← 板 3：該做什麼
├── 衝突.md               ← 板 4：兩處打架了
└── 工作流/               ← 板 5：★ 計畫（要做什麼、順序、判準）
    ├── 磁碟體檢與清理.yaml
    └── 每週復盤.yaml
```

> **為什麼要獨立成板，而不是塞進看板或待辦？**
> 看板是**現況**，待辦是**事項**，工作流是**計畫**——它有順序、有條件、有分岔，
> 塞進任何一塊都會被擠扁。更新頻率也不同：工作流一個月動一次，待辦一天動十次。

### 工作流定義的欄位

```yaml
id: 磁碟體檢與清理
名稱: 磁碟體檢 → 清理 → 報告
版本: 1
步驟:
  - 場景: 場景丙
    目的: 找出可清理的項目
    判據: 列出可釋放 ≥ 1 GB 的項目，每項標明路徑與大小
    落盤: 場景/場景丙/專案記憶/磁碟體檢-<日期>.md
    需確認: false
  - 場景: 場景丙
    目的: 清理
    判據: 實際釋放 ≥ 1 GB，並在回執列出刪了什麼
    需確認: true          # ★ 不可逆 ⇒ 設門檻
  - 場景: 場景甲
    目的: 出報告
    判據: 報告落盤且首行寫在共享看板
    需確認: false
失敗策略: 停在原地等人      # stop | continue | rollback
分岔:
  - 當: 步驟1 未找到 ≥1GB 可清理
    則: 跳過步驟2，直接進步驟3
```

| 欄位 | 作用 | 缺了會怎樣 |
|---|---|---|
| `步驟[].場景` | 這一跳由哪個場景執行 | 沒有對象 |
| `步驟[].目的` | 這一跳要做什麼 | 像一句願望 |
| `步驟[].判據` | **什麼算這步做完**（可驗證） | 回執無從判定真假 |
| `步驟[].落盤` | 產出寫到哪 | 產出散落，後續跳接不到 |
| `步驟[].需確認` | 這步是不是門檻 | 不可逆操作會被自動跑掉 |
| `失敗策略` | 壞了怎麼辦 | 壞了就斷在半路，沒人知道 |
| `分岔` | 條件式路徑 | 只能走直線 |

> **`判據` 這一欄是整份定義的核心。** 沒有判據，工作流的「完成」只是感覺。

## 4. 門檻：什麼該停、什麼不該停

工作流預設**自動往前跑**。只有兩種情況會停下來：

### 情況一：這一步被標了門檻（`需確認: true`）

停下來等人看過再繼續。**門檻該標在哪裡**，三個判準任一成立：

| 判準 | 例子 |
|---|---|
| **不可逆** | 刪檔、對外發送、發布 |
| **要花不可回收的資源** | 錢、對外配額、對第三人的通知 |
| **產出會被下游當成事實** | 刪完的清單會被後續步驟拿去刪東西 |

**中間步驟不設門檻。** 體檢、產草稿、整理清單這些可重跑的步驟，設門檻只會把工作流變成逐跳確認——那樣就失去意義了。

> **安全不該靠「每步都問人」，該靠「壞了就停」。**
> 逐跳確認是把停的決定權交給人每次都要行使；只在門檻停，是只在真正需要判斷時打斷。

### 情況二：任何一步失敗或回執不達判準 ⇒ 就地停下

這是**強制**的，不靠人設（fail-closed，跟整套架構同一套哲學）。

## 5. 執行生命週期

### 啟動（只有機主能啟動）

```
① 讀工作流定義 → 解析步驤、判準、失敗策略、分岔
② 預檢（fail-closed，任一不過就拒絕啟動）
     · 每個場景存在
     · 每個場景有邊界（獨立 git 倉庫）
     · 每步的判據非空
     · 入口步驟的入口條件已成立
③ 建立執行狀態（主控端私有，每個 run 一份）
```

### 每一跳

```
④ 主控端開一個新對話，綁定該步的場景
     → 這個對話開場自動讀該場景的 §〇（帶著累積）
⑤ 派單 ＝ 派單四件套 ＋ 上一跳的可累積物（若有）
⑥ 對話內執行
⑦ 收尾前寫：
     · §〇 交接（覆蓋寫，給下一個對話）
     · 回執三件套（見下文）
⑧ 關閉對話
⑨ 主控端校驗回執：
     · 判準是否達成？
     · 可累積物是否非空？
     · ★ 讀場景記憶，確認那條可累積物真的落地了
⑩ 依分岔條件選下一跳 → 回到 ④
```

> **第 ⑨ 步最後那段是這套設計的關鍵。**
> 主控端不只收回執，還去讀場景的記憶檔，確認那條可累積物真的被寫進去了。
> 這讓「回執要帶可累積物」從**口號**變成**機械可驗的事**——
> 而且順帶守住「⛔ 不許代改對方記憶」：驗收只讀不寫，寫入必須是場景自己做的。

### 停止與恢復

| 狀況 | 行為 |
|---|---|
| 某步失敗／回執不達判準 | **就地停下**，寫清楚「卡在哪、等什麼」 |
| 該步是門檻 | 跑完停下，等人確認 |
| 主控端中途重啟 | 從執行狀態恢復，**已完成的那跳不重跑** |
| 終點 | 產出一條給機主的總回執 |

## 6. 執行狀態放哪

**不在共享層**（那是計畫），**不在場景私有層**（那是某個場景的記憶，run 是主控端的東西）。所以要獨立一層：

```
<工作台根>/
├── 共享/                    ← L1 共享層：計畫與現況（所有人看同一份）
│   ├── _場景身份索引.md
│   ├── _跨場景通知.md
│   ├── _待辦.md
│   ├── 衝突.md
│   └── 工作流/<工作流id>.yaml
│
├── 場景/<場景id>/           ← L2 場景私有層：一件事的長期本體
│
├── 執行/<run-id>/           ← ★ L3 執行層：主控端私有（這一次的狀態）
│   ├── 執行狀態.md          ← 跑到哪、卡在哪、等什麼
│   └── 交接串.md            ← 每一跳的可累積物往下傳的載體
│
├── 工具/                    ← L4 工具層
└── 說明/                    ← L5 說明層
```

| | 共享層的工作流 | 執行層的 run |
|---|---|---|
| 內容 | **定義**：步驟、判準、分岔 | **狀態**：現在第幾跳、卡在哪 |
| 生命週期 | 長期，一版版改 | 一次啟動一份，結束封存 |
| 誰寫 | 機主 | 主控端 |
| 誰看 | 所有人 | 主控端（人可讀可改） |

> **一條工作流可以有多個 run；每個 run 一份私有狀態。**
> 定義是共用的，執行是各跑各的——這跟「場景可以有多個專案」是同一個形狀。

## 7. 一個場景能不能被多條工作流同時用

可以。**被佔用的不是場景，是對話。**

場景是檔案、是記憶、是邊界，它不是執行資源。真正在跑的是對話。所以「同一個場景被兩條工作流引用」沒有衝突——**兩條工作流各自開自己的對話。**

真正的衝突只有一個：**收尾時誰覆寫 `§〇`。**

| 做法 | 規則 | 評價 |
|---|---|---|
| **甲 · 序列化** | 同一場景同時只准跑一個 run，後來的要排隊 | 預設。簡單可靠 |
| **乙 · 寫入分離** | 可累積物走追加通道（`§五 決策與坑`，本來就是只追加）；`§₀` 覆蓋寫需仲裁 | 需要並行時才開 |

**甲為預設，乙為選擇性優化。** 乙的仲裁規則可以簡單到一句：**`§₀` 只由最後完成的那個寫，其餘把可累積物追加到 `§五` 即可。**

理由：`§₀` 的用途是「讓下一個對話知道現在狀態」，`§五` 的用途是「累積認識」。兩者用途不同，**衝突時保住 `§五`（累積）比保住 `§₀`（即時狀態）重要。**

> 順帶一提：`§五 決策與坑` 標著「只追加」——這條設計原本只是衛生習慣，
> 在新架構裡它變成了**主要的累積通道**。

## 8. 派單 vs 工作流

| | 派單 | 工作流 |
|---|---|---|
| 跳數 | **一跳** | **多跳** |
| 誰決定下一跳 | 人 | **工作流定義** |
| 中間資訊怎麼傳 | 下一跳自己去看 | **上一跳的可累積物** |
| 結束條件 | 一條回執 | 一條總回執（每一跳各有一條） |
| 人介入 | 每跳 | **只在門檻與失敗時** |

兩者不是競爭關係，是**同一個機制的兩種粒度**：

```
派單   ＝ 工作流的一步
工作流 ＝ 派單的串接，加上順序、分岔、失敗策略
```

## 8.5 這套東西有工具守著

規格寫得再好，沒有工具在管，它就只是一句請你記得。這部分有三支工具：

```bash
# ① 工作流定義合不合法
node 03-可執行工具/工作流校驗.mjs --root <工作台根>

# ② 跑：啟動 → 逐跳 → 收回執（★ 驗收不合格就擋下並就地停）
node 03-可執行工具/工作流執行.mjs start --root <工作台根> --工作流 <id>
node 03-可執行工具/工作流執行.mjs step  --root <工作台根> --run <run-id>
node 03-可執行工具/工作流執行.mjs 回執  --root <工作台根> --run <run-id> --回執 <檔>
node 03-可執行工具/工作流執行.mjs resume --root <工作台根> --run <run-id> [--門檻通過]

# ③ 回執單獨驗收（★ 含「可累積物有沒有落地到場景記憶」）
node 03-可執行工具/回執校驗.mjs --root <工作台根> --場景 <場景名> --回執 <檔>
```

端到端驗收（12 項，含故意弄壞）：

```bash
bash 03-可執行工具/工作流驗收.sh
```

> **這版執行器是離線的**：它不真的呼叫引擎，而是把每一步該做什麼寫成檔案並推進狀態機。
> 這是刻意的——**引擎中立**。引擎專用版只要把「產生派單」換成「真的派出去」，
> 狀態機與驗收邏輯完全沿用。

## 9. 失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 工作流卡住，没人知道卡在哪 | 沒有執行狀態檔 | 執行狀態要寫「卡在哪、等什麼」 |
| 壞了還繼續往下跑 | 沒有 fail-closed | 失敗即停，不靠人設 |
| 中間步驟設太多門檻 | 門檻濫用 | 只在不可逆／花資源／產出被當事實時設 |
| 兩條工作流互相覆蓋 `§₀` | 沒定序列化 | 甲為預設；並行時走乙 |
| 重啟後從頭再跑 | 執行狀態沒記完成步 | 每跳完成後在執行狀態裡標記 |
| 可累積物只寫在回執裡，沒落地 | 沒驗收 | `回執校驗.mjs` 會擋（落地驗收） |
| **run 停了之後接不回去** | 規格只寫「停下等人」，沒寫怎麼繼續 | `工作流執行.mjs resume` |

## 10. 一句話記住

> **工作流是場景的編排，不是程式。**
> **它住在共享層，狀態住在執行層；預設自動往前，門檻與失敗才停。**
