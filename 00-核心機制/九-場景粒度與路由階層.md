# 九 · 場景粒度與路由階層

> 這篇回答一個問題：**場景變多的時候，哪裡會先壞掉？**
>
> 原始動機是「場景越多 → 路由表越大 → 注入層越多 → token 浪費」。
> 實測下來：**token 那條不成立，路由那條成立。**
> 這篇把三件事拆開：哪些是真的瓶頸、哪些是真的誤解、以及怎麼設計才不會拆到一半。

---

## 一、先拆掉一個誤解：注入層不會隨場景數線性成長

### 誤以為

> 每個場景都要一份 `AGENTS.md`，每份都會被注入 → 24 個場景 = 24 份注入。

### 實測

引擎的注入路徑（`dsh-agent-instructions/lib/index.js`）：

```js
// :674
for (const dir of ancestorChain(projectRoot, cwd))
  for (const candidates of [config.instructionFileCandidates, config.localInstructionFileCandidates])
    for (const file of await allExistingInstructionFiles(dir, projectRoot, candidates, ...))
      addFile(file)
```

`ancestorChain(projectRoot, cwd)` = **從專案根走到 cwd 的那條路徑**，不是「所有專案」。

而 `projectRoot` 的定義是：**從 cwd 往上找第一個含 `.git` 的目錄**（`findProjectRoot`，:574）。

⇒ **一個會話只注入「它自己那棵樹」裡的 `AGENTS.md`，加上全域那一份。**

### 數字（2026-11-09 實測本機）

| 項目 | 字數 |
|---|---|
| 全域 `~/.dsh/AGENTS.md` | 921 chars |
| 24 個場景的 `AGENTS.md` 合計 | 33,451 chars |
| 單一場景平均 | 1,394 chars |
| **單會話實際注入量** | **≈ 2,315 chars**（全域 + 本場景） |
| （假設情境）24 場景全注入 | 34,372 chars ← **不會發生** |

**所以拆場景不會增加單會話的 token。** 反而會**減少**——因為每個小場景的 `AGENTS.md` 更小。

| | 注入量 |
|---|---|
| 一個大場景（`AGENTS.md` 2,000 chars） | 921 + 2,000 = 2,921 |
| 拆成三個小場景（各 600 chars） | 921 + 600 = **1,521** |

> **結論一：注入成本不是拆場景的理由，也不是不拆的理由。**
> 它是**每場景內部**的問題（`AGENTS.md` 該多短），不是**場景之間**的問題。

## 二、真正的瓶頸在哪：三個，不是一個

| # | 瓶頸 | 會隨場景數怎麼變 | 實測現況 |
|---|---|---|---|
| 1 | **路由表膨脹** | 線性 | 24 場景 / 348 關鍵字 / 平均 14.5 字／場景，最多「開發工具」30 字 |
| 2 | **每場景的登記成本** | 線性 × 4 處 | 每新場景要動 4 個地方（場景目錄、場景 json、身份索引、共享層）＋ 建常駐會話 |
| 3 | **每場景的 `check` 成本** | 線性 | 一次 `check --all` 要跑 24 場景 × 11 項 |

> **注意 #2 才是真正的重擔。** 拆一個 `影片剪輯` 成三個，等於多兩個場景目錄、
> 多兩條常駐會話、多 8 處登記、路由表多兩組關鍵字。
>
> **每場景的邊界成本是固定的，而場景的邊界成本 ≠ token 成本。**

## 三、那「更小的場景」該不該做？用累積判準回答

### 判準（來自[一-累積](1-accumulation.md)，全篇只有這一條）

> **這件事的價值，有沒有超過「它上次是怎麼做的」。**

### 拿「分離配音」這類案例套

| | 會反覆回來嗎 | 每次用同一批檔案／規則／知識嗎 | 累積得到什麼 | 結論 |
|---|---|---|---|---|
| 「幫我把這支影片的配樂關掉」 | 會 | 會 | **什麼都沒有**（一次性指令） | **不是場景** → 臨時執行體／技能 |
| 「影片剪輯流程」 | 會 | 會 | 分鏡規範、素材庫位置、字幕軸、發布檢查清單 | **是場景** |
| 「分離配音」 | 會 | 會 | 用哪個模型、參數怎麼調、哪種訊號會誤判、成品放哪 | **可能是場景**——但要問：這些累積跟影片剪輯的是同一批東西嗎？ |

### 關鍵追問

> **拆出來的這個小場景，累積的東西跟母場景是同一批嗎？**
>
> - **同一批** → 不該拆（拆了只是把記憶切成兩半，切口處兩個場景都要重述同一件事）
> - **不同批** → 該拆（它有自己的一套規矩、自己的檔案、自己的一堆坑）

「分離配音」的累積（模型選擇、參數、誤判型態）跟「影片剪輯」的累積（分鏡、字幕軸、發布檢查）**是不同批** → 從累積判準看，**該拆**。

### 但拆之前先看這三個失敗模式（[二-場景](2-scene.md) §4）

| 症狀 | 切錯在哪 | 修法 |
|---|---|---|
| 場景越來越多，每個都沒活 | 切太細 | 合併：用同一批檔案、同一個領域知識就該合 |
| 場景裡總在講別人的事 | 切太粗 | 拆開 |
| 場景要同時讀兩個目錄 | 邊界不對 | 一場景一 git 根，跨的那部分放共享層 |

## 四、架構層的空白：現在沒有「無記憶場景」這種東西

### 現有的三種型別

| 型別 | 有記憶嗎 | 有場景目錄嗎 | 有常駐會話嗎 | 備註 |
|---|---|---|---|---|
| **場景** | ✅ | ✅ | ✅ | 現在唯一的型別 |
| **視圖**（`"view": true`） | ❌ | ❌ | ❌ | 只讀呈現，見[場景戊規範](../02-落地實作/五-新場景規範.md) §B.3 |
| **臨時執行體**（sub-agent） | ❌ | ❌ | ❌ | 用完即棄，見[場景 vs 臨時執行體](../05-對照與選型/一-場景與臨時執行體.md) |

### 缺的那一格

使用者要的是：

> **有專屬技能、有路由入口、有自己的憲法，但「不需要記住上次做到哪」。**

這跟「視圖」不同（視圖根本沒有場景本體、不能干活），
跟「臨時執行體」不同（臨時執行體沒有專屬技能、每次重新組裝）。

**它叫「能力場景」或「無記憶場景」——這是這套架構目前沒有的一型。**

### 它的最小型別定義

| | 有 | 沒有 |
|---|---|---|
| `.git/` | ✅ **必須有**（否則技能不載入，症狀不明顯） | |
| `AGENTS.md` | ✅ 但要極短（它只講「我幹什麼、我不幹什麼」） | |
| `.dsh/skills/<id>/SKILL.md` | ✅ **這是它的主體** | |
| `定位卡.md` / `身份卡.md` / `場景畫像.md` | ✅ | |
| `場景私有記憶.md` | | ❌ **沒有**——因為沒有「上次做到哪」這件事 |
| `專案記憶/` | | ❌ |
| `歸檔/` | | ❌ |
| 常駐會話 | ✅（要能被打擾、接活） | |
| 四處登記 | ✅（它還是個能接活的場景） | |

**記憶去哪？** 兩條路，選一：

| | 落點 | 適合 | 代價 |
|---|---|---|---|
| **A. 母場景持有** | 子場景的 `AGENTS.md` 寫「我的記憶在 `影片剪輯/場景私有記憶.md`」 | 這活是母場景工作流的一步 | 跨場景讀記憶 → 破壞主權 |
| **B. 共享層持有** | `_共享記憶/` 下一份 `能力/<id>.md` | 這活不屬於任何單一場景 | 共享層只放「會影響別人」的東西，判準要重講 |

> **建議 A，並且明文化「只讀借用」**：子場景可以讀母場景的 §〇，但**回執寫回母場景**，不自己開記憶檔。
> 這樣記憶仍然只有一個真源（母場景），主權規則沒破。

## 五、關鍵機制：巢狀 vs 兄弟，差在 `.git` 有沒有

這是整篇最有用的一段，因為它決定「能不能繼承母場景的東西」。

### 引擎行為（實測 `dsh-agent-instructions` + `dsh-skill-filesystem`）

```
專案根 = 從 cwd 往上找第一個含 .git 的目錄
注入   = ancestorChain(專案根, cwd) 上的 AGENTS.md（由根往 cwd 逐層）
技能   = 只掃 <專案根>/.dsh/skills   ← 只有一層，不是整棵樹
```

### 三種放法，三種行為

| 放法 | 專案根 | 注入到的 AGENTS.md | 可見技能 |
|---|---|---|---|
| **兄弟**：<場景根>/音訊分離/（有 .git） | 音訊分離 | **只有** 音訊分離的 | 只有 音訊分離/.dsh/skills |
| **巢狀·無 .git**：<場景根>/音訊分離/（**沒有** .git） | **母場景** | **母場景 + 音訊分離 兩份**（鏈式） | 只有 母場景/.dsh/skills（**子場景的技能不可見**） |
| **巢狀·有 .git** | 音訊分離 | 只有 音訊分離的 | 只有 音訊分離/.dsh/skills |

### ★ 巢狀·無 .git = 天然的「借用母場景」機制

這就是使用者直覺裡的「記憶神經元」在引擎層的落點：

- **子場景的 `AGENTS.md` 會被鏈式注入到母場景的 `AGENTS.md` 之後** ⇒ 母場景的規矩自動繼承，不用重述
- **但子場景的專屬技能看不到** ⇒ 子場景的技能必須放進 **母場景的** `.dsh/skills/` 裡

**所以「小到不需要重複寫規矩」這件事，引擎已經原生支援了**，代價是技能要掛在母場景下。

**這條路省掉的是：重述母場景規矩的 token + 一份 4 處登記。**
**代價是：`check` 會擋（缺 `.git`）。** ⇒ 需要規格放行：**巢狀子場景是合法型別，`check` 要能分辨並放行。**

## 六、路由表：三個方案

### 現況

```json
{ "版本": 3, "路由": [ { "項目": ["簡報","簡報設計",...12 個], "owner": "簡報設計" }, ... ] }
```

**扁平結構，沒有群組、沒有階層。** 24 場景 / 348 關鍵字。

路由評分（`派單.mjs:1940-1990`）：

```
score = (動作詞 ? 1000 : 0) + 關鍵字長度 × 10 + 出現位置 / 1e6
然後：複合詞優先壓制（長關鍵字包含短關鍵字 → 短的被壓）
```

**關鍵限制：每個 owner 只能贏一次，路由表沒有第二層。**

### 方案 A：階層路由（路由表加一層）

```json
{ "路由": [
  { "項目": ["影片"], "owner": "影片剪輯" },
  { "項目": ["分離配音","去人聲"], "owner": "音訊分離" }
] }
```

加上：

```json
{ "群組": [
  { "id": "media", "項目": ["影片","音訊","配音","字幕"], "成員": ["影片剪輯","音訊分離"] }
] }
```

路由兩段：**先命中群組 → 群組內再比成員**。

**好處**：群組層的通用詞（「影片」）不會跟成員層的具體詞（「分離配音」）搶分。
**壞處**：路由表從 24 組變成「群組 + 成員」兩層，維護量不降反升。

### 方案 B：保持扁平，用複合詞優先機制解決（★ 推薦先做這個）

**現有的「複合詞優先壓制」已經能處理大部分情況**：

> 「分離配音」包含「配音」⇒ 若「配音」屬另一個 owner，「分離配音」勝。

**也就是說：新增一個小場景，它的關鍵字只要足夠具體，就會自動壓過母場景的泛用詞。**

實測案例（既有邏輯）：「每日簡報」壓過「簡報」、「排程發布」壓過「發布」。

**所以方案 B = 幾乎零改動**：
1. 新場景在路由表加一條，關鍵字寫**足夠具體**的複合詞
2. 確認沒有和既有 owner 搶字（用 `派單.mjs` 的歧義檢查）
3. 拿 `路由測試語句.json` 跑回歸

**這是成本最低、见效最快的一條路。**

### 方案 C：路由表自動分層（工具生成）

用關鍵字**包含關係**自動推導階層：若 A 的關鍵字集合 ⊇ B 的關鍵字集合，則 A 是 B 的上位。

**好處**：不用人手分層。
**壞處**：推導出來的階層可能不是你想要的職能分層（只是字面包含關係）。

## 七、實作順序（由小到大，每步可獨立驗收）

| 步 | 做什麼 | 驗收 |
|---|---|---|
| **1** | **釐清「能力場景」這個型別**——加進規格，定義有什麼／沒什麼、記憶歸屬、§〇 怎麼處理 | 規格文件 |
| **2** | **路由表升級成支援「能力場景」條目**（帶 `型別` 欄位） | `派單.mjs 路由` 對新條目行為一致 |
| **3** | **`check` 放行巢狀子場景**（無 `.git` 但有 `.git-marker` 標記） | `check --all` 綠 |
| **4** | **路由表複合詞回歸**（新增場景不搶既有 owner 的字） | `路由測試語句.json` 命中率不降 |
| **5** | **實作一個真例子**：音訊分離（或更小的） | 端到端派單 → 回執 → 落盤 |

---

## 八、三句話總結

1. **注入層不是瓶頸**——一個會話只注入自己那棵樹（≈ 2,315 chars），拆場景反而更省。
2. **真正的瓶頸是路由表與登記成本**——24 場景 / 348 關鍵字 / 每場景 4 處登記。
3. **「記憶神經元」在引擎層已經存在**——巢狀且無 `.git` 的子目錄會鏈式繼承母場景的 `AGENTS.md`，
   代價是技能要掛在母場景下、且 `check` 目前會擋。

> **要拆場景，理由是「累積的東西不同批」，不是「token 省」也不是「路由表大」。**
