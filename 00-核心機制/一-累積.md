# 一 · 累積 —— 能力不在模型裡，在累積裡

> 聰明是模型給的，本事是自己養的。
>
> 這篇是整套架構的主線：它先說清楚**主流多 Agent 框架錯在哪**，
> 再說清楚**要補哪一個載體**，最後說明那個載體長什麼樣。

---

## 1. 主流框架的前提

現在的多 Agent 框架，能力被假設成**模型聰明程度的函數**：

```
Agent 做得好不好 ≈ 模型夠不夠聰明
```

這個前提在單次任務裡沒問題。它出了問題，是在**同一類活要重複做很多次**的時候——而那正是多 Agent 系統存在的理由。

## 2. 三個症狀

### 症狀一：臨時執行體每次都從零開始

主流框架提供「臨時執行體」（sub-agent、task agent、子代理）來拆解任務。問題不在它做不做得成，而在**它做完之後什麼都沒留下**。

它留下的只有：這次任務的結論，和這次對話裡的 context。

**沒有事件歷史。** 它記的是「這角色是什麼」，不是「這件事上次怎麼做、踩過什麼坑」。

### 症狀二：經驗只活在當輪對話裡

臨時執行體的產出經驗預設只留在**那一輪的 context** 裡。session 一結束，它就蒸發了。

下次同類的活再來，臨時執行體被重新召喚、prompt 重新寫過，於是**從同樣的聰明程度重新出發**。中間那段該累積的經驗，沒有任何地方接得住。

> 症狀一與症狀二是同一件事的兩面：**沒有可被改寫的載體，累積就不可能發生。**

### 症狀三：技能愈多愈亂

另一條路徑是「用 skill」。但 skill 是**全域的清單**。

當全域掛了三十個 skill，索引塞進 context，Agent 看到的是三十個候選。它不知道該叫哪一個，也未必清楚各個 skill 到底是什麼——**能力越多，反而越挑不出能力。**

| | 症狀來源 | 本質 |
|---|---|---|
| 臨時執行體不累積 | 沒有載體 | 累積的問題 |
| skill 愈多愈亂 | 技能是全域清單 | **歸屬**的問題 |

兩者都被同一件事治：**讓能力住在對的範圍裡。**

## 3. 轉向：累積需要一個載體

要讓能力累積，載體必須同時滿足三個條件：

| # | 條件 | 缺了會怎樣 |
|---|---|---|
| **1** | **可被讀取** | 下一次拿不到累積，等於沒累積 |
| **2** | **可被改寫** | 只能追加不能修正，錯誤會永久累積 |
| **3** | **可被版本控制** | 改壞了回不來，累積變成負債 |

模型本身只滿足第 1 條的「推論出來」，第 2、3 條完全不成立。**模型不是載體，模型是引擎。**

> **判準：模型提供聰明，載體提供累積。兩者不可互相取代。**

## 4. 場景就是那個載體

這套架構把「一次會話」換成「一個場景」作為累積的單位：

```
場景 ＝ 一件事的長期本體
     ＝ 一個 git 邊界
     ＋ 一份可被改寫的記憶
     ＋ 幾個只屬於它的專屬技能
```

它滿足上面三個條件，而且是**用結構滿足**，不是用約定：

- **可讀**：每次開場先讀這個場景的 `§〇 當前交接`
- **可改**：記憶是 Markdown，人與 agent 都能寫
- **可版本控制**：每個場景是**獨立的 git 倉庫**，`git log` 全在

### 場景把「角色」變成「一段正在累積的歷史」

| | 臨時執行體 | 場景 |
|---|---|---|
| 身分 | 角色定義（可編輯） | 定位卡＋身份卡＋記憶 |
| 歷史 | **無** | 有（`§〇` 交接＋`§五 決策與坑`） |
| 存在的條件 | 被召喚的那一輪 | 不依賴任何一次呼叫 |
| 走掉之後 | 什麼都不剩 | 檔案還在，下次接得上 |

> **關鍵差別不是「能不能改」，而是「改了之後，那個改動有沒有地方留下」。**
> 臨時執行體的角色定義當然可以改——改完下一次召喚就用新的。
> 問題是它**沒有「這件事的歷史」**，所以每次改動都只是改掉設定，累積不出經驗。

### 專屬技能：把症狀三治掉

場景的技能是**掛在場景裡**的，不是掛在全域的。別的場景的技能，連清單裡都不會出現。

這不是把能力變少，是把能力**歸位**：

| | 全域 skill | 場景專屬技能 |
|---|---|---|
| 可見範圍 | 所有會話 | 只有本場景 |
| 索引成本 | 全部進 context | 只有本場景的進來 |
| 歧義 | 三十個候選，不知道叫哪個 | 幾個，明確 |

> **窄而深，比寬而全更準。** 這是這套架構在能力面唯一的主張。

## 5. 記憶在檔案裡，是累積的前提

> 記憶在檔案裡，不在會話裡 —— 這是累積能發生的前提。

場景記憶的 `§〇 當前交接`（≤ 4 KB，覆蓋寫）就是累積的介面：

- 每次**開場**讀它 ⇒ 下一次從累積開始
- 每次**收尾**覆寫它 ⇒ 這次的進度留給下一次
- `§五 決策與坑`（只追加）⇒ 認識本身會累積

而「開一個新對話」這個動作，就是**傳遞累積的動作**。新對話開場時先讀 `§〇`，所以換對話不等於歸零——**只要交接寫了。**

## 6. 累積的迴圈

整套機制的閉環在這裡：

```
① 派活          一次派單 ＝ 一條回執
② 執行          讀 §₀ 開場（帶著上次的累積）
③ 回執          三件套：差異集合 · 可累積物 · 下一棒
④ 寫回          可累積物落進場景記憶（場景自己寫，主控端只驗）
⑤ 下次          從累積開始
```

**第 ④ 步是整個迴圈的重點。** 沒有它，前三步只是把活做完；有了它，下一次才不用從頭。

> **新紅線：沒有可累積物的回執 ＝ 這次活白做。**
> （對應既有的「活幹完了但對方還不知道 ＝ 沒幹完」）
>
> 兩條紅線擋的是同一類病：**做了，但沒留下。**

## 7. 誰在累積：主控端與臨時執行體

分工是明確的：

| 角色 | 定位 | 累積發生在哪 |
|---|---|---|
| **主控端** | 持有場景的那個 agent／工作台 | **在它的場景裡**（記憶＋專屬技能＋邊界） |
| **臨時執行體** | 一次性派工（sub-agent 這類） | **不在它身上**——它的產出要由主控端收下並寫回場景 |

臨時執行體是**用完即棄**的，這不是缺陷，是定位。它不需要被進化；它需要的是**做完了把可累積物交回來**。

這是整套架構與主流框架最尖的一處分歧：

> **臨時執行體是可以被改寫的，但它沒有累積的載體。
> 場景是累積的載體，而場景通常是由主控端持有、由主控端改寫的。**
>
> 所以「累積」這件事，只能發生在主控端。

## 8. 失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 同類活做第二次還是從零開始 | 沒有交接，或交接沒寫 | 換會話前必寫 §〇；check 不過不許換 |
| 累積下來的是錯的 | 載體只能追加不能修正 | 場景記憶是 Markdown，可改；`§五` 只追加但可標註「已作廢」 |
| 技能愈挂愈多、愈挂愈亂 | 技能放全域 | 場景專屬技能；全域只留通用做法 |
| 累積長得比場景記憶快 | 沒有體量紅線 | `§〇` 4 KB / 主檔 25 KB，超了搬歸檔 |
| 可累積物只寫在回執裡，沒落地 | 回執與記憶是兩個地方 | 主控端驗收時**讀場景記憶確認那條真的落地** |

## 9. 一句話記住

> **能力不在模型裡，在累積裡。**
> **場景是累積的載體，工作流是場景的編排，回執的可累積物是累積的燃料。**
