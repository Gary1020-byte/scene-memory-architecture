# 二 · 工作流地圖

> **這篇回答一個很实际的問題：我手上有哪些工作流要搭？每條要配哪些場景？**
>
> 判準與規格在[五-工作流](../00-核心機制/五-工作流.md)；這裡是**具體清單與優先順序**。
> 引擎中立；引擎端的落地記錄見 `<工作台根>/`。

---

## 一、判準：什麼算「一條工作流」、什麼算「一個場景」

| | 場景 | 工作流 |
|---|---|---|
| 身份 | **長期本體** | **場景的編排** |
| 邊界由 | **職責**決定 | 交付物決定 |
| 壽命 | 一直在 | 每次跑一條新的 run |
| 判準 | 這類活會**反覆回來**，而且每次都用到同一批檔案、同一套規矩、同一個領域的知識 | 兩條以上場景之間**有可傳遞的東西** |

> ★ **場景與工作的差別**：場景長期存在；工作有明確結束點。
> **專案記憶放在場景底下**——專案結束，場景還在。

---

## 二、目前的五條工作流

### A · 素材 → 簡報／報告頁 → 旁白稿 → MP4 → 驗收 ✅ 已建

| | |
|---|---|
| 場景 | `場景己`（`sc-f`）、`場景庚`（`sc-g`） |
| 工作流定義 | `工作流/簡報到影片.yaml` |
| 規格 | [八-內容到鏡頭規格](../02-落地實作/八-內容到鏡頭規格.md) |
| 實測案例 | `ai-agents-report`（2026-10-27，4:30、繁中配音＋字幕、−16 LUFS） |
| 狀態 | 場景已建、工作流已定義、規格已被實測核對過一輪（v1.3） |

**這條鏈的關鍵認知（實測得出）**：

> **影片不是從報告 HTML 轉出來的。** 兩條線共用**素材**（`content.md`）與 **design token**，
> **不互相轉換**——轉換會有損（報告頁的表格塞不進 1080p、影片的節奏在單頁裡不成立）。

### B · 課程學習 🟡 共用前置已建

| 場景 | 狀態 | 說明 |
|---|---|---|
| `考古題庫`（`exam-bank`） | ✅ 已建 | **跨課共用**：範圍 → 題型地圖 → 題庫 → 公式閃卡 → 逐題複盤 |
| 各課場景（科目甲～戊） | 🔜 待建 | 每門課＝一個場景（該課的領域記憶、進度、考古題） |

> ★ **每一門課對應一個 teaching skill，它本身就是場景的原型。**
> 每門課＝一個場景（該課的領域記憶、考古題、公式表、考古題型地圖）。

**為什麼把「考古題庫」抽成跨課共用的一個場景**：考古題是**跨課但同一套規矩**的活
（範圍→地圖→題庫→複盤）。放進各課程場景，會讓每門課各做各的、地圖格式就不一致了。

**要做的**：把進度檔從 vault 遷成場景的 `專案記憶/`，
並讓每個場景的 §五 收「考古題型地圖」（哪幾題沒做、哪些章節本學期不考）。

> ★ 考試範圍**要重新核對**，不要沿用舊筆記——停課（颱風假）會讓課程順序順延。
> 實測：資料結構舊筆記把 Hash Tables 列為考前，實際順延到 11/13 → 不在範圍內。

### C · 每日輸入 → 詞彙 → 複習 🟡 場景已存在

| | |
|---|---|
| 場景 | `英語學習`（**已存在**） |
| 工具 | `英文輸入` skill（每天 07:05 抓文章 → 推播 → 回報 → 寫入 vault）、`英文口說` skill |
| 要補的 | 場景記憶裡要收「低摩擦動作」（讀 3 句 ＋ 記 1 個字）、觸發時機、詞彙寫入規則 |

### D · 每日簡報 → 推播 ✅ 已建

| | |
|---|---|
| 場景 | `每日簡報`（`daily-digest`）✅ |
| 工具 | `productivity/scheduled-digest-pipeline` skill、`daily-brief-bot`（公開 repo）、digest dashboard（khroma 四色）、Hermes cron（4 條相關） |
| 判準 | **它有自己的一套規矩（版式、配色、推送時機、來源清單）**，所以獨立成場景——不是 A 的 `簡報設計` 的一個專案 |

**兩條紅線**：① 輸出永遠是**純文字**（信箱不渲染 markdown）；② **排程失敗要講**，不要默默跳過。

### E · 產品發布（repo 稽核 → 公開）✅ 已建

| | |
|---|---|
| 場景 | `產品發布`（`release`）✅ |
| 工具 | `public-repo-hygiene` skill、`software-development/github-project-development` skill（八階段方法論） |
| 要做的 | 方法論已在 repo；場景已把「稽核清單」變成可累積的記憶。**剩下的**：把清單做成可重跑的腳本 |

**★ 這條鏈上最重要的一句話**：**force-push 之後，舊 commit 與舊 blob 仍然可以透過
GitHub API 讀取。**「已 force-push」≠「已不可逆移除」——不可逆移除需要 GitHub Support
清除快取，或刪除並重建 repo（不可逆，要問過機主）。

### F · 觀測（把傳遞機制看見）✅ 已建

| | |
|---|---|
| 場景 | `主控端`（`master`）✅ |
| 介面 | `dsh-scene-workbench`（公開 repo）——DSH 原生 Cordis client plugin，右側 sidebar 的兩個分頁 |
| 這條鏈的產出 | 3D 記憶神經元總覽：節點＝場景／私有記憶／共享文件，**連線＝跨場景派單與回執的實際流向** |
| 界線 | **主控端是觀測站，不是第二個路由者**——路由本體在 repo 的 `路由.mjs` ＋ `路由表.json` |

## 三、優先順序

| 優先 | 工作流 | 狀態 | 理由 |
|---|---|---|---|
| **1** | **A 簡報→影片** | ✅ 已建 | 你自己說最想優先；鏈的接縫最清楚（素材是共同語言）；已被實測核對過 |
| 2 | **B 課程學習** | 🟡 共用前置已建 | 各課場景的原型現成（skill 就是雛形），但**進度檔分散在 vault**，要先遷 |
| 3 | **C 每日輸入** | 🟡 場景已存在 | cron 已在跑，缺的只是把它變成場景＋回執 |
| 4 | **D 每日簡報** | ✅ 已建 | 版型與推送時機自成一規則，獨立成場景 |
| 5 | **E 產品發布** | ✅ 已建 | 方法論已在 repo；場景把稽核清單變成可累積記憶 |
| **6** | **F 觀測（3D 總覽）** | ✅ 已建 | 讓傳遞機制看得見；路由本身仍在 repo |

## 四、建場景前必問的三個問題

| # | 問題 | 為什麼 |
|---|---|---|
| 1 | 這件事會**反覆回來**嗎？ | 一次性任務不該開場景（做一次就結束的活，開了場景只是增加維護負擔） |
| 2 | 它用到的是**同一批檔案、同一套規矩**嗎？ | 同一套規矩才值得累積成記憶；否則只是又一個目錄 |
| 3 | 它和現有場景的**職責邊界**在哪？ | 邊界不清 ⇒ 兩個場景會互相改對方的記憶，最後誰都不敢信 |

> ★ **第 3 問最容易踩。** A 的兩條線共用素材，但它們**不互相轉換**——
> 如果當初沒想清楚，就會長成「一個場景包辦全部」，
> 然後場景記憶裡混了兩種東西，誰也讀不動。

## 五、每條工作流建完之後要驗的

| # | 驗收 | 工具 |
|---|---|---|
| 1 | 場景四處登記一致 | `一致性稽核.mjs` |
| 2 | 場景 check 全綠 | `場景記憶.mjs check --all` |
| 3 | 工作流定義通過校驗 | `工作流校驗.mjs` |
| 4 | **鏈真的跑得動，而且跑的是有意義的活** | `鏈式呼叫.mjs --任務` |
| 5 | **每棒有可累積物落盤** | 看場景的 `專案記憶/` |

> ★ **第 4 與第 5 才是「工作有意義」的證據。**
> 前三項全綠但第 4 項只回「未開始任何操作」——
> 那叫**空轉**，不叫跑通。
