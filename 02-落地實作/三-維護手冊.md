# 三 · 維護手冊 —— 三個月後要改架構時，看這篇

> **這篇是寫給「回來維護」的那個人的。**
> 目標：任何一次架構調整，都有標準流程、能驗、能回滾，而且**不會靜默地壞掉**。

---

## 0. 先讀這三句

1. **先盤點現況再設計。** 動手前先把現有的讀一遍——包括你以為已經存在的部分。
   （教訓：曾經推廣一套 SDK 方案，結果對方早就自己寫好了一條更合適的路，
   還更好用。**看到官方有 ≠ 那就是更好的做法。**）
2. **每個值只准有一份定義。** 規則、紅線、路徑、索引位置——任何一個東西只准有一個真源。
3. **改完要能驗證「該失敗時會失敗」。** 只看到「正常情況通過」不算數。

---

## 1. 改架構的標準流程（五步）

```
① 盤點 ──▶ ② 定義變更 ──▶ ③ 遷移 ──▶ ④ 驗證 ──▶ ⑤ 記錄
```

### ① 盤點（不寫程式）

先回答這四個問題，**寫下來**：

| 問題 | 為什麼要問 |
|---|---|
| 這個值/規則現在定義在哪幾處？ | 有兩處以上 ⇒ 遲早分叉 |
| 誰在讀它？ | 讀的人沒改 ⇒ 改了等於沒改 |
| 改了之後，舊資料還合法嗎？ | 決定要不要遷移 |
| 出問題時怎麼回滾？ | 沒有回滾方案就不要動 |

> **產出：一張「誰定義／誰讀／怎麼遷」的表。**
> 這張表是後面所有步驟的地基，別跳過。

### ② 定義變更（先寫規則，再寫程式）

- 規則寫進**單一來源**（本架構用 `交接規則.json`）。
- 程式**只讀這份規則**，不自己硬編碼。
- 規則改動本身要版本化（見第 3 節）。

### ③ 遷移（先快照，再動手）

```
① 先存一份「搬之前」的快照          ← 沒這步，後面無法證明沒丟東西
② 跑遷移
③ 跑核對腳本：逐行比對「搬前非歷史行 == 搬後非歷史行」
      命中 0 差異 ⇒ 才算沒丟
④ 跑索引體檢：死條目 / 未登記 / 過期 / 身分漂移
```

> 真實教訓：有一次沒存快照就動手拆，結果**核對腳本根本跑不了**——
> 你無法證明自己沒丟東西。從那以後規矩改成：**先快照，再動手。**

### ④ 驗證（雙軌）

| 軌 | 內容 |
|---|---|
| **正例** | 正常資料應該通過 |
| **反例** | 故意弄壞，必須被擋下（見[二-交接與校驗](二-交接與校驗.md)第 6 節 V1–V8） |

**只有正例通過 = 沒驗證。** 反例必須真的被擋。

### ⑤ 記錄

- 改動寫進 [`更新清單.md`](../更新清單.md)（本機版）或 git commit message；
- 新的規則寫進對應的機制篇；
- 踩到的坑寫進 [`四-已知裂縫與待修`](四-已知裂縫與待修.md)。

## 2. 常見維護任務的具體做法

### 任務 A：加一個新場景

```
① 場景/ <新場景名>/.git init          ← 先有邊界
② 拷 04-模板/ 的：場景私有記憶.md、定位卡.md、身份卡.md、場景畫像.md
③ 改定位卡：場景 id、名稱、面板路徑、專屬技能
④ 場景/ <新場景名>/AGENTS.md          ← 場景憲法
⑤ 場景/ <新場景名>/.dsh/skills/<場景id>/SKILL.md
⑥ 在 _場景身份索引.md 加一行
⑦ 跑：場景記憶.mjs stamp --場景 <新場景名>
⑧ 跑：場景記憶.mjs check --場景 <新場景名>   ← 必須全綠
⑨ 建常駐會話，釘住，回填 sessionId（見任務 B）
```

**驗收標準**：切到新場景，AI 看到的技能清單只有新場景自己的那幾個。

### 任務 B：換一條會話

```
① 覆蓋寫 §〇 當前交接（進度 / 下一步 / 卡點）
② 建新會話，舊會話歸檔
③ 同步三處：場景配置 sessionId / 身份索引會話 id 欄 / §〇 交接署名
④ 場景記憶.mjs stamp --場景 <名>       ← 重蓋身份卡
⑤ 場景記憶.mjs check --場景 <名>        ← 必須通過
```

> 第 ③ 步漏了任何一處 ⇒ 面板指向舊會話 ⇒ 「AI 像換了個人」。

### 任務 C：改紅線（比如 §〇 從 4 KB 改成 8 KB）

#### 先想清楚：改紅線不是改數字，是改一個行為門檻

動手前先回答這四個問題，**寫下來**：

| 問題 | 為什麼要問 |
|---|---|
| **現在有多少資料超標？** | 超標的資料要嘛瘦身，要嘛接受它們永遠過不了檢查 |
| **紅線存在的理由還成立嗎？** | 4 KB 的理由是「30 秒讀得完」。如果場景性質變了（例：從「派活」變成「深度研究」），理由可能變了；**如果理由沒變，就別動數字** |
| **放寬之後，誰會付代價？** | 代價是**新會話要讀更多**。放寬 4 KB → 8 KB ＝ 開場成本翻倍 |
| **放寬之後，這條紅線還擋得住任何東西嗎？** | 如果沒有任何場景的 §〇 會超 8 KB，這條紅線就已經是裝飾了——**裝飾比沒有更危險** |

> ★ **紅線不是「大概別寫太多」，它是一個明確的門檻。**
> 放寬紅線之前先確認：**你要放寬的是「門檻」還是「懶」？**
> 如果是懶，正確的動作是減肥，不是放寬。

#### 動手：改哪幾處（規則單一來源）

```
① 改交接規則.json 的 sec0MaxBytes          ← ★ 規則單一來源，只改這裡
② 確認工具讀的是這份規則（不是自己硬編碼）
③ 找出現有資料：哪些 §〇 超標？逐一手動瘦身或搬歸檔
④ 跑 check --all，確認報告一致
⑤ 更新 04-模板/ 裡的骨架（工具生成 §〇 時會用新值）
⑥ 更新文件裡所有提到 4 KB 的地方
```

> ⚠️ **第 ⑥ 步別跳。** 紅線數字散落在文件、模板、工具三處，
> 改一處就會出現「文件說 4 KB、工具擋 8 KB」的不一致——
> 這正是[二-交接與校驗](二-交接與校驗.md)第 7 節講的病。

#### ⚠️ 改完一定要做的兩步自檢（否則你不知道有沒有生效）

```bash
# ① 看工具自報的規則來源，確認讀的是你改的那份
node 03-可執行工具/場景記憶.mjs list --root <工作台根>
#    輸出：規則來源：<路徑>   ← 這要是你改的那個檔案

# ② 故意灌爆交接段，看報的紅線數字是不是新值
#    期望：「§〇 N B 超 8 KB（紅線 8192）」而不是 4096
```

> **這兩步不做，等於沒改。**
> 本 repo 就有這個實例：`04-模板/交接規則.json` 用中文鍵名
> （`交接段紅線位元組`），工具認的是英文鍵（`sec0MaxBytes`）——
> **檔案被讀到了，值卻沒生效，而且沒有任何錯誤訊息**。
> 完整實測見[二-交接與校驗](二-交接與校驗.md)第 7 節。

### 任務 D：改場景劃分（合併／拆分場景）

```
① 盤點：兩個場景各自有什麼（記憶、專案、技能、會話）
② 決定：記憶檔併到哪一份？專案記憶怎麼遷？
③ 快照兩邊的記憶檔
④ 合併 §〇（不是拼接，是重寫成一份新的交接）
⑤ 遷移專案記憶檔，保留原檔名
⑥ 刪掉舊場景的 git 倉庫前，★ 必須先 commit + 打包備份
⑦ 更新身份索引、路由表
⑧ 跑 check --all
```

> ⚠️ **第 ⑥ 步是一條硬關卡。**
> 刪掉一個場景時，裡面有未提交的修改 ⇒ **當場丟失，沒有備份**。
> **刪任何場景之前，先 commit，再打包。** 沒有例外。

### 任務 D2：退役一個場景（長期沒活的那個）

**判據**：半年後還會為它單獨開一個視窗嗎？答不出來就退役。
退役**不等於刪除**——它是「保留記憶與索引，讓它不再占著位置」。

```
① 盤點：這個場景還有什麼未完成的活？搬到哪裡去？
② 把沒做完的活搬到接收它的場景（或標記為「已擱置，待機主拍板」）
③ 跑場景記憶.mjs 交接 --場景 <名>     ← 產生最後一份歸檔快照
④ ★ git commit（場景倉庫裡的未提交內容）
⑤ ★ 打包備份：<工作台根>/.歸檔/<場景名>-<時間戳>.tar.gz
⑥ 從身份索引刪掉那一行
⑦ 從場景配置刪掉 <場景id>.json
⑧ 從共享層刪掉該場景的條目（areas／索引／項目表）
⑨ 歸檔會話（引擎若有 archiveSession 之類的 API）
⑩ 跑 check --all，確認剩下的場景全綠
```

**刪除前的檢查清單（逐項打勾，一項都不能跳）**：

```
□ git status 乾淨？（不乾淨 ⇒ 先 commit 或 stash）
□ 已打包備份？（路徑：<工作台根>/.歸檔/<場景名>-<時間戳>.tar.gz）
□ 場景記憶已匯出成單檔？（交接快照在 歸檔/ 裡）
□ 裡面沒有別人依賴的專案記憶？
□ 身份索引、場景配置、共享層三處都清乾淨了？
```

> ⚠️ **git 只保護已經 commit 的東西。**
> 「有版本控制」不等於「不會丟」——未提交的部分，一刪就沒。
>
> **實測（2026-10-31）**：一個場景被刪時，裡面有 **2 個未提交修改 + 2 個未追蹤檔案**，
> 刪除後**當場遺失，沒有備份**。
> 另註：那次刪除後，`場景記憶.mjs list` 只認 `場景/` 下的目錄 ⇒
> **刪目錄即退場，不需要改引擎**。

### 任務 E：升級引擎

```
① 先看引擎版改了什麼行為（尤其：專案根判定、技能掛載、指令注入）
② 在測試場景上重建一個會話，跑隔離驗證（見下）
③ 對比：新舊引擎下，場景看到的技能清單是否一致
④ 確認 §〇、身份卡、場景畫像的生成邏輯有沒有變
⑤ 升級後立刻跑 check --all
```

**隔離驗證怎麼做**（這是驗「換場景＝換腦子」到底成不成立的實測）：

```
① 在每個場景目錄建一條臨時會話，跑一輪探針問題
② 在一個「非場景目錄」建一條臨時會話，同樣跑探針 —— 做對照組
③ 探針問三題（不許調工具，只根據上下文回答）：
     ① 你的工作目錄是什麼？
     ② 你能看到的技能清單（只列名字）
     ③ 你的上下文裡有沒有《場景憲法》？有就抄一級標題
④ 對比各場景回答：該看到的技能看到了嗎？不該看到的有沒混進來？
⑤ 全部清理（cancel + archive），不留側邊欄
```

> **對照組是關鍵。** 沒有對照組，你無法區分「隔離生效」和「它本來就看不到那些技能」。

## 3. 版本化：規則與架構怎麼記版本

| 東西 | 版本化方式 | 理由 |
|---|---|---|
| 場景記憶 | 每次交接產生一份 `歸檔/` 快照（時間戳 + 會話前 6 碼） | 快照即版本 |
| 場景倉庫 | 各自的 git 倉庫 | `git log` 就是完整歷史 |
| 工具 | git 倉庫 | —— |
| 規則（交接規則.json） | 檔內 `version` 欄位 + git | 改紅線是重大變更 |
| 定位卡 | `定位卡版本：N` 欄位 | 工具可據此判斷要不要重蓋 |
| 全域憲法 | 版本號 + 舊版留檔 | 改一次 +1 |

> **規則版本欄位不是裝飾**：當工具要遷移舊資料時，
> 它需要知道「這份資料是照哪版規則生成的」。

## 4. 回滾：每個變更都要有退路

| 變更類型 | 回滾方式 |
|---|---|
| 記憶內容 | `git checkout` / 從 `歸檔/` 撈快照 |
| 工具改版 | 工具倉庫 `git revert` |
| 規則改版 | 規則檔版本欄位 + git |
| 場景合併／拆分 | 刪除前必須 commit + 打包（**硬規定**） |
| 引擎升級 | 保留舊版引擎目錄，不覆蓋 |

> **「可以回滾」和「已經驗證可以回滾」是兩件事。**
> 真要回滾時才第一次發現回不來，就太遲了——
> **每次大改之後，實際演練一次回滾。**

## 5. 維護時最容易犯的六個錯

| # | 錯 | 後果 | 防範 |
|---|---|---|---|
| 1 | 看到官方方案就直接用 | 推了 SDK，結果對方早就寫好更合適的 | **先盤點現況** |
| 2 | 同一規則寫在兩處 | 看板分裂、訊息靜默丟失 | **規則單一來源** |
| 3 | 只驗正例 | 檢查器看起來很安全，其實不擋任何東西 | **反例驗收** |
| 4 | 刪場景前沒 commit | 未提交內容當場丟失 | **先 commit，再打包** |
| 5 | 改紅線只改工具沒改文件 | 文件與行為不一致 | 紅線改動要三處同步 |
| 6 | 以為「有可觀察落點」就等於生效 | 寫了，但寫到沒人看的地方 | **看落點的時間戳有沒有動** |
| 7 | 改了規則檔就當作生效 | 值沒被讀到，但沒有任何錯誤 | **看 `list` 自報的「規則來源」** |

## 6. 每次改完要跑哪幾個驗收

**這張表是「改完了」的定義。** 沒有跑完，change 就沒完成。

| # | 驗收 | 場景甲 | 通過的判據 |
|---|---|---|---|
| **A1** | 全場景結構 | `場景記憶.mjs check --all --root <工作台根>` | 退出碼 **0**；每個場景「✓ 全部通過」 |
| **A2** | ★ 反例驗收 | `bash 03-可執行工具/反例驗收.sh` | **10 通過，0 失敗**（證明檢查器還會擋） |
| **A3** | ★ 規則來源 | `場景記憶.mjs list --root <工作台根>` | 印的「規則來源」是**你改的那個檔案** |
| **A4** | 紅線邊界 | 故意灌爆交接段 | 報的紅線數字 = **你改的新值**（不是舊值） |
| **A5** | 內部連結 | `node 03-可執行工具/檢查連結.mjs` | 「✓ 全部連結有效」 |
| **A6** | 隔離 | 探針問卷（任務 E 第 2 步） | 該看到的技能看到了，不該看到的沒混進來 |
| **A7** | 回滾 | 真的回滾一次 | 能回到改動前的狀態 |
| **A8** | 記錄 | 更新清單 + 已知裂縫 | 兩邊都有你這次的紀錄 |

> ⚠️ **A2 與 A3 最容易被跳過，而它們最要命。**
> - **A2 跳過** ⇒ 你不知道檢查器是不是還會擋（它可能壞掉而且一直回 0）。
> - **A3 跳過** ⇒ 你不知道你改的紅線有沒有生效（檔案被讀到了但鍵名對不上時，**不會有任何錯誤**）。
>
> **A2 和 A3 加起來的執行時間是幾秒鐘，但它們決定了前面所有工作是不是真的做完了。**

**依變更類型選要跑哪幾項**：

| 變更類型 | 必跑 |
|---|---|
| 只改文件 | A5 · A8 |
| 改紅線／規則 | A1 · A2 · A3 · A4 · A8 |
| 改工具 | A1 · A2 · A8 |
| 加／刪／合併場景 | A1 · A2 · A3 · A7 · A8 |
| 升級引擎 | 全部（A1–A8） |

## 7. 什麼時候該停下來找人確認

以下四種情況，**不要自己決定**：

| 情況 | 為什麼 |
|---|---|
| 要刪任何場景或目錄 | 不可逆 |
| 要改紅線（4 KB / 25 KB 這類） | 影響所有既有資料 |
| 要合併場景（記憶會搬家） | 涉及所有權歸屬 |
| 要改全域憲法 | 全域規則只認機主 |

> 這條是整套架構裡少數「機械不變量」之外的：**主權規則本身也要有人守。**

## 8. 維護前的自我檢查清單

```
□ 我讀過 [二-交接與校驗](二-交接與校驗.md) 的反例驗收表
□ 我盤點了「這個規則定義在哪幾處」
□ 我確認了「誰在讀它」都會一起改
□ 我有「搬之前」的快照
□ 我寫了正例 + 反例兩組驗證
□ 我確認過回滾方式（且演練過）
□ 我更新了文件裡所有受影響的數字
□ 我把新踩到的坑寫進 [四-已知裂縫與待修](四-已知裂縫與待修.md)
□ 我更新了 [更新清單.md](../更新清單.md)
```
