# 五 · 場景戊規範

> **一個標準場景＝目錄內 10 項 ＋ 場景外 3 處登記。**
> 這篇是那 10＋3 的條文化，以及「從零到能用」的十步與每步的驗收標準。
>
> **這篇的目標不是讓你讀完記住，是讓你照著做完就對。**
> 每一步都有機械驗收——`check` 會擋，所以不必靠記。

---

## 零、先問：這件事該不該開一個場景

**判準（一條就夠）**：這類活**會反覆回來**，而且**每次都用到同一批檔案、同一套規矩、同一個領域的知識**。

| ❌ 不該開場景 | ✅ 該開場景 |
|---|---|
| 「今天做影片」—— 一次性任務 | 「影片工作流」—— 每次做片都要用到分鏡規範、素材庫、發布檢查 |
| 「一個專案」—— 有明確結束點 | 「場景丁」—— 每週都會回來，永遠不會結束 |
| 按工具分 —— 一個工具一個場景 | 按職能分 —— 一段職責一個場景 |

### 場景 vs 專案的差別（最容易搞混）

| | 場景 | 專案 |
|---|---|---|
| 生命週期 | 長期存在 | 有明確結束點 |
| 邊界 | 由**職責**決定 | 由**交付物**決定 |
| 記憶歸屬 | 場景擁有 | 專案記憶放在**場景底下** |
| 例子 | 場景丁 | 「2026 年 10 月電路學講義考古」 |

> **一個場景底下可以有多個專案；專案結束，場景還在。**

### 場景 vs 臨時執行體（sub-agent）

| | 臨時執行體 | 場景 |
|---|---|---|
| 存在條件 | 被召喚的那一輪 | **不依賴任何一次呼叫** |
| 有沒有事件歷史 | **無** | 有（`§〇` 交接 ＋ `§五` 決策與坑） |
| 走掉之後 | 什麼都不剩 | 檔案還在，下次接得上 |
| 什麼時候用 | 一次性查詢、獨立探索、互不相干的並行 | **會反覆回來的活** |

> **判準一句話：這件事的價值，有沒有超過「它上次是怎麼做的」。**
> 沒有 → 臨時執行體。有 → 場景。

## 一、標準場景的規格

### A. 場景目錄內（`場景/<場景名>/`）

| # | 項目 | 誰寫 | 作用 | `check` 會驗 |
|---|---|---|---|---|
| 1 | `.git/` | `git init` | **場景邊界**：引擎靠它判定專案根，決定哪些憲法會被注入、哪些專屬技能可見 | ✅ 缺了會擋 |
| 2 | `AGENTS.md` | 人 | **場景憲法**：我是誰、職責邊界、記憶規則、換會話協議、跨場景規矩 | — |
| 3 | `.dsh/skills/<場景id>/SKILL.md` | 人 | **場景專屬技能**：開場怎麼接手、怎麼幹活、怎麼寫回、怎麼交接 | — |
| 4 | `定位卡.md` | 人 | **身分說明書**：場景 id／名／面板路徑／記憶目錄／專屬技能 —— **校驗的指紋來源** | ✅ 存在 ＋ 指紋一致 |
| 5 | `場景私有記憶.md` | 人 | **記憶真源**（唯一） | ✅ 存在 ＋ 有職責塊 |
| 6 | `身份卡.md` | **工具** | 身分／權限／卡指紋 —— ⛔ 手改即校驗失敗 | ✅ 存在 |
| 7 | `場景畫像.md` | **工具** | 面板布局／渲染器／依賴，由場景定義推導 | ✅ 存在 |
| 8 | `_檔案索引.md` | 人 | 檔案清單，四態：`活 / 常備 / 留檔 / 待清` | ✅ 存在 |
| 9 | `專案記憶/` | 人 | 一專案一份，≤ 8 KB | ✅ 存在 |
| 10 | `歸檔/` | 人／工具 | 交接前快照，只進不改 | ✅ 存在 |

### B. 場景外（場景自己管不到，必須另外登記）

| # | 項目 | 位置 | 誰寫 | `check` 會驗 |
|---|---|---|---|---|
| 11 | **場景定義**（面板） | `<工作台根>/工作流…` 之外的引擎側目錄（見引擎端說明） | 人 | ✅ 會話已綁定 |
| 12 | **身份索引一行** | `場景/_場景身份索引.md`（7 欄對齊） | 人 | ✅ 有這張卡 |
| 13 | **一條常駐會話**（cwd ＝ 場景目錄） | 引擎 | 引擎 | ✅ 會話在 session 庫裡 |

> **第 11–13 項最容易被漏。** 因為它們不在場景目錄裡，`ls` 場景目錄看不出來少了什麼。
> 所以 `check` 把它們也算進去——**少一項就會報錯，而不是等三個月後發現場景叫不動。**

### C. `場景私有記憶.md` 的固定結構

```
## §〇 當前交接（≤ 4 KB，新會話先讀這一節）
  ### 1) 上次交接        —— 上次幹到哪、產出在哪
  ### 2) 當前專案        —— 表格：專案 / 記憶檔 / 狀態 / 下一步
  ### 3) 私有記憶變更    —— 這次改了什麼、為什麼
  ### 4) 下一步 / 卡點    —— 誰先動、按什麼順序；卡住就寫清等誰
  ### 5) 全貌            —— 工具生成
## 核心職責             ← 至少 3 條
## §一 我管什麼 / 不管什麼
## §二 幹活入口
## §五 決策與坑（只追加）  ← ★ 可累積物的落點
## 〇-通知               ← 跨場景留言的收件處
```

**§〇 只回答四個問題**：我是誰／幹到哪／下一步／卡在哪。
寫成週報是最常見的錯法——超線，而且新會話讀完仍然不知道下一步該幹什麼。

## 二、十步流程

### 步驟 0：判斷該不該開場景

見 [§零](#零先問這件事該不該開一個場景)。**不要跳過這步**——開錯場景比不開場景更貴。

### 步驟 1：決定三個名字

| 名字 | 例 | 規則 |
|---|---|---|
| **場景 id** | `sc-e` | 英文 kebab-case；**同時**是專屬技能目錄名與場景定義檔名 |
| **場景名** | `場景戊` | 中文；面板顯示用，也是身份索引的「會話名」 |
| **場景目錄名** | `場景戊` | 實體目錄名 |

> ⚠️ **三個名字的對應不能錯位。** 校驗工具是**用場景定義的 `name` 欄反查目錄**的。
> 目錄名跟 `name` 不一致 ⇒ 工具會說「不是場景目錄，沒有對應場景 json」。

### 步驟 2：建立目錄與邊界（最關鍵的一步）

```bash
cd <工作台根>
mkdir -p 場景/<場景名>/.dsh/skills/<場景id> 場景/<場景名>/專案記憶 場景/<場景名>/歸檔
cd 場景/<場景名> && git init -q
```

> ⛔ **`git init` 不能省。** 沒有 `.git` ⇒ 專屬技能不會被載入，
> **但場景憲法仍會被鏈式載入 ⇒ 症狀不明顯**，表現為「這個場景好像變笨了」。
> `check` 會擋：場景目錄缺少邊界標記。

### 步驟 3：寫三份核心文件

| 檔案 | 放什麼 |
|---|---|
| `定位卡.md` | 場景 id／名／面板路徑／記憶目錄／專屬技能 |
| `AGENTS.md` | 場景憲法：我是誰、職責邊界、記憶規則、換會話協議、跨場景規矩 |
| `.dsh/skills/<場景id>/SKILL.md` | 專屬技能：開場怎麼接手、怎麼幹活、怎麼寫回、怎麼交接 |

**`SKILL.md` 的 frontmatter 必須有 `name` 與 `description`，且 description 裡要帶場景目錄的絕對路徑**——
那是引擎判斷「這個技能在不在本場景可見」的依據。

模板見 [`04-模板/`](../04-模板/)。

### 步驟 4：建立記憶骨架

```bash
node <工作台根>/工具/場景記憶.mjs init --場景 <場景名> --root <工作台根>
```

生成 `場景私有記憶.md`、`_檔案索引.md`，並建 `專案記憶/`、`歸檔/`。

**接著把 `## 核心職責` 換掉**（模板是「待補」），**至少 3 條**——少於 3 條等於沒有職責，
新會話不知道自己是谁。

### 步驟 5：建立場景定義（面板）

在引擎側的場景目錄放 `<場景id>.json`。至少要有一個 `harness` 型面板，
`sessionTitle` 填場景名，`sessionId` **先留空**（下一步回填）。

### 步驟 6：建立常駐會話

用引擎端的建會話工具（DSH：`bash 工具/建會話.sh <場景名>`）。
它會走引擎 RPC：建立 workspace → 建立會話 → 改名 → 送開場訊息 → 釘到側邊欄。

> **只傳 cwd 建出來的會話會掉進「未分組」**，所以要帶 workspaceId。

### 步驟 7：★ 回填 sessionId 到兩處（最容易漏）

```
① 場景定義 json 的 harness 面板 sessionId
② 場景/_場景身份索引.md 的「會話 id」欄（7 欄對齊）
```

> ⛔ **漏任何一處 ⇒ `check` 報「會話未綁定場景 json」**，
> 而且症狀是「check 全紅但看不出哪裡錯」。

### 步驟 8：蓋章與自檢

```bash
node <工作台根>/工具/場景記憶.mjs stamp --場景 <場景名> --root <工作台根>
node <工作台根>/工具/場景記憶.mjs check --場景 <場景名> --root <工作台根>
```

`stamp` 重生成 `身份卡.md`（含定位卡指紋）與 `場景畫像.md`（含面板布局）。

> **改了定位卡就必須重跑 `stamp`**，否則 `check` 報「卡指紋過期」。

### 步驟 9：確認能被呼叫

用引擎端的呼叫工具（DSH：`node 場景/場景甲/呼叫場景.mjs`）。
每個場景都印「✓ 已呼叫」⇒ 場景活了。

## 三、三個最容易踩的坑

| 坑 | 症狀 | 修法 | 有沒有機械檢查 |
|---|---|---|---|
| **忘了 `git init`** | 專屬技能不會被載入，**但症狀不明顯**（看起來像場景變笨了） | `git init -q` | ✅ `check` 會擋 |
| **sessionId 只回填一處** | `check` 報「會話未綁定場景 json」，看不出哪裡錯 | 兩處都填 | ✅ `check` 會擋 |
| **改了定位卡沒重蓋** | `check` 報「卡指紋過期」 | 跑 `stamp` | ✅ `check` 會擋 |

**三個都有機械檢查**——這是整套架構的核心主張：**規矩不靠記，靠擋。**

---

## 四、還有一個坑目前沒有機械檢查

**每個場景早期可能有兩份記憶檔**：`場景私有記憶.md` 與 `<場景名>場景私有記憶.md`。
inode 不同、內容會分叉，而 `check` 只看前者 ⇒ **後者是孤兒，沒有人管**。

> **新場景不要造第二份。** 記憶真源只有一個：`場景私有記憶.md`。
> （這個缺口記在 [已知裂縫](四-已知裂縫與待修.md) #11。）

## 五、刪除場景（順手記一下，因為流程相反）

刪場景**比新增更需要護欄**：

1. **先 commit 或打包**——未提交內容會當場遺失
2. 先撤釘、歸檔引擎端的會話
3. 從身份索引移除那一行、刪場景定義 json
4. 刪場景目錄
5. 跑 `check --all` 確認沒有殘留

> 真實教訓：曾經刪場景時沒先 commit，內容當場不見。
> 詳見 [已知裂縫](四-已知裂縫與待修.md)。
