# 二 · 交接與校驗 —— 讓「做完了」變成可驗證的事

> 這套機制裡最實操的一條。**沒有校驗，所有規矩都只是建議。**

---

## 1. 校驗要做什麼

一句話：**證明「該失敗時會失敗」。**

| 要擋的 | 怎麼擋 | 為什麼 |
|---|---|---|
| 交接段爆掉 | 量位元組，> 4096 直接失敗 | 超了沒人讀，交接形同虛設 |
| 交接段缺小節 | 五小節逐項比對 | 缺一項，下一任接手就缺一步 |
| 定位卡被手改 | sha256 指紋不符 | 記憶卡的描述跟實際身分對不上 |
| **場景邊界失效** | 場景目錄沒有 `.git/` 就擋 | 專屬技能不會被載入，而且症狀不明顯 |
| 身份索引對不上 | 查不到這張場景卡就擋 | 索引壞掉 ⇒ 校驗對這個場景整個失效 |
| 工具生成的檔被手改 | 由工具全量重寫 | 避免兩份真相 |
| 紅線超了 | 警告（不擋） | 主檔案超標通常是「該減肥了」 |

> **分清楚「擋」與「警」**：
> 擋 = 結構性錯誤，繼續下去一定壞 ⇒ **fail-closed，直接擋**。
> 警 = 品質問題，可能只是忘了更新 ⇒ 只提示，讓人自己判斷。

### fail-closed 是什麼意思

**fail-closed = 預設「不過」，要有人明確放行才能過。**

| | fail-open（預設放行） | **fail-closed（預設擋）** |
|---|---|---|
| 檢查失敗時 | 照樣往下走 | **停下來，不准換會話** |
| 誰能放行 | —— | 只有「把東西修到真的過」的人 |
| 出事時 | 錯過了，而且**沒人知道錯過了** | 立刻停在門口，錯在哪一行寫得很清楚 |
| 適用 | 提示性質的建議 | **結構性不變量**（紅線、邊界、指紋、小節齊備） |

> ⚠️ **「fail-closed」是這套機制全部價值的所在。**
> 它把「我記得先寫交接」從**依賴自覺**變成**依賴機械**。
> 沒有它，「換會話前先寫交接」就只是文件裡一句好話。

### ⚠️ 一個永遠回傳「通過」的檢查器，比沒有檢查器更危險

這是本篇最該被記住的一句。

| | 沒有檢查器 | **永遠回「✅ 通過」的檢查器** |
|---|---|---|
| 你知道有東西沒被驗 | ✅ 知道（因為根本沒檢查） | ❌ **不知道** |
| 你會去修嗎 | 會（因為沒人給你保證） | **不會**（因為它說沒問題） |
| 出事時 | 「我早就知道沒檢查」 | 「檢查通過了呀」⇒ **浪費更多時間去查錯方向** |

**機制層面的原因**：一個永遠通過的檢查器，會把「**我以為有防護**」變成一個**假的安全感**。
它不只不擋任何東西——它還**主動讓你停止警覺**。
這比「沒有防護」更貴，因為沒有防護時你至少知道自己是裸奔的。

> **所以「該失敗時會失敗」不是一句嚴格的要求，是這支工具唯一的驗收標準。**
> 驗法見第 6 節：故意弄壞 10 種情況，確認每一種都被擋下。
> **反例不報，這個檢查器就是假的。**

## 2. 機械不變量（工具實際檢查的）

```javascript
// ① §〇 段位元組數（從 '## §〇' 到下一個同級標題）
const s0 = sec0Range(main)
if (s0.bytes > rules.sec0MaxBytes) problems.push('§〇 ' + s0.bytes + ' B 超 4 KB（紅線 4096）')

// ② 五小節齊不齊
for (const sub of rules.sec0Subsections)          // 五小節名稱來自規則檔，不寫死在程式裡
  if (!main.includes(sub)) problems.push('§〇 缺小節 ' + sub)

// ③ 核心職責條數
const n = (sec.match(/^- /gm) || []).length
if (n < rules.dutyMinItems) problems.push('核心職責只有 ' + n + ' 條（至少 3 條）')

// ④ 卡指紋（定位卡 sha256 前 16 位寫在身份卡裡）
const fp = (card.match(/sha256:([0-9a-f]+)/) || [])[1]
if (!sha(ident.card).startsWith(fp)) problems.push('卡指紋過期（卡已改，跑 stamp）')

// ⑤ 場景邊界：.git 存在性（★ 缺了會靜默降級，症狀不明顯）
if (!fs.existsSync(path.join(dir, '.git')))
  problems.push('場景目錄缺少 .git（場景邊界失效 ⇒ 專屬技能不會被載入，且症狀不明顯）')
```

> ★ **五個數字（紅線、小節清單、指紋長度、職責條數）全部來自規則檔，不寫死在程式裡。**
> 工具自己的搜尋順序是：
> ```
> 工具同目錄/交接規則.json
>   → <工作台根>/交接規則.json
>   → 04-模板/交接規則.json
>   → （都沒有 ⇒ 內建預設）
> ```
> 生效的是**第一個讀到的**——所以 `list` 會自報「規則來源」讓你確認。

### 紅線數值（本機實測）

| 對象 | 紅線（位元組） | 性質 | 定義在哪 |
|---|---|---|---|
| `§〇` 當前交接 | **4 096**（4 KB） | **硬紅線，超了直接失敗** | `交接規則.json` → `sec0MaxBytes` |
| 場景私有記憶主檔案 | **25 600**（25 KB） | 警告，搬進歸檔 | `交接規則.json` → `mainMaxBytes` |
| 專案記憶（每份） | **8 192**（8 KB） | 警告 | `交接規則.json` → `projectMaxBytes` |
| 定位卡指紋長度 | **16** 碼（十六進位） | 寫在身份卡裡 | `交接規則.json` → `fingerprintLength` |
| 單篇技能 | 12 KB | 慣例（無工具檢查） | —— |

> 為什麼是 4 KB？**約等於「看 30 秒就能開工」。**
> 這是一個「讀得完」的門檻，不是「體積美觀」的偏好。

**實測值（2026-11-01，本機工作台三個場景）**：

| 場景 | §〇 實測大小 | 主檔實測大小 | 距 4 KB 紅線 |
|---|---|---|---|
| 場景甲 | 4 012 B | 6 323 B | 剩 84 B ⚠ |
| 場景丁 | 4 047 B | 7 627 B | 剩 49 B ⚠ |
| 場景丙 | 1 693 B | 3 608 B | 剩 2 403 B |

> ⚠️ **兩個場景的 §〇 距紅線不到 100 B。**
> 紅線只在「超過」的時候才會擋，**不會提前警告你快滿了**——
> 所以減肥要提早做，不要等它某天突然全紅。
> （量測時間 2026-11-01；本機為 Linux 工作台，三個場景各為獨立 git 倉庫。）

## 3. 換會話協議（四步，第 ③ 步不能省）

```
① 先把「進度 / 下一步 / 卡點」覆蓋寫進 §〇   ← 這一步就是「交接」，別省
② 再換（新建會話 + 舊會話歸檔）
③ 換完同步三處：
     · 場景配置裡的 sessionId
     · 身份索引表的會話 id 欄
     · §〇 裡的交接署名（「本交接由會話 <新id> 於 <日期> 改寫」）
④ 跑自檢：`場景記憶.mjs check --場景 <名>`，通過才准換
```

**為什麼第 ③ 步不能省**：面板是按 `sessionId` 釘會話的。
不同步 ⇒ 面板指向一條**已歸檔的會話**，表現為「切到這個場景，AI 像換了個人」（其實就是換了個人）。

> ⚠️ **同步三處是「三處」，不是「兩處加備忘」。**
> 少同步任何一處的症狀都一樣（切場景像換了個人），
> 但根因不同——**所以要三處一起對，不要靠症狀去猜是哪一處漏了**。

### 第 ② 步的引擎 RPC 序列（實測可用）

換會話不是「開個新視窗」，是把一條會話的**身分**換掉。引擎側的完整序列：

```
workspace/create        建場景工作區（以場景目錄為路徑）
  → session/create      在該工作區建新會話（帶 workspaceId）
  → session/rename      把標題改成場景名
  → session/prompt      送一句開場（mode:'queue' ＝ 排隊，不打斷當前輪）
  → session/cancel      立刻取消（空會話不會進側邊欄）
  → workspace/pinSession 把會話釘在側邊欄
  → session/page        ★ 抓回對方最近 200 條訊息，用來「核對結果」
```

> ★ **`session/page` 是「不靠信任，靠讀證據」的關鍵。**
> 沒有它，通道只能「送」，不能「收」——
> 那就回到[四-派單與回執](../00-核心機制/四-派單與回執.md)說的「主控端只送到 prompt，沒有讀回來的程式」那個洞。

**認證的兩個坑（實測）**：

| 坑 | 做法 |
|---|---|
| token 不在設定檔裡 | 從 **systemd 日誌**撈（`journalctl --user -u <服務> \| grep -o 'token=…'`），或用環境變數指定 |
| 換 cookie 會 401 | 必須 **`redirect: 'manual'`**——跟隨重定向反而 401 |

> 這兩條寫在文件裡沒用，**它們要寫進你的工具程式碼裡**。
> 寫法見[四-派單與回執](../00-核心機制/四-派單與回執.md)第 4 節。

**交接工具做的事**（`場景記憶.mjs 交接`）：

```
① 舊版整份快照進 歸檔/<時間戳>-<會話前6碼>.md
② §〇 缺的小節逐個補上（缺一個補一個，不覆蓋已有正文）
③ 重蓋 身份卡 / 場景畫像（stamp）
④ 在 _檔案索引.md 登記歸檔條目
```

> ⚠️ **補小節是「缺才補」，不是「整段重寫」**——
> 交接工具若覆蓋整段，會把人在 §〇 裡寫的進度洗掉，那是比沒交接更糟的結果。

## 4. 什麼時候才該換會話（反直覺的一條）

| 觸發 | 換嗎 |
|---|---|
| 機主說「換會話」 | ✅ 換 |
| 上下文超限（報 413）且**壓縮之後仍然** 413 | ✅ 換（真死局） |
| 只是「到壓縮線了」、還沒報錯 | ❌ **不換**——引擎會自動壓縮，繼續幹 |
| 任務做完了 | ✅ 建議換（一個話題一個會話） |

> 「到線就換」是常見的誤操作：換了會話，狀態沒交接，
> 下一任從零開始——**這正是這套機制要消滅的那種事**。

## 5. 校驗工具的五個命令

```bash
# 一覽：每個場景缺什麼（含邊界 .git 有沒有）
node 場景記憶.mjs list    --root <工作台根>

# 建目錄骨架 + 三份文件（不覆蓋既有正文）
node 場景記憶.mjs init    --場景 <名> --root <工作台根>

# 重生成 身份卡 + 場景畫像（定位卡改了就必須重跑）
node 場景記憶.mjs stamp   --場景 <名> --root <工作台根>

# 交接：歸檔舊版 + 補 §〇 + stamp + 登記索引
node 場景記憶.mjs 交接    --場景 <名> --root <工作台根>

# ★ 全檢：結構/邊界/指紋/§〇/專案/歸檔
node 場景記憶.mjs check   --場景 <名> --root <工作台根>

# 全場景一次過
node 場景記憶.mjs check   --all --root <工作台根>
```

> `--root` 不給也行——工具會往上找，或讀環境變數 `DSH_WORKBENCH_ROOT`。
> 完整用法與逐條訊息見 [`03-可執行工具/讀我.md`](../03-可執行工具/讀我.md)。

### 退出碼

| 碼 | 意思 |
|---|---|
| `0` | 全部通過（可能有警告） |
| `1` | 有問題（擋） |
| `2` | 用法錯誤 |

> **退出碼要對**，因為這工具會被別的腳本、cron、CI 呼叫。
> 一個永遠回 0 的檢查器，比沒有檢查器更危險。

### 紅線數字不在程式裡，只在規則檔裡

```bash
node 場景記憶.mjs list --root <工作台根>
# 輸出第一行會自報：規則來源：<規則檔路徑>
```

> ★ **「規則來源」這一行就是證據。**
> 它印出來的路徑，就是**實際生效**的那份規則檔。
> 看這一行的成本是零，收益是「我改的紅線到底生效了沒」有答案。

## 6. 反例驗收：必須證明「該失敗時會失敗」

**這是校驗工具的自我驗收標準。** 光看「正常情況回 0」不算數。

工具自帶一份可執行的反例驗收腳本，跑一次就知道它是不是真的在擋：

```bash
bash 03-可執行工具/反例驗收.sh
```

**實測結果（2026-11-01，示範工作台）**：

```
═══ 反例驗收：校驗工具必須能證明「該失敗時會失敗」 ═══
【V8】正常資料應該通過（期望 exit=0）   ✓ 正常場景全部通過
【V1】§〇 灌爆 4 KB 紅線（期望 exit=1） ✓ §〇 超紅線被擋
【V2】刪掉「### 4) 下一步 / 卡點」        ✓ §〇 缺小節被擋
【V3】改定位卡但沒重蓋身份卡              ✓ 卡指紋過期被擋
【V5】刪掉「## 核心職責」整塊             ✓ 缺核心職責被擋
【V6】核心職責只寫 2 條                   ✓ 核心職責條數不足被擋
【V9】場景目錄缺 .git                     ✓ 缺 .git 被擋
【V10】身份索引裡沒有這張場景卡            ✓ 索引無此卡被擋
【V11】定位卡欄位指向不存在的檔            ✓ 定位卡不存在被擋
【V7】專案記憶有份但當前專案表寫「暫無」   ✓ 表格過期只警告不擋（exit=0）
═══ 結果：10 通過，0 失敗 ═══
```

| 編號 | 反例 | 期望結果 |
|---|---|---|
| V8 | 全部正常 | 退出碼 0 |
| V1 | 把 §〇 灌到 > 4096 位元組 | 報「§〇 N B 超 4 KB（紅線 4096）」，退出碼 1 |
| V2 | 刪掉 `### 4) 下一步 / 卡點` | 報「§〇 缺小節 ### 4) 下一步 / 卡點」，退出碼 1 |
| V3 | 改 `定位卡.md` 內容但不重蓋身份卡 | 報「卡指紋過期」，退出碼 1 |
| V5 | 刪掉 `核心職責` 整塊 | 報「缺『## 核心職責』塊」，退出碼 1 |
| V6 | `核心職責` 只寫 2 條 | 報「核心職責只有 2 條（至少 3 條）」，退出碼 1 |
| V9 | 刪掉場景目錄的 `.git/` | 報「場景目錄缺少 .git（場景邊界失效…）」，退出碼 1 |
| V10 | 從身份索引刪掉這個場景那一行 | 報「身份索引裡沒有這張場景卡」，退出碼 1 |
| V11 | 讓索引的定位卡欄位指向不存在的檔 | 報「定位卡不存在」，退出碼 1 |
| V7 | §〇 第 2 小節寫「（暫無）」但專案記憶有份 | **只警告**，退出碼仍為 0 |
| V4 | 手改 `身份卡.md` | 重蓋後被還原（工具全量重寫） |

> ⚠️ **注意 V1–V3、V5–V6、V9–V11 的共同點**：它們都必須讓**退出碼**也變 1。
> 只印紅字但回 0，是最常見的假安全。
>
> **V7 是刻意相反的**：它證明工具**分得清「擋」與「警」**——
> 表格過期是品質問題，該提示但不該擋住整個工作台。

### 紅線邊界的實測（2026-11-01）

| 實測值 | 數字 | 說明 |
|---|---|---|
| 示範場景 §〇 實測大小 | **587 B** | 紅線 4096 B，餘量 3509 B |
| 示範場景主檔實測大小 | **1 375 B** | 紅線 25 600 B |
| 恰好不超線的最大 §〇 | **4 089 B** | 187 列填充；再多一行就是 4 109 B ⇒ 超線 |

> 紅線是**位元組數**，不是「行數」也不是「字元數」。
> 同一段中文在不同工具下算出來的字元數可能差異很大——**只有位元組是穩定的**，
> 所以紅線必須寫成位元組。

## 7. 一個工具的真實教訓：規則要有單一來源

曾經出現過兩個腳本各自硬編碼「記憶根路徑」，結果：

- 訊息寫進了舊看板
- 收件方的 `場景私有記憶.md` 裡**根本收不到**
- 兩個看板的時間戳還在原地不動，**表面看不出來**

**病根不是「忘了同步」，是「同一件事有兩份路徑定義」。**

**實測證據（2026-11-01，本機工作台）**：

| 看板 | 最後一則訊息 | 檔案大小 |
|---|---|---|
| 新根 `場景/_共享記憶/_跨場景通知.md` | 2026-10-31 17:40 | 7 061 B |
| 舊根 `引擎數據/.dsh/場景記憶/_共享記憶/_跨場景通知.md` | 2026-10-31 08:26 | 5 050 B |

> 兩塊看板**各自都在長**，內容卻互不重疊——
> 這就是「分裂」的字面意思：**沒有任何一塊是完整的真相**。

**修法（架構層面的，不是打補丁）**：

1. **規則單一來源** —— 紅線、小節清單、指紋規則寫在**一份 JSON**，
   工具與腳本**都讀它**。要改規則，只改一個地方。
2. **統一路徑解析** —— 所有腳本走同一個候選順序解析記憶根：
   ```
   環境變數 DSH_SCENE_MEMORY
     → <工作台根>/場景
     → <工作台根>/引擎數據/.dsh/場景記憶
   ```
   取第一個**存在且是目錄**的。
3. **一次性合併舊看板** —— 保留原時間戳，不重寫歷史。

> **這條教訓的普適版本：**
> 同一個值有兩份定義時，早晚會分叉。
> 與其記得同步，不如**讓它沒有兩份**。

### ⚠️ 「規則單一來源」本身也會長出裂縫

即使你已經把規則集中成一份 JSON，**那份 JSON 還是可能有多份**。

**本 repo 的實測（2026-11-01）**：

| 檔案 | 鍵名風格 | 工具會讀嗎 |
|---|---|---|
| `03-可執行工具/交接規則.json` | 英文鍵（`sec0MaxBytes`…） | ✅ **會讀**（搜尋順序第 1 位） |
| `04-模板/交接規則.json` | 中文鍵（`交接段紅線位元組`…） | ❌ **讀不到** |

**兩個問題**：

| # | 問題 | 實測證據 |
|---|---|---|
| 1 | 同一份規則存在兩個檔案、兩種鍵名 | 英文版能被解析，中文版的鍵**全部對不上** |
| 2 | 工具的搜尋順序讓其中一份**永遠不會被讀到** | 放在 `04-模板/` 那份，因為 `03-可執行工具/` 那份先命中，它就是死檔 |

**端到端實測**：把 `04-模板/交接規則.json`（中文鍵）放進工具同目錄，
並把紅線改成 `999`：

```
規則來源：…/交接規則.json        ← 工具自報讀到了這份
T：✗ §〇 19235 B 超 4 KB（紅線 4096）   ← 但紅線是 4096，不是 999
```

> **檔案被讀到了，值卻沒生效。**
> 因為工具認的是 `sec0MaxBytes`，而那份檔案寫的是 `交接段紅線位元組`——
> 合併時這兩個鍵各自不相干，值就落回內建預設。
>
> **這是最安靜的一種失效**：沒有報錯、沒有警告，紅線看起來「有設定」但改不動。

**修法**：

| 做法 | 說明 |
|---|---|
| **一份就夠** | 只保留一份 `交接規則.json`，其餘地方**引用**它，不要複製 |
| **鍵名用英文** | 程式讀的鍵名寫成英文，中文只留「說明」欄——避免兩種風格並存 |
| **失效要看得見** | 工具在 `list` 裡自報「規則來源」路徑；**改完紅線後一定要看一眼這一行** |
| **加一道自檢** | 反例驗收加一條：「把規則檔的紅線改成 999 ⇒ check 必須報 999」 |

> ⚠️ **最省事的自檢**：改完紅線，跑一次 `list`，確認「規則來源」印的是你改的那個檔案；
> 然後故意灌爆交接段，看報的紅線數字是不是你改的新值。
> **兩步做完，才算「規則改生效了」。**

## 8. 校驗的失效模式

| 症狀 | 根因 | 修法 |
|---|---|---|
| 校驗一直回 0 | 工具的 `check` 分支沒被走到 | **反例驗收**（10 個案例，見第 6 節） |
| 全紅但不知道哪裡壞 | 索引路徑錯，讀不到身分表 | 索引路徑做成候選鏈，不寫死 |
| 紅字很多但沒人管 | 警告與錯誤混在一起 | **分開**：錯誤擋、警告只提示 |
| 檢查通過但交接還是壞 | 只檢查了結構，沒檢查內容時效 | 交接要帶署名與日期 |
| 工具升級後資料壞了 | 工具與資料混在同一層 | 工具放 L3，資料放 L2/L5 |
| 改了紅線但沒生效 | 規則檔有兩份／鍵名對不上 | 只留一份；看 `list` 自報的「規則來源」 |
| §〇 突然某天全紅 | 之前就貼近紅線，沒人提前量 | 定期量 §〇 大小；近線就減肥 |
