# 六 · 歸檔層：聊天全文的歸處

> **場景記憶只管「結論」，聊天全文是另一回事。**
> 這篇把那個「另一回事」講清楚：它存哪、怎麼檢索、何時清、跟記憶層怎麼分。
>
> **這不是新觀念，是補一個洞。** 換掉的舊會話如果不落到檔案裡，
> 它就只剩引擎內部的一個黑盒子——**引擎一改版，整批讀不回來**。

---

## 一、為什麼要有這一層

### 1.1 一個真實的失效模式

2026-11-03，實測某工作台的會話庫：

| | 數量 |
|---|---|
| 磁碟上的會話檔 | 30 條 |
| 引擎 `session/list` 認得的 | 11 條 |
| **引擎實際讀得動的** | **7 條** |
| 引擎回報 `corrupt` 讀不了的 | **23 條** |

那 23 條報 `corrupt Zstandard session log: first frame is not exactly one header line`。
但 `zstd -t` **全部通過，資料一個字沒壞**——**引擎換過 session log 格式**，
新的每行一個 frame，舊的整份塞在第一個 frame。

> **資料沒壞，是引擎讀不動。** 而引擎還會再改版。

### 1.2 結論

> **聊天全文不能只活在引擎裡。**
> 引擎的儲存格式是引擎的私有實作細節，它會變；**你的檔案不會。**

### 1.3 但它也不是記憶

| | 記憶層 | 歸檔層 |
|---|---|---|
| 放什麼 | **結論**（下次開場要用的） | **聊天全文**（一次性的過程） |
| 誰寫 | 人／場景 | 工具（從引擎匯出） |
| 誰讀 | **每次開場都讀** | 需要時才查 |
| 體量紅線 | `§〇` 4 KB／主檔 25 KB | 單檔 512 KB |
| ⛔ | —— | **不要把正文抄進記憶檔** |

> **那句「不要抄」是硬規則。** 抄了，記憶檔會變肥、會過期、會讓新會話讀到一堆過程廢話——
> 而新會話需要的是「現在幹什麼」，不是三小時前打了 200 次的字。

---

## 二、三層的分工（完整版）

| 層 | 放什麼 | 在哪 | 生命週期 | 誰寫 |
|---|---|---|---|---|
| **記憶層** | 結論 | `場景/<名>/場景私有記憶.md` | 永久，覆蓋式更新 | 人／場景 |
| **記憶歸檔** | 舊版記憶快照 | `場景/<名>/歸檔/` | 只進不改 | 工具（交接時） |
| **會話檔案層** ★ | **聊天全文** | `會話檔案/<場景名>/` | 只進不改，可清 | 工具（從引擎匯出） |

三層各有各的問題：

- **記憶層**回答「現在該幹什麼」⇒ 每次開場都讀 ⇒ 必須小
- **記憶歸檔**回答「這個場景的記憶長什麼樣」⇒ 只在追溯時讀 ⇒ 快照足矣
- **會話檔案層**回答「當時到底發生了什麼」⇒ 極少讀，但要能 grep 得到

---

## 三、目錄規格

```
<工作台根>/
├── 場景/<場景名>/
│   ├── 場景私有記憶.md          ← 記憶層（結論）
│   └── 歸檔/                     ← 記憶歸檔（舊版快照，只進不改）
└── 會話檔案/                     ← ★ 會話檔案層（跨場景，住在工作台根）
    ├── _會話檔案索引.md          ← 索引：每份在哪、何時、多少則、摘要
    └── <場景名>/
        └── <YYYY-MM-DDTHH-mm-ss>-<會話id前8碼>.md
```

> **為什麼住在工作台根，不住場景裡**：
> 會話檔案是**跨場景的歷史**，不是某個場景的私有資料。
> 放進場景會讓場景目錄越來越肥，而且換場景時要搬檔案。

### 3.1 一份會話檔案的格式

```markdown
# 會話檔案 · <會話名>

> 這是**聊天全文**，不是結論。結論在場景的記憶檔裡。
> ⛔ 不要把這裡的正文抄進記憶檔——那是兩回事。

| 欄位 | 值 |
|---|---|
| 會話 id | `session-xxxx` |
| 會話名 | <名> |
| 場景 id | <id> |
| 開始時間 | <ISO8601> |
| 訊息數 | <n> |

---

### 使用者

<訊息>

### 助手

<訊息>

### 工具

<訊息>
```

> **角色只分三種**：使用者／助手／工具。
> 別再細分——細分的成本（每個引擎的訊息結構都不同）遠大於收益。

---

## 四、引擎端契約（repo ↔ 引擎）

### 4.1 匯出格式

引擎端把會話匯出成一個 JSON 檔，交給 repo 的工具：

```json
{
  "會話id": "session-xxxx",
  "會話名": "場景名",
  "場景id": "scene-id",
  "開始時間": "2026-11-02T15:03:19+08:00",
  "訊息": [
    { "角色": "使用者", "文字": "……" },
    { "角色": "助手", "文字": "……" }
  ]
}
```

| 欄位 | 必填 | 備註 |
|---|---|---|
| `會話id` | ✅ | 索引靠它認會話 |
| `會話名` | | 缺了用場景名 |
| `場景id` | | 缺了用 `--場景` 指定的 |
| `開始時間` | | 缺了用當下 |
| `訊息` | ✅ | 角色可用中英兩種寫法 |

> **repo 定義格式，不定義引擎怎麼匯出。** 引擎端想用 JSONL、用 SQLite、用直接讀自己的 log，都行——
> 只要最後變成上面這個形狀。

### 4.2 索引：三種讀法

| 讀法 | 做法 |
|---|---|
| **按場景** | `node 會話檔案.mjs 列出 --root <根> --場景 <名>` |
| **按日期** | `--關鍵詞 2026-11-02`（日期在路徑與欄位裡） |
| **按關鍵詞** | `--關鍵詞 <字>`（grep 索引與檔案） |

## 五、工具

```bash
# 從引擎匯出檔抽出（會自動重建索引）
node 03-可執行工具/會話檔案.mjs 抽出 --root <工作台根> \
  --引擎端 <匯出.json> --場景 <場景名>

# 重建索引
node 03-可執行工具/會話檔案.mjs 索引 --root <工作台根>

# 自檢（索引指向的檔案還在嗎？紅線破了嗎？）
node 03-可執行工具/會話檔案.mjs 檢查 --root <工作台根>

# 查
node 03-可執行工具/會話檔案.mjs 列出 --root <工作台根> --場景 <名>
node 03-可執行工具/會話檔案.mjs 列出 --root <工作台根> --關鍵詞 <字>
```

### 5.1 `檢查` 擋什麼

| 問題 | 處置 |
|---|---|
| 索引指向不存在的檔案 | **擋**（exit 1） |
| 缺索引 | **擋** |
| 單檔超過 512 KB | 警 |
| 某場景的份數超過 20 | 警（舊的該清） |
| 場景缺 `歸檔/` | 警 |

> ★ **`檢查` 不會重建索引。** 它只讀。
> 如果檢查會重建，那被破壞的索引會在檢查當下被覆蓋掉——**檢查就永遠查不出問題**。
> 這是本 repo 反覆出現的教訓：**檢查器必須是唯讀的**。

## 六、紅線與保留

| 對象 | 紅線 | 超了怎麼辦 | 擋還是警 |
|---|---|---|---|
| 單一份會話檔 | 512 KB（524288 B） | 該場景另開一份；或只留摘要 | 警 |
| 單一場景的份數 | 20 份 | 清最舊的 | 警 |
| 索引大小 | —— | 過大就按場景分索引 | 慣例 |

> **保留 20 份不是拍的**，是「夠回頭查、又不會撐爆磁碟」的折衷。
> 真的需要更多就調 `交接規則.json` 的 `會話檔案層保留份數`——**規則單一來源，不在程式裡另寫一份**。

---

## 七、什麼時候該歸檔

| 觸發 | 該歸檔嗎 |
|---|---|
| 換會話（舊會話被頂替） | ✅ 該歸檔 |
| 場景收工、短期不動 | ✅ 該歸檔 |
| 引擎剛換版、舊 log 讀不動 | ✅ **最該歸檔**（這是它們唯一還在的機會） |
| 會話還在活躍用 | ❌ 別急——引擎裡還能讀 |

> **最後那列是重點**：引擎讀不動的會話，是**唯一**只能靠歸檔救的。
> 引擎還讀得動的，先讓引擎用著。

---

## 八、常見錯誤

| 症狀 | 根因 | 修法 |
|---|---|---|
| 抽不出來 | 匯出檔的 `訊息` 欄不是陣列 | 對照 §4.1 的格式 |
| 索引是空的 | 沒跑 `索引` | `抽出` 會自動重建；手動跑一次 |
| `檢查` 說索引指向不存在的檔 | 檔案被手動刪了 | 跑 `索引` 重建 |
| 抽進去的檔名有奇怪字元 | 引擎給的時間戳格式怪 | 工具會正規化；仍怪就手動改匯出檔 |
