## 2. 五條真實教訓（症狀 → 根因 → 修法 → 狀態）

> 這五條是**真的踩過**的，不是「聽說會這樣」。
> 每條的格式固定：**症狀／根因／修法／目前狀態**。

### 教訓 1：沒有存快照就動手拆檔 ⇒ 核對腳本根本跑不了

| | 內容 |
|---|---|
| **症狀** | 減肥（把歷史搬進 `歸檔/`）做完之後，**跑不出「有沒有丟東西」的答案** |
| **根因** | 沒有先存「搬之前」的快照 ⇒ 核對腳本沒有比對基準 ⇒ **連「我沒丟東西」都無法證明** |
| **修法** | **先快照，再動手。** 順序不可顛倒：① 快照 → ② 搬 → ③ 跑核對腳本 → ④ 跑索引體檢 |
| **目前狀態** | 🟢 **已修（已變成規矩）**。寫在[三-場景記憶](../00-核心機制/三-場景記憶.md)第 6 節、[三-維護手冊](三-維護手冊.md)第 1 節 ③ 遷移 |

> **這條的教訓比修法更值錢**：不是「記得存快照」，
> 而是**「沒有快照就不要動手」**——因為沒有基準的改動，**無法被驗收**，
> 它的正確性只能靠運氣。

### 教訓 2：刪場景前沒先 commit／打包 ⇒ 未提交內容當場遺失

| | 內容 |
|---|---|
| **症狀** | 場景被刪後，裡面 **2 個未提交修改 + 2 個未追蹤檔案** **當場遺失，沒有備份** |
| **根因** | 刪除流程沒有前置關卡。**git 倉庫的存在只在事後提供追溯能力，不能挽回未提交的東西** |
| **修法** | **刪任何場景之前：先 commit，再打包。沒有例外。** 檢查清單見[三-維護手冊](三-維護手冊.md)任務 D2 |
| **目前狀態** | 🔴 **未修**（2026-10-31 實測確認）。目前的對策是**文件裡的硬規定**，不是機器會擋的閘門 |

> **「有版本控制」不等於「不會丟」。** git 只保護已經 commit 的東西。

### 教訓 3：記憶根硬編碼在兩個腳本裡且不一致 ⇒ 看板分裂、訊息靜默丟失

| | 內容 |
|---|---|
| **症狀** | 手動發訊息時，收件方的 `場景私有記憶.md` **根本收不到**；訊息只寫進舊看板 |
| **根因** | 兩個腳本（`發消息.mjs`、`_共用-場景記憶.mjs`）的記憶根硬編碼舊路徑 `引擎數據/.dsh/場景記憶/`，其餘腳本已改指 `場景/` |
| **修法** | **統一路徑解析**：所有腳本走同一個候選鏈（環境變數 → `<根>/場景` → `<根>/引擎數據/.dsh/場景記憶`），取第一個**存在且是目錄**的。再一次性合併舊看板，**保留原時間戳** |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測確認：兩個腳本仍硬編碼舊路徑） |

**實測證據（2026-11-01）**：

| 看板 | 最後一則訊息 | 大小 |
|---|---|---|
| 新根 `場景/_共享記憶/_跨場景通知.md` | 2026-10-31 17:40 | 7 061 B |
| 舊根 `引擎數據/.dsh/場景記憶/_共享記憶/_跨場景通知.md` | 2026-10-31 08:26 | 5 050 B |

> 兩塊看板**各自都在長**，內容卻互不重疊——
> **沒有任何一塊是完整的真相**，而表面完全看不出來。
>
> **病根不是「忘了同步」，是「同一件事有兩份路徑定義」。**
> 與其記得同步，不如**讓它沒有兩份**。

### 教訓 4：身份索引搬走了但工具裡的路徑沒跟著搬 ⇒ 三場景 check 全紅

| | 內容 |
|---|---|
| **症狀** | `場景記憶.mjs check` 對**三個場景全紅**，錯誤是「身份索引裡沒有這張場景卡」 |
| **根因** | 索引從 `外壳/scenarios/` 搬到 `場景/_場景身份索引.md`，但工具裡的 `IDX` **仍指舊位置** |
| **修法** | 索引路徑做成**候選鏈**（`場景/_場景身份索引.md` → `外壳/scenarios/_場景身份索引.md`），取第一個存在的 |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測：三場景 check 仍全紅，退出碼 1） |

> **為什麼嚴重**：不是「報錯了很煩」，而是**校驗機制整個癱瘓**——
> 所有場景都顯示紅燈，紅燈就等於沒有燈。
> **「換會話前 check 必須過」這條鐵律，在那一刻是全面失效的。**
>
> 驗收：`check --all` 三個場景全綠；且**故意把索引移走**時，
> 工具應報「找不到索引」而不是「每個場景都紅」。

### 教訓 5：兩份記憶檔以為是硬連結，其實 inode 不同、內容會分叉

| | 內容 |
|---|---|
| **症狀** | 以為 `場景私有記憶.md` 與 `<場景名>場景私有記憶.md` 是同一份（以為會自動同步），實際上**兩份內容已經不同**，而且**沒有任何錯誤訊息** |
| **根因** | 以為建立了硬連結，實際上 inode 不同、連結數都是 1 ⇒ 是**兩個獨立檔案**，各自被寫 |
| **修法** | ⛔ 不要假設副本會同步。要嘛**只用一個檔案**，要嘛真的 `ln` 並**驗證連結數 > 1** |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測確認） |

**實測證據（2026-11-01，本機工作台）**：

```bash
stat -c 'inode=%i links=%h  %n' 場景私有記憶.md 場景丙場景私有記憶.md
# inode=5636724 links=1  場景私有記憶.md
# inode=5374645 links=1  場景丙場景私有記憶.md
```

| 事實 | 數值 | 意義 |
|---|---|---|
| inode | **5636724 vs 5374645** | ★ **不同 inode ⇒ 不是硬連結** |
| 連結數 | **兩者都是 1** | 各自只有一個名稱指向它 |
| 內容 | 主檔有最新進度；副本還是空骨架 | **已經分叉了** |

> ⚠️ **這是本篇最安靜的一種失效**：沒有報錯、沒有警告。
> 你只會在讀到舊內容時覺得「怎麼回到舊狀態了」，
> 然後懷疑是**人寫錯了**，而不是懷疑檔案系統。
>
> **驗證成本是個 `stat`，不驗證的成本是「讀到舊內容還不知道」。**

## 3. 尚未修的結構性缺口

> 前面五條是**具體事故**。這三條是**結構性的**——
> 它們不是「某個檔案壞了」，是「這個架構天生缺這一塊」。

### 缺口 A：跨場景派單無原生支持（只有檔案留言 + 人工確認）🔴

**現況**：跨場景派單靠**檔案留言 + 人工確認**，沒有原生支援。
留言能送達，但不能確認對方看過；派了單沒有逾時偵測，
**「活幹完了但對方還不知道」只能靠人發現**。

**修法**：把派單四件套與回執差異集合寫成**結構化格式**（前綴標記），
讓工具能解析、彙總、對帳。

**注意**：結構化格式要**保持對人可讀**——
記憶是給人看的，機器可解析只是附加價值。

### 缺口 B：工具路徑與資料路徑分離不足 🔴

**現況**：教訓 3、4、5 都是這個缺口的**不同外顯**——
路徑解析散落在各腳本裡、規則檔散落在各目錄裡、檔名對應靠約定而不是靠機制。

| 症狀 | 表現 |
|---|---|
| 路徑解析散落 | 兩個腳本各自硬編碼記憶根 ⇒ 看板分裂 |
| 索引路徑寫死 | 索引一搬位 ⇒ 三場景 check 全紅 |
| 規則檔散落 | 兩份規則檔鍵名不同 ⇒ 改紅線沒生效且無錯誤 |
| 檔名對應靠約定 | 以為是硬連結其實不是 ⇒ 內容分叉 |

**修法**：**所有路徑解析走同一個函式**，**所有規則數字只存在一份**，
**檔名對應由工具生成而不是由人記住**。

### 缺口 C：規則數字散落多處易漂移 🔴

**現況**：紅線、小節清單、指紋長度這些數字，理論上應該只在一份 JSON 裡。
但**規則檔自己也會長出裂縫**。

**本 repo 的實例（2026-11-01，端到端驗證）**：

| 檔案 | 鍵名風格 | 工具會讀嗎 |
|---|---|---|
| `03-可執行工具/交接規則.json` | 英文鍵（`sec0MaxBytes`…） | ✅ 會讀（搜尋順序第 1 位） |
| `04-模板/交接規則.json` | 中文鍵（`交接段紅線位元組`…） | ❌ **讀不到** |

**端到端實測**：把中文鍵名的那份放進工具同目錄、紅線改成 `999`：

```
規則來源：…/交接規則.json              ← 工具自報讀到了這份
T：✗ §〇 19235 B 超 4 KB（紅線 4096）   ← 但紅線是 4096，不是 999
```

> **檔案被讀到了，值卻沒生效，而且沒有任何錯誤訊息。**
> 這是「規則數字散落多處易漂移」最典型的樣子：
> **不是某一處錯了，是兩處都「看起來對」。**

**修法**：

| 做法 | 說明 |
|---|---|
| **一份就夠** | 只保留一份 `交接規則.json`，其餘地方**引用**它，不要複製 |
| **鍵名用英文** | 程式讀的鍵名寫英文，中文只留「說明」欄 |
| **失效要看得見** | 工具在 `list` 自報「規則來源」路徑；改完紅線**一定要看一眼這一行** |
| **加一道自檢** | 反例驗收加一條：「把紅線改成 999 ⇒ check 必須報 999」 |

## 4. 逐條詳述（其他已知問題）

### #5 `.git` 缺失會靜默降級 🟢 已在工具層加擋

**症狀**
- 場景目錄的 `.git` 被刪掉後：
- 引擎的專案根**往上溯**到祖先目錄
- **該場景的專屬技能全部消失**
- 但**場景憲法仍會被鏈式載入**（因為憲法是沿祖先鏈找的）

**為什麼難發現**
症狀不明顯。場景還能聊天、還能讀記憶，
只是「這個場景好像變笨了」「它好像不知道怎麼做這件事了」。

**修法**：把「`.git` 存在性」加進 `check`：
```
✗ 場景目錄缺少 .git（場景邊界失效 ⇒ 專屬技能不會被載入，且症狀不明顯）
```

**目前狀態**：🟢 **已修**。校驗工具已實作此檢查，
且反例驗收 **V9**（刪掉示範場景的 `.git` ⇒ `check` 明確報錯，退出碼 1）證明它真的會擋。

> ★ **這是「把規矩變成機制」的一個完整案例**：
> 從「引擎會靜默上溯」這個發現，到「工具會擋下它」這個結果，
> 中間每一步都有可驗收的落點。

### #1 沒有自動路由 🟡

**現況**
「這活該誰幹」仍由場景甲的模型依職責卡判斷。判錯了要人糾正。

**修法**
在共享層加路由表（場景 → 觸發詞 / 場景名），
命中就用表，**沒命中才交給模型判**。

**注意**
路由表是**預設值**，不是唯一真理——
模型判斷的能力不該被路由表取代，路由表只是給它一個起點。

### #2 回執沒有逾時偵測 🟡

**現況**
規矩是「對方不回＝算未回執」，但沒有機制會**主動發現**「沒人接」。

**修法**
在主控端側記錄每次派單的時間戳，
定期掃描：超過門檻（例：2 小時）未收到回執 ⇒ 標記為「逾時未回執」。

**注意**
門檻值要有起點但不宜死——不同活的工作量差很多，
建議預設值 + 可覆寫。

### #10 場景記憶無原生派單／回執 🟡

**現況**
跨場景派單靠「檔案留言 + 人工確認」，沒有原生支援。

**修法**
把派單四件套與回執差異集合寫成**結構化格式**（前綴標記），
讓工具能解析、彙總、對帳。

**注意**
結構化格式要**保持對人可讀**——
記憶是給人看的，機器可解析只是附加價值。

## 5. 設計上接受的（不是 bug）

| # | 現象 | 為什麼接受 |
|---|---|---|

> 否則下次會有人把它當成新 bug 重新查一遍。

| **P2** | #1 路由表 · #2 逾時偵測 | 提升效率，非正確性 |
| **P3** | #10 原生派單 | 有了路由與逾時之後再做 |

> **P0 裡有兩條的共同特徵：沒有任何錯誤訊息。**
> 這是最貴的一類問題——因為**沒有報錯，就沒有人會去查**。

## 6.1 累積機制的五個缺口（2026-11-02 重排架構時發現 → 實作時修掉）

架構改成「累積」主線之後，有五件事是**規格有了、機制還沒有**的。

**這五條全部在 v0.3 實作並修掉了。** 修的過程本身就是這份清單最有價值的部分——
因為**其中三個缺口是「照著規格寫完、實際跑一遍才發現」的**。

### 缺口 13：可累積物沒有機械驗收 🟢 已修

**原本的問題**：「沒有可累積物的回執 ＝ 這次活白做」這條紅線只是文件裡的一句話，
沒有任何程式在管。回執可以只寫「差異集合」就送回。

**修法**：
1. `03-可執行工具/回執校驗.mjs`——檢查回執有沒有三件套
2. ★ **落地驗收**：每一條可累積物都必須在**場景記憶的 §五 決策與坑（或專屬技能）裡找得到**。
   只寫在回執裡不算數。
3. `工作流執行.mjs` 收回執時呼叫它；不合格就**就地停**（fail-closed）

**驗收**：`工作流驗收.sh` 的 E3、E5、E6 三項。

### 缺口 14：工作流執行狀態沒有落地機制 🟢 已修

**原本的問題**：工作流定義能寫、能校驗，但**執行時的狀態放哪、誰寫、怎麼恢復，只有規格沒有實作**。

**修法**：
1. `03-可執行工具/工作流執行.mjs`——離線執行器（start / step / 回執 / resume / status）
2. `執行/<run-id>/` 目錄：執行狀態.md（跑到哪、卡在哪）+ 交接串.md（累積物往下傳）+ 回執/（派單與回執副本）
3. 預檢 fail-closed：場景不存在、缺邊界標記、步驟缺判據 ⇒ 拒絕啟動

**驗收**：`工作流驗收.sh` 的 E1、E2。

> **這個版本是離線的**：它不真的呼叫引擎，而是把每一步該做什麼寫成檔案並推進狀態機。
> 這是刻意的——**引擎中立**。引擎專用版只要把「產生派單」換成「真的派出去」，
> 狀態機與驗收邏輯完全沿用。

### 缺口 15：回執欄位名散在多處 🟢 已修

**原本的問題**：「差異集合 / 可累積物 / 下一棒」同時出現在四個檔案裡，改一次要改四處。

**修法**：全部欄位名進 `交接規則.json`（單一來源），文件與工具都讀它。

### 缺口 16：回執三件套只有文件層、沒有工具層 🟢 已修

**原本的問題**：即使欄位名統一了，也沒有東西會在回執送達時檢查它。

**修法**：`回執校驗.mjs` 會擋「缺小節」與「小節是空的」。

### 缺口 17：run 停下後沒有復原機制 🟢 已修（**實跑才發現**）

**這是規格裡完全沒有的東西**——原規格只寫「失敗就地停」，沒寫「修好之後怎麼接回去」。

**症狀**：第一次被 fail-closed 擋下時，run 停在「已停」，
然後**修好回執也收不進去**（「run 狀態是『已停』，不能收回執」）。

**修法**：`resume` 場景甲把狀態拉回「執行中」，重收同一跳的回執。

## 6.3 歸檔層與換會話（2026-11-03 補完時發現）

### 缺口 18：聊天全文沒有歸處 ⇒ 引擎改版就整批讀不回來 🟡 已修（規格＋工具）

**實測**：某工作台的會話庫 30 條，引擎只認 11 條、只讀得動 **7 條**；
23 條回報 `corrupt`——但 `zstd -t` 全部通過，**資料一個字沒壞**。

**根因**：引擎換過 session log 格式（新的每行一個 frame，舊的整份塞在第一個 frame）。
**這不是資料損壞，是引擎讀不動自己的舊檔。**

**修法**：新增[六-歸檔層](六-歸檔層.md) ＋ `會話檔案.mjs`——
把聊天全文落到 `會話檔案/<場景名>/`，配一份可 grep 的索引。
**引擎改版不再影響你的資料**，因為資料已經不在引擎裡了。

### 缺口 19：換會話是手工流程 ⇒ 漏一處的症狀全是同一個 🟡 已修（規格＋工具）

**症狀**：切到某場景，AI 像換了個人。三處（場景配置 sessionId／身份索引會話 id 欄／
§₀ 交接署名）漏同步任一處，症狀**完全一樣**——所以靠症狀根本猜不出是哪一處漏了。

**修法**：新增[七-換會話](七-換會話.md) ＋ `換會話.mjs`——
前置檢查（能不能換）、三處同步的機械自檢、缺一處也算不一致。

### 缺口 20：檢查器會改資料 🟢 已修（**實測才發現**）

`會話檔案.mjs 檢查` 原本會先重建索引 ⇒ **把被破壞的索引覆蓋掉** ⇒ 問題永遠查不出來。

> **檢查器必須是唯讀的。** 會改資料的檢查器每次檢查都把問題擦掉，
> 它會永遠回 0，而人會以為有防護——**比沒有檢查器更危險**。

### 缺口 21：規格 §6 的「到線動作」在工具層不存在 🔴

**症狀**：`場景記憶.mjs 交接` 把**整份主檔複製一份到 `歸檔/`**，主檔一個字都沒變小。
規格 §6 寫的「把舊輪次、舊決策搬進 `歸檔/`，主檔只留入口 + 指針」——**「搬」這個動作沒有程式**。

**根因**：現有五個命令 `init / stamp / 交接 / check / list` 裡，沒有任何一個會讓檔案變小。
「交接」是**複本機制，不是搬移機制**。

**後果**：爆炸最嚴重的郵件處理**一份歸檔都沒有**（22 個場景只有 9 個有歸檔）——
因為沒人跑交接，而跑了也沒用。

**修法**：新增 `場景記憶.mjs 減肥 --場景 <名> [--dry]`，把規格 §6 四步抄成程式：

| 步 | 程式要做什麼 |
|---|---|
| ① 先快照 | 寫 `歸檔/減肥前-<時戳>.md`（＝減肥前完整主檔） |
| ② 搬 | §₀ 第 3 小節只留 ≤3 行摘要，其餘進 `歸檔/§〇變更-<日期>.md`；§五 超量進歸檔、主檔留指針；`〇-通知` 整段進歸檔 |
| ③ 核對 | **同一支程式裡**逐行比對「搬前非歷史行 == 搬後非歷史行」，輸出「搬走 N / 殘留 M / 差異 0」，**非 0 差異即中止** |
| ④ 體檢 | 更新 `_檔案索引.md`、重算指紋、重蓋身份卡（`stamp`） |

**硬要求**：`--dry` 必須做到「算完計畫、一個字都沒寫」。
理由見[教訓 1](#教訓-1沒有存快照就動手拆--核對腳本根本跑不了)——沒有快照就無法證明沒丟東西。

**驗收**：`--dry` 後主檔 hash 不變；實跑後 §₀ ≤ 4,096 B 且核對差異 = 0；
反例：手動刪掉歸檔裡的搬走內容 ⇒ 核對腳本必須報「丟了東西」。

### 缺口 22：紅線層級錯了——主檔超標只警不擋 🔴

**症狀**：`check` 裡 §₀ 超 4 KB → `problems`（**擋**）；主檔超 25 KB → `warns`（**只警**）；
**共享層超標 → 連警都沒有**（`交接規則.json` 裡沒有共享層的紅線條目）。

**根因**：紅線的「擋／警」是按物件的重要性手工分的，沒有一致原則；
而且校驗只在換會話時被順帶呼叫，**沒有任何 cron 會跑 `check --all`**——
`check --all` 現在退出碼 1，這個紅燈已經亮著，系統照跑不誤。

**修法**：
1. 主檔超 25 KB ⇒ 升為 `problems`（擋交接），或至少**擋交接不擋 check**
2. `交接規則.json` 補共享層紅線條目（看板、待辦板、`〇-通知` 段）
3. **加排程**：每日 `check --all` ＋ `一致性稽核.mjs`，異常就推播

**驗收**：把某場景主檔灌到 26 KB ⇒ `check` 必須報錯且退出碼 1（現在只印一行警）。

### 缺口 23：共享層看板是「單向寫入的匯流排」——沒有任何 agent 讀它 🔴

**症狀**：23 個場景的 `AGENTS.md` **沒有一個教 agent 讀共享層**（唯一提到「共享層」的是開發工具，
而且是禁止語「不碰場景記憶與共享層」）；全域憲法 `~/.dsh/AGENTS.md` grep「共享／看板／通知」**0 命中**；
81 份會話檔裡提到 `_跨場景通知` 的只有 8 份，且**全部是寫入側，讀取型 = 0**。

**根因**：看板的原始定位本來就是「留痕」（規格《八》§3.2：「共享層看板＝留痕，所有人看得到；
收件場景的 `## 〇-通知`＝收件方自己看得到」），**它從來不是給 agent 用的通道**。
真正在讀它的只有 `wb-web` 網頁（`readNotices()`）與 topbar 狀態列——**都是給人看的**。

**現況數據**：`_跨場景通知.md` 66,910 B（≈22k token）、140 條，其中 121 條是機械噪音、
只有 12 條真派單／5 條回執／2 條退回；**還混著 2026-10-30 已被刪掉的「B站」場景的歷史**。

**修法（兩個選項，機主擇一）**：

| 選項 | 做法 | 代價 |
|---|---|---|
| **A. 砍掉** | 刪 `_跨場景通知.md`／`_場景活動.md`／`_待辦.md`／`衝突.md`（先搬 `歸檔/`）；稽核改吃 `派單/<場景>/*.狀態.json`（**已有 `發起方`／`狀態`／`送出時間`／`拒絕原因`**） | 網頁版少一塊看板；3D 總覽的邊本來就不是從看板來的（`buildGraph()` 只用 scene→skill→project） |
| **B. 修好** | 看板加「未讀旗標＋按收件方過濾＋輪轉（近 7 天留檔，其餘歸檔）」；並在全域憲法＋23 個場景 `AGENTS.md` 教 agent 讀 | 22 個場景的憲法要同步改；token 成本仍在 |

**驗收（A）**：刪看板後 `派單 --全部` 流程端到端跑一趟，回執與稽核不受影響；
**驗收（B）**：新開一個場景會話，在回覆裡能引用看板中 `→ <本場景>` 的未讀條目。

### 缺口 24：`## 〇-通知` 是壞掉的「通道 B」生效條件 🔴

**症狀**：規格《八》§3.2 明寫「只寫看板、不寫進對方的記憶檔，就是訊息被寫進舊看板，
收件方的記憶檔裡根本收不到——那個真事故正是這樣發生的。**雙寫不是冗餘，是生效條件。**」
但實機上 `〇-通知` 段被 append 在記憶檔**最後**（§五 之後），不在 §₀ 裡；
`check` 完全不管這一段；**沒有任何 `AGENTS.md` 教 agent 去讀它**。

**現況數據**：`〇-通知` 段合計 40,947 B，最大郵件處理 6,421 B（**比它整個 §₀ 5,435 B 還大**），
裡面塞著 19 行自己派給自己的流水；4 個場景超 4 KB。

**根因**：規格《八》把「收件方自己看得到」當成**檔案位置**的問題，
但 agent 開場只讀 §₀（換會話開場訊息硬寫死 `先讀 §〇 交接，再干活`）——
**位置對了，沒人讀，一樣收不到**。

**修法**：
1. `check` 加一條：`〇-通知` 段大小紅線（8 KB）
2. 把「未讀通知」摘要搬進 §₀ 管轄範圍（或 §₀ 加一行「未讀通知 N 條，見 X」）
3. `派單.mjs` 的 `dualWrite` 改道：不再寫公共看板，改寫收件場景自己的收件匣
4. 23 個場景 `AGENTS.md` 各加一句本場景的收件匣讀法

**驗收**：派一張單給某場景 → 該場景新開會話時，開場自我介紹裡要能說出「有 1 條未讀通知」。

### 缺口 25：路由表命中率撐不起「機械優先」 🟢 已修（2026-11-09）

**症狀**：實跑 `派單.mjs 路由`，7 句日常用語**只有 3 句命中**：

| 輸入 | 結果 |
|---|---|
| 期中考範圍是什麼 | ✓ 考古題庫 |
| 剛才那個音檔太大聲 | ✓ 音效配樂 |
| 幫我看磁碟剩多少空間 | ✓ 本地電腦 |
| 幫我查一下這週的待辦 | ✗ 落空 |
| 把這封信轉寄給王 | ✗ 落空 |
| 我要做一支短片 | ✗ 落空 |
| 整理我的筆記 | ✗ 落空 |

**根因**：路由表 32 條、owner 重複出現（產品發布 ×2、自我復盤 ×3、開發工具 ×2），
命中靠「條目順序」決定，而順序是維護時的手工決定；沒有同義詞／詞形／權重概念。

**另一層**：路由表裡還留著已被自己判定為泛用詞的關鍵字（如「音檔」→音效配樂、
「摘要」→每日簡報），**與 skill 裡「移除泛用詞」的既有教訓抵觸**。

**修法**：
1. 補關鍵字（把上面 4 句落空的收進去），每條 owner 只留一組
2. 移除泛用詞
3. **加回饋迴圈**：記錄每次路由命中／未命中與人工糾正，讓路由表能自己變好

**驗收**：一份 30 句的實測語句集，命中率 ≥ 80%。

**實際修法**（2026-11-09，先量後改）：

1. **先建立回歸基準**：`工具/路由測試語句.json`（58 句、24 場景）＋
   `工具/路由回歸測試.mjs`（可重跑，支援 `--明細` 與門檻模式）。
   基準量測：**41 句中 34 句命中 = 82.9%**（7 句不符）。
2. **評分機制重寫**（`派單.mjs` 的 `routeBy()`）：舊邏輯「長關鍵字永遠勝過短動作詞」
   會讓「幫我把這個 repo 公開」誤派。改為**動作加權 ＋ 出現位置加權 ＋ 關鍵字長度加權 ＋ 多詞加權**。
   動作詞表只放動作（做／寫／剪／配／轉寄…），名詞性關鍵字不拿動作加權。
3. **路由表整理**：合併重複 owner（每個 owner 一組）、移除泛用詞
   （摘要／空間／音檔／同步／sync／貼文／排程 —— 依 skill §8 交模型判）、
   補入口語複合詞與同義詞（`復盤|複盤`、`每日摘要`、`每日資訊摘要`、`流程編排|流程编排`）。
4. **簡繁正規化**：使用者打簡體、路由表寫繁體會落空（例：`帮我写个脚本` 落空、
   `流程编排` 被我改成繁體後變成新的落空）。加入 1794 字對的簡→繁對照表，
   **比對時雙邊正規化**。對照表已排除 value 碰撞（一對多會誤命中）與
   「既是簡體又是正體」的危險字（茫／蒙／襁／谷 等）。
5. **回饋閉環**：路由查詢寫入 `場景/_共享記憶/路由回饋.jsonl`；
   `--糾正` 可指定人工正確 owner；**只有人工結果與機械命中不同才記為「搶單」**
   （相同時不污染統計）；新增 `回饋 --明細` 檢視。

**驗收（實測）**：

| 項目 | 結果 |
|---|---|
| 回歸測試集命中率 | **67/67 = 100.0%**（基準 82.9%），非預期不符 0 句 |
| 歧義句（第一二名分數差 < 20） | **0 句**（已併入回歸測試，歧義則 exit 1；並以「故意刪掉投資簡報複合詞」反證它會抓到） |
| 350 個路由表關鍵字的簡體形 | 全部仍命中原 owner（0 例外） |
| 改動前 280 個代表詞驗證 | 275 仍命中原 owner；5 例為刻意的泛用詞移除，**無搶字** |
| `工具/一致性稽核.mjs` | 99 項全過 |

> **關鍵教訓（與缺口 20 同型）**：**先量再改**。
> 沒有回歸語料集前改路由表，等於用「自己新寫的測試句」證明自己對 ——
> 舊代表詞搶字檢查（275/280）才是真正防止修壞別人的那一半。
> 另一個教訓：**改關鍵字時要連字形一起想**，「流程編排 → 流程编排」這種改動
> 本身會製造新的落空。

### 缺口 26：可累積物分流判準沒實作 ⇒ 派單要求逐字、實機長出雙寫 🟢 已修（2026-11-09）

**原診斷（錯的，已作廢）**：原文寫「§五 與 SKILL.md 各自新增、逐字相同」是硬性要求，
與「一個事實只存一處」矛盾，修法是「擇一為權威，另一處改用指標」。

**為什麼原診斷是錯的**（2026-11-09 實測）：

1. **「逐字相同」這條規則從未寫在規格裡** —— 全文只有本節提到它。
   《四-派單與回執》§3.2 講的是**依內容性質分流**：「會再用一次以上的，寫成專屬技能；
   只這一次的，寫進 §五」—— 這是分工，不是雙寫。
2. **「擇一為權威」會破壞規格** —— 若把 §五 設為唯一權威，
   則「會再用一次以上的做法」全擠在「只追加的 §五」裡，而專屬技能（那才是真的會被複用的容器）
   變成指標 —— 規格原本的「§五 是堆積、專屬技能是提煉」被推翻。
3. **引用的證據已過時** —— 原文引郵件處理 §五「各自新增五條、逐字相同」；
   2026-11-09 實測該場景 §五 5 段、SKILL.md 11 段，早已不是五五對稱。

**真正的根因（實測）**：**分流判準從來沒有被實作**。

| 層 | 實際狀況 |
|---|---|
| 規格 §3.2 | 有分流判準（做法→技能／事實→§五） |
| `回執校驗.mjs` | 把 §五 與技能**串成同一個 haystack**，任一處命中就過 —— 分不出版本該去哪 |
| `派單.mjs 退回` | 卻寫「（**逐字比對**）」—— 與校驗程式自己的註解（不要逐字）相反 |
| 實機 | 於是場景照派單做逐字 ⇒ 被逼把同一段抄成兩份 |

★ **派單那句才是真正的成因**：`派單.mjs` 是**場景真正會讀到**的那一份（被派出去的派單正文），
`回執校驗.mjs` 只是驗收用的。派單叫它逐字抄，它就逐字抄。

**實測證據（2026-11-09）**：郵件處理場景有 **4 組**「可累積物登記」段落
在 §五 與 `email/SKILL.md` 裡**去空白後逐字完全相同**（1054／751／397 字，
另 1 組 9/11 條重疊），而標題**早已寫了指標**（「做法見 SKILL.md」／「事實見 §五」）
—— 指標寫了，內文沒瘦身。

**修法**：
1. `派單.mjs 退回` 的「逐字比對」改回與校驗一致（≥ 8 字公共子字串），並註明分流判準、
   明說「不要兩邊各抄一份」（實機 commit `5c3dc521`）。
2. 實機 §五 與專屬技能依規格 §3.2 分流：**每條 bullet 仍然存在，只是不再兩邊各抄一份**
   （郵件處理場景 commit `06ea982`）。
3. 指標段瘦身成真的指標（只留「見 X」一行）。

**驗收（實測）**：
- 99 條 bullet 的聯集前後一致（**0 遺失 0 新增**）
- 4 組逐字重複 → **0 組**
- 郵件處理 13 份真實回執校驗結果 **0 變化**（9 過 4 敗，4 敗是既有的格式問題，非本次造成）
- 場景記憶 `check --all` 24 個場景全過
