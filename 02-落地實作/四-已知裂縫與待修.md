## 2. 五條真實教訓（症狀 → 根因 → 修法 → 狀態）

> 這五條是**真的踩過**的，不是「聽說會這樣」。
> 每條的格式固定：**症狀／根因／修法／目前狀態**。

### 教訓 1：沒有存快照就動手拆檔 ⇒ 核對腳本根本跑不了

| | 內容 |
|---|---|
| **症狀** | 減肥（把歷史搬進 `歸檔/`）做完之後，**跑不出「有沒有丟東西」的答案** |
| **根因** | 沒有先存「搬之前」的快照 ⇒ 核對腳本沒有比對基準 ⇒ **連「我沒丟東西」都無法證明** |
| **修法** | **先快照，再動手。** 順序不可顛倒：① 快照 → ② 搬 → ③ 跑核對腳本 → ④ 跑索引體檢 |
| **目前狀態** | 🟢 **已修（已變成規矩）**。寫在[三-場景記憶](../00-核心機制/三-場景記憶.md)第 6 節、[三-維護手冊](三-維護手冊.md)第 1 節 ③ 遷移 |

> **這條的教訓比修法更值錢**：不是「記得存快照」，
> 而是**「沒有快照就不要動手」**——因為沒有基準的改動，**無法被驗收**，
> 它的正確性只能靠運氣。

### 教訓 2：刪場景前沒先 commit／打包 ⇒ 未提交內容當場遺失

| | 內容 |
|---|---|
| **症狀** | 場景被刪後，裡面 **2 個未提交修改 + 2 個未追蹤檔案** **當場遺失，沒有備份** |
| **根因** | 刪除流程沒有前置關卡。**git 倉庫的存在只在事後提供追溯能力，不能挽回未提交的東西** |
| **修法** | **刪任何場景之前：先 commit，再打包。沒有例外。** 檢查清單見[三-維護手冊](三-維護手冊.md)任務 D2 |
| **目前狀態** | 🔴 **未修**（2026-10-31 實測確認）。目前的對策是**文件裡的硬規定**，不是機器會擋的閘門 |

> **「有版本控制」不等於「不會丟」。** git 只保護已經 commit 的東西。

### 教訓 3：記憶根硬編碼在兩個腳本裡且不一致 ⇒ 看板分裂、訊息靜默丟失

| | 內容 |
|---|---|
| **症狀** | 手動發訊息時，收件方的 `場景私有記憶.md` **根本收不到**；訊息只寫進舊看板 |
| **根因** | 兩個腳本（`發消息.mjs`、`_共用-場景記憶.mjs`）的記憶根硬編碼舊路徑 `引擎數據/.dsh/場景記憶/`，其餘腳本已改指 `場景/` |
| **修法** | **統一路徑解析**：所有腳本走同一個候選鏈（環境變數 → `<根>/場景` → `<根>/引擎數據/.dsh/場景記憶`），取第一個**存在且是目錄**的。再一次性合併舊看板，**保留原時間戳** |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測確認：兩個腳本仍硬編碼舊路徑） |

**實測證據（2026-11-01）**：

| 看板 | 最後一則訊息 | 大小 |
|---|---|---|
| 新根 `場景/_共享記憶/_跨場景通知.md` | 2026-10-31 17:40 | 7 061 B |
| 舊根 `引擎數據/.dsh/場景記憶/_共享記憶/_跨場景通知.md` | 2026-10-31 08:26 | 5 050 B |

> 兩塊看板**各自都在長**，內容卻互不重疊——
> **沒有任何一塊是完整的真相**，而表面完全看不出來。
>
> **病根不是「忘了同步」，是「同一件事有兩份路徑定義」。**
> 與其記得同步，不如**讓它沒有兩份**。

### 教訓 4：身份索引搬走了但工具裡的路徑沒跟著搬 ⇒ 三場景 check 全紅

| | 內容 |
|---|---|
| **症狀** | `場景記憶.mjs check` 對**三個場景全紅**，錯誤是「身份索引裡沒有這張場景卡」 |
| **根因** | 索引從 `外壳/scenarios/` 搬到 `場景/_場景身份索引.md`，但工具裡的 `IDX` **仍指舊位置** |
| **修法** | 索引路徑做成**候選鏈**（`場景/_場景身份索引.md` → `外壳/scenarios/_場景身份索引.md`），取第一個存在的 |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測：三場景 check 仍全紅，退出碼 1） |

> **為什麼嚴重**：不是「報錯了很煩」，而是**校驗機制整個癱瘓**——
> 所有場景都顯示紅燈，紅燈就等於沒有燈。
> **「換會話前 check 必須過」這條鐵律，在那一刻是全面失效的。**
>
> 驗收：`check --all` 三個場景全綠；且**故意把索引移走**時，
> 工具應報「找不到索引」而不是「每個場景都紅」。

### 教訓 5：兩份記憶檔以為是硬連結，其實 inode 不同、內容會分叉

| | 內容 |
|---|---|
| **症狀** | 以為 `場景私有記憶.md` 與 `<場景名>場景私有記憶.md` 是同一份（以為會自動同步），實際上**兩份內容已經不同**，而且**沒有任何錯誤訊息** |
| **根因** | 以為建立了硬連結，實際上 inode 不同、連結數都是 1 ⇒ 是**兩個獨立檔案**，各自被寫 |
| **修法** | ⛔ 不要假設副本會同步。要嘛**只用一個檔案**，要嘛真的 `ln` 並**驗證連結數 > 1** |
| **目前狀態** | 🔴 **未修**（2026-11-01 實測確認） |

**實測證據（2026-11-01，本機工作台）**：

```bash
stat -c 'inode=%i links=%h  %n' 場景私有記憶.md 場景丙場景私有記憶.md
# inode=5636724 links=1  場景私有記憶.md
# inode=5374645 links=1  場景丙場景私有記憶.md
```

| 事實 | 數值 | 意義 |
|---|---|---|
| inode | **5636724 vs 5374645** | ★ **不同 inode ⇒ 不是硬連結** |
| 連結數 | **兩者都是 1** | 各自只有一個名稱指向它 |
| 內容 | 主檔有最新進度；副本還是空骨架 | **已經分叉了** |

> ⚠️ **這是本篇最安靜的一種失效**：沒有報錯、沒有警告。
> 你只會在讀到舊內容時覺得「怎麼回到舊狀態了」，
> 然後懷疑是**人寫錯了**，而不是懷疑檔案系統。
>
> **驗證成本是個 `stat`，不驗證的成本是「讀到舊內容還不知道」。**

## 3. 尚未修的結構性缺口

> 前面五條是**具體事故**。這三條是**結構性的**——
> 它們不是「某個檔案壞了」，是「這個架構天生缺這一塊」。

### 缺口 A：跨場景派單無原生支持（只有檔案留言 + 人工確認）🔴

**現況**：跨場景派單靠**檔案留言 + 人工確認**，沒有原生支援。
留言能送達，但不能確認對方看過；派了單沒有逾時偵測，
**「活幹完了但對方還不知道」只能靠人發現**。

**修法**：把派單四件套與回執差異集合寫成**結構化格式**（前綴標記），
讓工具能解析、彙總、對帳。

**注意**：結構化格式要**保持對人可讀**——
記憶是給人看的，機器可解析只是附加價值。

### 缺口 B：工具路徑與資料路徑分離不足 🔴

**現況**：教訓 3、4、5 都是這個缺口的**不同外顯**——
路徑解析散落在各腳本裡、規則檔散落在各目錄裡、檔名對應靠約定而不是靠機制。

| 症狀 | 表現 |
|---|---|
| 路徑解析散落 | 兩個腳本各自硬編碼記憶根 ⇒ 看板分裂 |
| 索引路徑寫死 | 索引一搬位 ⇒ 三場景 check 全紅 |
| 規則檔散落 | 兩份規則檔鍵名不同 ⇒ 改紅線沒生效且無錯誤 |
| 檔名對應靠約定 | 以為是硬連結其實不是 ⇒ 內容分叉 |

**修法**：**所有路徑解析走同一個函式**，**所有規則數字只存在一份**，
**檔名對應由工具生成而不是由人記住**。

### 缺口 C：規則數字散落多處易漂移 🔴

**現況**：紅線、小節清單、指紋長度這些數字，理論上應該只在一份 JSON 裡。
但**規則檔自己也會長出裂縫**。

**本 repo 的實例（2026-11-01，端到端驗證）**：

| 檔案 | 鍵名風格 | 工具會讀嗎 |
|---|---|---|
| `03-可執行工具/交接規則.json` | 英文鍵（`sec0MaxBytes`…） | ✅ 會讀（搜尋順序第 1 位） |
| `04-模板/交接規則.json` | 中文鍵（`交接段紅線位元組`…） | ❌ **讀不到** |

**端到端實測**：把中文鍵名的那份放進工具同目錄、紅線改成 `999`：

```
規則來源：…/交接規則.json              ← 工具自報讀到了這份
T：✗ §〇 19235 B 超 4 KB（紅線 4096）   ← 但紅線是 4096，不是 999
```

> **檔案被讀到了，值卻沒生效，而且沒有任何錯誤訊息。**
> 這是「規則數字散落多處易漂移」最典型的樣子：
> **不是某一處錯了，是兩處都「看起來對」。**

**修法**：

| 做法 | 說明 |
|---|---|
| **一份就夠** | 只保留一份 `交接規則.json`，其餘地方**引用**它，不要複製 |
| **鍵名用英文** | 程式讀的鍵名寫英文，中文只留「說明」欄 |
| **失效要看得見** | 工具在 `list` 自報「規則來源」路徑；改完紅線**一定要看一眼這一行** |
| **加一道自檢** | 反例驗收加一條：「把紅線改成 999 ⇒ check 必須報 999」 |

## 4. 逐條詳述（其他已知問題）

### #5 `.git` 缺失會靜默降級 🟢 已在工具層加擋

**症狀**
- 場景目錄的 `.git` 被刪掉後：
- 引擎的專案根**往上溯**到祖先目錄
- **該場景的專屬技能全部消失**
- 但**場景憲法仍會被鏈式載入**（因為憲法是沿祖先鏈找的）

**為什麼難發現**
症狀不明顯。場景還能聊天、還能讀記憶，
只是「這個場景好像變笨了」「它好像不知道怎麼做這件事了」。

**修法**：把「`.git` 存在性」加進 `check`：
```
✗ 場景目錄缺少 .git（場景邊界失效 ⇒ 專屬技能不會被載入，且症狀不明顯）
```

**目前狀態**：🟢 **已修**。校驗工具已實作此檢查，
且反例驗收 **V9**（刪掉示範場景的 `.git` ⇒ `check` 明確報錯，退出碼 1）證明它真的會擋。

> ★ **這是「把規矩變成機制」的一個完整案例**：
> 從「引擎會靜默上溯」這個發現，到「工具會擋下它」這個結果，
> 中間每一步都有可驗收的落點。

### #1 沒有自動路由 🟡

**現況**
「這活該誰幹」仍由場景甲的模型依職責卡判斷。判錯了要人糾正。

**修法**
在共享層加路由表（場景 → 觸發詞 / 場景名），
命中就用表，**沒命中才交給模型判**。

**注意**
路由表是**預設值**，不是唯一真理——
模型判斷的能力不該被路由表取代，路由表只是給它一個起點。

### #2 回執沒有逾時偵測 🟡

**現況**
規矩是「對方不回＝算未回執」，但沒有機制會**主動發現**「沒人接」。

**修法**
在主控端側記錄每次派單的時間戳，
定期掃描：超過門檻（例：2 小時）未收到回執 ⇒ 標記為「逾時未回執」。

**注意**
門檻值要有起點但不宜死——不同活的工作量差很多，
建議預設值 + 可覆寫。

### #10 場景記憶無原生派單／回執 🟡

**現況**
跨場景派單靠「檔案留言 + 人工確認」，沒有原生支援。

**修法**
把派單四件套與回執差異集合寫成**結構化格式**（前綴標記），
讓工具能解析、彙總、對帳。

**注意**
結構化格式要**保持對人可讀**——
記憶是給人看的，機器可解析只是附加價值。

## 6.1 累積機制的五個缺口（2026-11-02 重排架構時發現 → 實作時修掉）

架構改成「累積」主線之後，有五件事是**規格有了、機制還沒有**的。

**這五條全部在 v0.3 實作並修掉了。** 修的過程本身就是這份清單最有價值的部分——
因為**其中三個缺口是「照著規格寫完、實際跑一遍才發現」的**。

### 缺口 13：可累積物沒有機械驗收 🟢 已修

**原本的問題**：「沒有可累積物的回執 ＝ 這次活白做」這條紅線只是文件裡的一句話，
沒有任何程式在管。回執可以只寫「差異集合」就送回。

**修法**：
1. `03-可執行工具/回執校驗.mjs`——檢查回執有沒有三件套
2. ★ **落地驗收**：每一條可累積物都必須在**場景記憶的 §五 決策與坑（或專屬技能）裡找得到**。
   只寫在回執裡不算數。
3. `工作流執行.mjs` 收回執時呼叫它；不合格就**就地停**（fail-closed）

**驗收**：`工作流驗收.sh` 的 E3、E5、E6 三項。

### 缺口 14：工作流執行狀態沒有落地機制 🟢 已修

**原本的問題**：工作流定義能寫、能校驗，但**執行時的狀態放哪、誰寫、怎麼恢復，只有規格沒有實作**。

**修法**：
1. `03-可執行工具/工作流執行.mjs`——離線執行器（start / step / 回執 / resume / status）
2. `執行/<run-id>/` 目錄：執行狀態.md（跑到哪、卡在哪）+ 交接串.md（累積物往下傳）+ 回執/（派單與回執副本）
3. 預檢 fail-closed：場景不存在、缺邊界標記、步驟缺判據 ⇒ 拒絕啟動

**驗收**：`工作流驗收.sh` 的 E1、E2。

> **這個版本是離線的**：它不真的呼叫引擎，而是把每一步該做什麼寫成檔案並推進狀態機。
> 這是刻意的——**引擎中立**。引擎專用版只要把「產生派單」換成「真的派出去」，
> 狀態機與驗收邏輯完全沿用。

### 缺口 15：回執欄位名散在多處 🟢 已修

**原本的問題**：「差異集合 / 可累積物 / 下一棒」同時出現在四個檔案裡，改一次要改四處。

**修法**：全部欄位名進 `交接規則.json`（單一來源），文件與工具都讀它。

### 缺口 16：回執三件套只有文件層、沒有工具層 🟢 已修

**原本的問題**：即使欄位名統一了，也沒有東西會在回執送達時檢查它。

**修法**：`回執校驗.mjs` 會擋「缺小節」與「小節是空的」。

### 缺口 17：run 停下後沒有復原機制 🟢 已修（**實跑才發現**）

**這是規格裡完全沒有的東西**——原規格只寫「失敗就地停」，沒寫「修好之後怎麼接回去」。

**症狀**：第一次被 fail-closed 擋下時，run 停在「已停」，
然後**修好回執也收不進去**（「run 狀態是『已停』，不能收回執」）。

**修法**：`resume` 場景甲把狀態拉回「執行中」，重收同一跳的回執。

## 6.2 實作時踩到的坑（都是「寫完不看、跑一遍才現形」）

| # | 症狀 | 根因 | 修法 | 狀態 |
|---|---|---|---|---|
| 18 | `step` 指令炸：`Cannot read properties of undefined` | **狀態屬性名寫錯**：寫入用 `目前步驟`、讀取用 `目前步驤`（差一個字的同義詞），讀到 undefined ⇒ `steps[NaN]` | 統一用同一個字；教訓：**同一個概念在程式裡只能有一個拼法** | 🟢 已修 |
| 19 | 交接串一直是空的，可累積物沒寫進去 | **用 regex 抓 markdown 小節不可靠**：lookahead `\s*$`（m flag）在標題後的空白行立刻成立 ⇒ 捕獲到空字串；lazy + lookahead 又會吃掉最後一行 | 改成**逐行掃描**（`sectionLines`），放進共用模組 | 🟢 已修 |
| 20 | 三支工具各有一份 YAML parser，各錯一次 | 重複實作 | 抽出 `工作台.mjs` 共用模組（路徑解析 + YAML + 小節解析） | 🟢 已修 |
| 21 | 派單內容裡缺「需要（上一跳的可累積物）」 | 交接串寫入失敗（見 #19）⇒ 讀不到 | 隨 #19 一起修好 | 🟢 已修 |
| 22 | 門檻要人「手改執行狀態.md」 | 規格只寫了「停下等人」，沒寫怎麼繼續 | 加 `resume --門檻通過` 場景甲 | 🟢 已修 |

> **#18 是最值得記的一條**：一個字的差別，程式照跑不誤地寫進檔案，
> 讀的時候才發現是 undefined。**沒有實際執行過的程式碼，等於沒有驗證過。**
> 這也是為什麼 v0.3 的驗收是「端到端跑一遍」而不是「看程式碼對不對」。
