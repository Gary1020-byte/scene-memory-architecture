# 八 · 內容到鏡頭規格

> **這篇是「一支影片怎麼從素材長出來」的接縫規格。**
> 素材是唯一真源（`content.md`），鏡頭與報告頁是它的兩個消費者。
>
> **這篇的來源是實測**：2026-10-27 完整做過一次（`ai-agents-report`，4 分 30 秒、1920×1080、
> 繁中配音 ＋ 字幕、−16 LUFS），本篇把那次踩到的坑與驗收紀律寫成規格。

---

## 一、模型：兩條平行線，一個源

```
                        content.md（事實 ＋ 來源 URL）
                                    │
              ┌─────────────────────┴─────────────────────┐
              ↓                                           ↓
   線 A · 報告／簡報                              線 B · 影片
   OpenDesign（SSE 呼叫）                        narration.json（旁白稿）
              ↓                                           ↓
   report/*.html（單頁滾動／deck）              edge-tts 逐句 → assets/audio/line-NN.mp3
                                                          ↓
                                              audio_timing.json（每句時長）
                                                          ↓
                            ┌─────────────────────────────┼─────────────────────────────┐
                            ↓                             ↓                             ↓
                     make_beats.py               make_captions.py            build_scenes.py
                            ↓                             ↓                             ↓
                       beats.json                    captions.html            compositions/*.html
                            └─────────────────────────────┼─────────────────────────────┘
                                                          ↓
                                          hyperframes check → render → MP4
                                                          ↓
                                              REVIEW.md（抽 frame ＋ vision ＋ ffprobe）
```

> ★ **影片不是從報告 HTML 轉出來的。**
> 實測：`build_scenes.py` 讀的是 `audio_timing.json` 與 `beats.json`，
> **沒有讀 report HTML，也沒有讀 content.md**（內容硬編碼在 Python 裡）。
> ⇒ 兩條線共用的是**素材**，不是產物。

### 為什麼這樣分

| | 分開的好處 |
|---|---|
| 報告頁 | 承載完整細節（表格、來源），適合查 |
| 影片 | 只能講一個想法（REVIEW 裡的 rule：「End on the one idea in one line」） |
| 素材 | 事實只寫一次，兩邊都不會說謊 |

> ⚠️ **反過來說，兩邊要各自對齊同一份事實。** 素材改了 ⇒ 兩邊都要重做。
> 這就是「素材檔是單一權威」的另一面：**它是唯一真源，也是唯一需要同步的點。**

## 二、素材檔的規格

### 2.1 `content.md`（素材）

> ★ **格式規則（2026-11-03 實測修正）**
> 舊版寫「每條事實一行，附來源 URL」**自相矛盾**——同一節又允許表格。
> 實測（`ai-agents-report/content.md`）的真實做法是：
> **列表條目逐條附 URL；表格承載的事實以「表級來源群組」標註。**
> 照字面執行會把表格拆成逐行列表，與實測不符。

```markdown
# <主題>

## 0 導讀／層次定位
- 讀者要先建立的心智模型（例如「三者不在同一層」）

## 1-3 事實（分項）
- 列表條目 → 逐條附來源 URL
- 量化快照 → 標明「實查日期」

## 4 對照表／清單
- 表格形式；來源以「表級來源群組」標註
- ⛔ 不可刪欄位、不可摘要成「大部分一樣」

## 5 怎麼選（決策建議）
- 從對照推出來的結論

## 6 查不到／不確定的部分
- 三類：① 查不到可查證的數據 ② 來源互相衝突 ③ 來源版本落後
- 衝突時**並列寫出各說法與出處**，不挑一個當真的
```

> ★ **實測的素材是 6 節 ＋ 導讀，不是 3 節。**
> 漏掉「導讀／層次定位」與「怎麼選（決策建議）」會讓報告的骨架少兩根柱子——
> 實測報告頁的章節骨架（`report/ai-agents-report.html`）正是照這 6 節來的。

> ★ **「查不到就寫出來」是硬規則。**
> 實測：`REVIEW.md` 明寫「沒有做 Claude 模型的 benchmark 比較：查不到可查證的跨框架量化數據，
> 寫上去就是編」。這是**事實性 referent 必須用真實素材**的原則。

### 2.2 `narration.json`（旁白稿）

```json
[
  { "id": "line-01", "text": "三個 AI agent 工具，…", "path": "assets/audio/line-01.mp3", "duration": 10.68 }
]
```

| 欄位 | 誰寫 | 說明 |
|---|---|---|
| `id` | 人 | `line-NN`，**全片唯一** |
| `text` | 人 | 這句要說的話 |
| `path` | 工具 | 逐句 TTS 的音檔 |
| `duration` | 工具 | 這句的實測時長（**不是估的**） |

### 2.3 `audio_timing.json`（時間軸）

由 TTS 產出：**每句的起訖時間 ＋ 每句切成哪些詞、每詞多長**。

> ★ **時間軸必須來自實測音檔，不能用「字數 × 0.4 秒」估算。**
> 實測：15 段逐句生成後**按語速排入時間軸**，逐句對齊。

### 2.4 `beats.json`（節奏）

```json
{
  "per_scene": {
    "title": [
      { "t": 0.5, "end": 0.993, "sentence": "三個 ", "scene": "title",
        "element": "#a-title", "line": 1, "sent": 0 },
      { "t": 26.55, "end": 26.95, "sentence": "", "scene": "title",
        "element": "#a-layers .layer:nth-child(1)", "line": 2, "sent": 1, "filler": true }
    ]
  }
}
```

| 欄位 | 說明 |
|---|---|
| `t` / `end` | **絕對片長**時間（秒）——不是場景內相對時間 |
| `sentence` | 這一段唸的詞／片段（逐詞切分） |
| `scene` | 落在哪個 composition |
| `element` | **這段話對應的畫面元素**（CSS selector）⇒ spotlight 打在它身上 |
| `line` / `sent` | 第幾句旁白／那句的第幾個分句 |
| `filler` | 沒有對應詞，但畫面不能死掉 ⇒ 補一個空 beat |

> ★ **`element` 是這條鏈的核心。** 見下節。

### 2.6 ★ 消費者必呈現（2026-11-03 實測補）

> ★ **這是舊版最大的缺漏。**
> 舊版只要求「素材把查不到的部分寫出來」就停了——
> **沒有要求消費者（報告頁）必須把它呈現出去。**
> 照舊版走，報告頁完全可以不呈現這一章，
> 而**那正是「編」的溫床**：素材誠實了，但成品把它藏起來。

**硬規則：**

| # | 規則 |
|---|---|
| 1 | 報告頁必須把素材的不確定章節**升級為正式章節** |
| 2 | **逐條原樣列出**，不得摘要、不得改寫、不得補白 |
| 3 | 章節開頭要有一句明示（實測原句：「這一節是報告的一部分」「原樣保留，不做推測補白」） |
| 4 | 素材的「來源互相衝突」要在消費者端**原樣保留分歧**，不挑一個講 |

> 實測依據：`od-turn-1.txt` 第 1 條（「不要新增任何沒有來源的指標…」）
> ＋ `report/ai-agents-report.html:830-852`（7 條逐字保留）
> ＋ `REVIEW.md:33`。

### 2.7 ★ 交叉驗收：素材的數字要能在成品裡對到

**規則：成品裡的每個數字，都必須能在素材裡找到出處。**

| 檢查 | 做法 |
|---|---|
| 素材 ↔ 報告頁 | 抽出報告頁所有數字，逐個回素材比對（實測：9 個抽驗值全對得上） |
| 素材 ↔ 旁白稿 | **見 §六 的「口語化必須保留不確定性」** |

> ★ 實測的量化快照要標「實查日期」（`content.md:154` 的「可量化現況（2026-10-27 實查）」）——
> 沒有日期的數字，三個月後沒人知道它什麼時候過期。

### 2.8 ★ 同名 design system 防呆（2026-11-03 實測抓到的坑）

> **實測：有兩套完全不同、但都叫 `aurora` 的 design system。**

| | `open-design/design-templates/html-ppt/assets/themes/aurora.css` | `<vault>/.../<brand-design-system>/assets/vars-light.css` |
|---|---|---|
| 底／主色 | 深藍黑 `#06091c` ／ 青綠 `#5ef2c6`・藍 `#7aa2ff` | 暖白 `#FBF9F8` ／ 暖金 `#DEC16B`・深紫 `#32283F` |
| token 命名 | `--bg` `--accent` | `--c-bg` `--c-accent` |

> ⛔ **用名字選一定選錯。**
> 而且 `open-design/design-systems/` 的 148 套裡**沒有** aurora——
> Aurora 只在 vault 裡。

**規則：design system 要用「token 檔路徑」指認，不能只用名字。**
寫進素材／工作流的是路徑，不是「Aurora」三個字。

### 2.9 ★ canonical 素材路徑

> **「素材是唯一真源」在語意層成立，在檔案層有漂移風險。**
> 實測：同一份素材與報告存在**兩個目錄**（影片工程目錄 ＋ vault 專案目錄），
> 內容 md5 一致但**靠人工複製，沒有同步機制**。

**規則：**

| # | 規則 |
|---|---|
| 1 | 素材**只有一份檔案**，canonical 路徑要寫進工作流定義與場景記憶 |
| 2 | 其他目錄的副本視為**唯讀鏡像**；改素材必須同時改副本（目前靠人，要靠工具） |
| 3 | 產出物不要複製到第二處，除非有明確的「發布」動作 |

### 2.5 `compositions/*.html`（鏡頭）

HyperFrames 的每個場景一個 sub-composition。**渲染契約 12 條**由 `hyperframes` skill 擁有，
本節只列這條鏈額外要求的：

| 規則 | 為什麼 |
|---|---|
| 每個 timed 元素要有 `class="clip"` ＋ `data-start` ＋ `data-duration` | HyperFrames 的基本契約 |
| `element` 對應的元素**必須有穩定的 `id`** | spotlight 要打得到它 |
| `filler` beat 對應的元素要能被點亮 | 否則那 2 秒畫面是死的 |
| 一個 beat 群 = 一個 `data-track-kind="graphics"` 的 track | 一軌一類，Studio 才改得動 |
| 字幕字級 ≥ 34 px、位置 bottom 118 px | 28 px 是門檻；118 px 落在 action-safe 內又不壓主卡 |

## 三、★ SPOT 對照表：這條鏈的核心資產

**「旁白唸的這句話，畫面上哪個元素應該亮起來」**——這是**逐片手寫**的。

```python
# make_beats.py（實測）
SPOT = {
    (1, 0): ("title", "#a-title"),
    (1, 1): ("title", "#a-layers .layer:nth-child(1)"),
    (1, 2): ("title", "#a-layers .layer:nth-child(2)"),
    ...
    (9, 0): ("code", "#d-card1 .mech:nth-child(3)"),
}
```

> ★ **這是全片最難機械化的部分** —— 它需要「理解這句話在講哪個元素」，
> **任何演算法都推不出來**。
> 而它是**可累積的**：同類型的片子（產品比較、觀念教學）會用到同樣的對照模式。

### 3.1 三種填法（依可靠度排序）

| # | 做法 | 可靠度 | 成本 | 適用 |
|---|---|---|---|---|
| **A** | **在旁白稿裡直接標註**：`這句話[#a-layers .layer:nth-child(1)]` | ★★★ 最高 | 低 | 你自己寫稿時 |
| **B** | **語意比對**：拿元素的可見文字與旁白句比對 → 產生建議 → 人工確認 | ★★ | 中 | 稿子已定、元素已存在 |
| **C** | **模型草稿**：把旁白句 + 元素清單交給模型 → 產生 SPOT 草稿 → 人工確認 | ★ | 高 | 大量句子的初稿 |

> **★ 驗收只能驗「有沒有漏」，不能驗「對不對」。**
> 因為 SPOT 的正確性是語意的。
> 所以機械驗收只能做：**每個旁白句都有 SPOT** ＋ **每個 SPOT 的 selector 在畫面上真的存在**。

### 3.2 機械可驗的四條

| # | 檢查 | 擋還是警 |
|---|---|---|
| 1 | 每個 `(line, sent)` 都出現在 SPOT 裡 | **擋** |
| 2 | 每個 SPOT 的 selector 在對應 scene 的 HTML 裡真的存在 | **擋** |
| 3 | 沒有兩個相鄰 beat 指向同一元素又時間重疊 | 警 |
| 4 | 每個 beat 的 `t`/`end` 落在該 scene 的時間範圍內 | 警 |

> ★ **第 2 條能擋掉最常見的錯**：寫了 `#d-card1 .mech:nth-child(7)` 但畫面只有 6 個 ⇒
> spotlight 打在空處 ⇒ **畫面看起來沒反應，但 check 全綠**。

## 四、REVIEW 紀律：check 全綠不等於沒問題

> **這是這條鏈最重要的一條驗收規則**，而且是實測學到的。

### 4.1 `check --json` 抓不到什麼

實測案例（`REVIEW.md` §3b，**兩個 bug 存在時 check 回報 0 error、0 craft warning**）：

| # | bug | 症狀 | 為什麼 check 抓不到 |
|---|---|---|---|
| 1 | 六個機制列**露出順序反了** | 卡片看起來只有兩列、順序是倒的 | 元素都在、都在時間軸內 ⇒ 靜態審計無話可說 |
| 2 | 灰色說明框**壓到三張白卡上** | 視覺重疊 | 沒有溢出、沒有出界 ⇒ 不違反任何 layout 規則 |

### 4.2 所以驗收必須是三層

```
① check --json          靜態審計：契約違反、對比不足、音訊問題
② 渲染後抽 frame        ★ 用 vision 逐格看（13 個時間點 + contact sheet）
③ ffprobe 量             時長、音軌存在性、LUFS／dBTP／clipping
```

> ★ **② 是唯一能抓到「順序錯」與「疊在一起沒溢出」的方法。**
> ① 全綠 **不代表**沒問題——這是這條鏈最容易自信滿滿地踩空的假設。

### 4.3 REVIEW.md 的固定結構

```markdown
# REVIEW — <片名>
專案：<路徑>  片長：<秒> / <尺寸> / <fps>  配音：<引擎／聲線／rate>
## 1. 量到的 vs 只看的        ← 每項標明是量的還只是看圖
## 2. 做的 creative calls     ← 為什麼這樣選（以及為什麼不做某些）
## 3. 沒做的 storylines       ← 明講沒做什麼、為什麼
## 3b. 渲染後才發現的 bug      ← ★ check 全綠卻抓到的
## 4. 已知弱點                ← 誠實列出不滿意的地方
## 5. 刻意保留的項目          ← 那些看起來像 bug 但是故意的
## 6. 產出物                  ← 檔案清單
```

> ★ **§3b 與 §4 是最有價值的兩節。**
> §3b 是「工具的盲點」，§4 是「這次的成品還不夠好」——
> 兩者都是下一支片能直接用的資訊。**不要刪掉它們。**

## 六、兩條線各自的職責邊界

| | 線 A · 場景己 | 線 B · 場景庚 |
|---|---|---|
| 產出 | 報告頁／deck 的 HTML | MP4 ＋ 工程檔 ＋ REVIEW.md |
| 引擎 | OpenDesign（SSE 呼叫） | HyperFrames（HTML→MP4） |
| 共有 | **`content.md`** ＋ **design token** | 同左 |
| ⛔ 不做 | 不做影片 | 不做報告頁（那是線 A 的） |

> ★ **共用的是素材與 token，不是產物。**
> 兩個消費者**不互相轉換**（實測：影片沒有從報告 HTML 來）。
> 這是刻意的：**轉換會有損**（報告頁的表格在 1080p 裡塞不下、影片的節奏在單頁裡不成立）。

### 6.1 ★ 口語化必須保留素材的不確定性（2026-11-03 實測抓到的真斷裂）

> **實測兩個案例：**
>
> | # | 素材 | 旁白稿 | 問題 |
> |---|---|---|---|
> | 1 | `content.md:158` 的 `257,602` | 「二十五萬七千顆星」 | ✅ 數字對得上，只是口語化 |
> | 2 | `content.md:119` 的「架構頁 70+ / docs 60+ / README 40+ **三處不一致**」 | 只留「架構頁寫七十幾個工具」 | ⚠️ **不確定性被消化掉了** |

> ★ 第 2 個案例**不是編**（有出處限定），但**觀眾不會知道官方口徑有分歧**。
> **這正是口語化的副作用：它天然傾向於「講一個說法」。**

**規則：**

| # | 規則 |
|---|---|
| 1 | 口語化敘述中的數字**必須可回溯到素材原值** |
| 2 | 素材標記了「來源衝突／不確定」的地方，口語化**不得只挑一個說法講**；要講成「三處說法不一致」 |
| 3 | 省略是允許的，**但省略不能製造虛假的確定性** |

### 6.2 ★ 視覺 token 的真源（2026-11-03 實測修正）

> ★ **舊版把影片側的視覺來源寫成「OpenDesign `design-templates/hyperframes/` 的 9 個配色」——
> 這是歸屬錯。**
> 實測：**9 套 hyperframes palette 一套都沒用**（全是飽和多色系，與品牌不符）。
> 影片的主色來自 **Aurora**（`#DEC16B` ＋ `#32283F` ＋ `#6F677B`），
> 報告頁的 CSS 與 `compositions/*.html` 同色 ⇒ **兩條線的視覺 token 確實共用**。

| | 真相 |
|---|---|
| 9 套 hyperframes palette | **可用資源**，不是「已擁有且已用」 |
| Aurora token 檔 | **視覺真源**（兩條線共用） |

> 設計 system 要用**路徑**指認，見 §2.8。

## 七、這條鏈現在還缺的（規格層）

> ★ **2026-11-03 修正：舊版只盤了線 B 的缺口，線 A 的缺口整片沒列。**

### 7.1 線 A（場景己）缺口

| # | 缺什麼 | 影響 |
|---|---|---|
| A1 | **模板選用判準**（48 個模板各自適合什麼形狀／密度／語氣） | 每次都要重新挑；實測是「三個模板的組合需求」，單一模板都不夠 |
| A2 | **確認關卡的輸出格式**沒有定死（只寫了「先回報狀態」） | 每次回報的內容會飄 |
| A3 | **素材 ↔ 報告頁數字交叉驗收**沒有工具 | 見 §2.7，只能人工抽驗 |
| A4 | **canonical 素材路徑**沒有宣告 | 見 §2.9，副本會漂移 |
| A5 | **同名 design system 防呆** | 見 §2.8，「Aurora」有兩套 |
| A6 | **logo 取用規則**（抓不到就留空並註解，**絕對不要自己重畫或用近似圖形替代**） | 實測 `od-turn-1.txt` 硬要求 2，規格漏了 |
| A7 | **OpenDesign 呼叫層**不可重跑 | 改一版要重貼一次指令 |
| A8 | **單頁滾動 vs deck 的判準** | 素材是長文報告頁時，deck 形狀塞不下大表 |

### 7.2 線 B（場景庚）缺口

| # | 缺什麼 | 影響 |
|---|---|---|
| B1 | **內容硬編碼在 `build_scenes.py` 裡** | 每支新片要重寫 40 KB 腳本 |
| B2 | **SPOT 對照逐片手寫** | 見 §三 |
| B3 | **沒有「素材 → 旁白稿」的方法** | 旁白稿現在也是人手寫 |
| B4 | **OpenDesign 呼叫是手動 SSE** | 線 A 的問題，見 A7 |
| B5 | **REVIEW 的驗收紀律沒有工具** | 全靠人記得抽 frame —— ★ 最該先補的一條 |
| B6 | **口語化沒保留不確定性**（§6.1） | 觀眾以為官方只有一個說法 |

> ★ **B5 是最該先落地的一條**：把「check → render → 抽 13 個 frame → contact sheet」做成一支工具，
> 就能讓「渲染後驗收」從靠記得變成靠流程。
